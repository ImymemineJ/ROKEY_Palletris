## 1. 시스템 구조

### 1.1 전체 흐름

```
박스 스폰
  ↓
메인 컨베이어  ── RGB-D 카메라1 (크기 + 코드 인식)
  ↓            ── RGB 카메라2 (검증)
[Sorter 2방향] ──분기──→ Return Line (재순환 / 버퍼 우회)
  ↓ 직진
[3갈래 분기] ──→ A라인 / B라인 / C라인
                   ↓ 각 라인 끝
              스토퍼 + 구간 벨트 정지
                   ↓
              로봇팔 (구역별 1대) — 천장 RGB-D로 위치 확인
                   ↓ heightmap 배치 결정
              팔레트 적재 (흡착 pick & place)
                   ↓ 팔레트 완성
              전용 슬롯으로 트럭 상차
```

### 1.2 구역 정의

- **3구역 A / B / C**
- 분류 기준: **배송 순서** (마지막 배송지가 트럭 안쪽 슬롯)
- 구역당 로봇팔 1대 + 팔레트 1개

### 1.3 트럭

| 항목 | 값 |
|---|---|
| 적재함 | 2700 × 1600 mm (표준 1T) |
| 팔레트 | 1200 × 800 mm × 3개 |
| 배치 | 길이 방향 일렬, 폭 방향 1개 |
| 여유 | 폭 400mm / 길이 300mm (슬롯 간 100mm) |
| 상차 | **트럭 고정**, 라인별 전용 슬롯으로 측면 삽입 |

> ⚠️ **여유가 빡빡함.** 팔레트가 yaw로 조금만 틀어져도 걸림.
> 정렬 오차 허용치 **±50mm / ±2°**, 액추에이터에 가이드 레일 필수.

## 2. 박스

### 2.1 규격 (한국 표준 택배박스)

| 호수 | W × D × H (mm) | 부피 (m³) | 권장 질량 |
|---|---|---|---|
| 3호 | 340 × 250 × 210 | 0.0179 | 2 kg |
| 4호 | 410 × 310 × 280 | 0.0356 | 4 kg |
| 5호 | 480 × 380 × 340 | 0.0620 | 6 kg |

- **전부 10mm로 떨어짐** → heightmap 셀 10mm와 정확히 맞물림
- 질량은 **권장값, 미확정** (§9)
- 너무 가볍게(0.1kg 등) 잡으면 물리 솔버가 불안정해짐
- 그리퍼/로봇 링크 질량과 박스 질량 비가 100배 넘으면 솔버가 흔들림 → 링크 inertia도 확인

### 2.2 라벨 가정

**"라벨(QR/바코드)은 항상 박스 상단에 완벽하게 부착되어 있다"**

- 이 가정 때문에 카메라1은 사실상 절대 놓치지 않음
- → **reject line이 데모에서 한 번도 발동하지 않는 문제** 발생
- **해결책 채택**: 카메라1 인식 노드에 **인위적 드롭률 5%** 주입
  - 라벨 텍스처는 손대지 않음
  - "인식 노드가 가끔 프레임을 놓친다"는 소프트웨어 실패만 모델링
  - 코드 몇 줄로 reject line 시연 가능

## 3. 패킹 알고리즘

### 3.1 배치 규칙 — heightmap-greedy

두 점수의 가중합으로 후보를 평가:

| 점수 | 정의 |
|---|---|
| **높이 점수** | 바닥에 가까울수록 높음 |
| **지지율 점수** | 바닥면이 평평하고 잘 받쳐줄수록 높음 |

> 논문 용어로는 **DBLF(Deepest-Bottom-Left-Fill) + Max-Contact-Area 하이브리드**.
> 발표 시 이 이름을 쓰면 유리함.

**가중치는 미확정** (§9)

### 3.2 파라미터

| 항목 | 값 | 근거 |
|---|---|---|
| **격자 셀** | **10mm** (80 × 120 = 9,600셀) | 박스 치수가 전부 10으로 떨어짐. 5mm는 이득 없이 4배 무겁고, 20mm는 3단 이상에서 지지율 점수가 뭉개짐 |
| **회전** | **yaw 0° / 90°만** | 상단 라벨 가정 유지 + 흡착이 항상 위에서 접근 가능 |
| **탐색 방식** | **순수 online, lookahead 없음** | 눈앞의 박스 1개만 보고 즉시 배치 |
| **최대 높이** | 트럭 내치(1000) / 로봇 도달 / 물리 안정성 **중 최솟값** | §8에서 뒤 두 개 확정 |

### 3.3 그리퍼 간섭 — 수직 접근 통로 검사

heightmap은 "박스가 들어갈 자리"만 보지, 그리퍼가 내려올 공간은 안 봄.

**채택 방식 (swept-volume / corridor check):**

후보 위치에서 `박스 + 그리퍼` 단면을 목표 높이부터 현재 팔레트 최고점 위까지 **수직으로 쓸어올려**, 그 기둥이 heightmap과 겹치는지 검사.

- 주변이 비어있으면 **손해 0** (마진 팽창 방식은 5~10% 적재율 희생)
- heightmap 위에서 도는 계산이라 사실상 공짜
- **부수 효과: 경로계획이 불필요해짐.** 접근 경로가 뚫린 자리만 후보로 남으므로 충돌회피 로직이 필요 없음 → §4의 제어 스택 선택 근거가 됨

*(시간이 부족하면 임시로 마진 20mm 팽창. 세 줄이면 되고 대부분 막아줌)*

### 3.4 ⭐ 필수: place 후 실제 pose로 heightmap 갱신

**이걸 안 하면 4~5단에서 반드시 어긋나 적재율 숫자가 안 나옴.**

```
place 완료 → 0.5초 안정화 대기 → 실제 박스 pose 읽기 → heightmap 재갱신
```

- 알고리즘이 *"내가 놓으려 한 위치"* 를 믿으면 오차가 누적됨
- 실제 위치로 갱신하면 **자기교정**이 되어 오차 누적이 끊김
- 1차는 ground truth pose를 그냥 읽음 / 2차는 천장 RGB-D
- 실제 pose는 DB `boxes_sorted.place_x/y/z`에 기록

### 4.1 하드웨어

- **두산 H2017** — reach 1700mm, payload 20kg
- 상태: USD 로드 + 관절 구동까지 확인됨 (§8에서 재확인)

### 4.2 제어 스택 — 하이브리드

```
ROS2 레이어  → "무엇을 할지"   (next_box 요청, 상태 publish, 중재자 통신)
Isaac 내부   → "어떻게 움직일지" (Lula IK + 웨이포인트)
```

**선택 근거:**
- "미들웨어 ROS2 Jazzy" 요구사항 충족 (실제로 ROS2 노드가 시스템을 조율)
- MoveIt2 설정(SRDF, kinematics.yaml, ros2_control, Isaac 브릿지)에 1~2일 소요 — 6일에서 감당 불가
- **§3.3 통로 검사가 충돌회피를 대신하므로** 경로계획이 애초에 불필요

**발표 대비 답변:** *"정형화된 수직 pick & place라 경로계획 오버헤드가 불필요하고, 배치 알고리즘 단계에서 접근 가능성을 이미 보장한다"*

### 4.3 그리퍼 — SurfaceGripper

**안전장치 (필수):** 제어 코드에서 `grasp()` / `release()` 두 함수로만 호출하도록 감쌀 것.
5.1 API가 예상과 다르게 굴어도 함수 내부만 fixed joint로 바꾸면 되므로, 일정 손실을 반나절로 막을 수 있음.

### 4.4 픽업 방식 — 스토퍼 + 구간 벨트 on/off

```
픽업 구간(마지막 1~2m)을 별도 ConveyorBeltGraph로 분리
  + 컨베이어 끝에 스토퍼 (Cube에 Collider만, Rigid Body 없음)

박스가 스토퍼 도달 → 해당 구간 velocity = 0   (떨림 정지, 안정 흡착)
로봇이 집어감       → velocity 복구            (다음 박스 당겨옴)
스토퍼 도달        → 다시 0
```

**이 방식이 주는 것:**

| 효과 | 설명 |
|---|---|
| 대기열 자동 형성 | 앞 구간은 계속 도니까 뒤 박스가 밀려와 줄을 섬 → **백압 조율에 필요한 버퍼가 물리적으로 생김** |
| **픽업 위치가 상수** | IK 목표가 고정값. 매번 위치를 찾을 필요 없고 실패 지점이 하나 사라짐 |
| 떨림 제거 | 정지 중엔 벨트가 박스를 밀지 않음 |
| 안전망 | 정지 타이밍이 늦어도 스토퍼가 박스를 넘어가지 못하게 막음 |

## 5. 컨베이어 / 분기

### 5.1 파라미터

| 항목 | 값 | 근거 |
|---|---|---|
| **벨트 속도** | **0.5 m/s** | 문서 기본 1.0의 절반. 스토퍼 충돌이 부드럽고 2차 QR 모션블러도 절반 |
| **스폰 간격** | **4초에 1개** (0.25 boxes/s) | 3구역 처리 능력 0.3 boxes/s보다 **약간 낮게** — 평소엔 안정적이나 랜덤 편향 시 백압 발생 |
| **총 스폰** | **60개** | 구역당 팔레트 1개 ≈ 20개 × 3구역 |
| 데모 길이 | **약 5분** | 60 × 4초 스폰 + 마지막 처리 |
| 로봇 사이클 | 10초 (가정) | Day 1 실측 후 위 숫자 재조정 |

> **왜 "약간 빠르게"인가:** 스폰이 너무 느리면 로봇이 놀아서 버퍼가 안 차고,
> 그러면 §7 조율 실험에서 *"조율했는데 차이가 없네"* 로 끝남.

### 5.2 분기 구조

```
메인 → [Sorter 2방향] ──분기──→ Return Line
          ↓ 직진
      [3갈래 분기 에셋] ──→ A / B / C
```

Sorter가 **2개**로 끝나고 역할이 명확히 분리됨 (앞=reject/재순환, 뒤=구역 분류).

### 5.3 ⭐ 런타임 제어 방법

**`binary_switch`를 찾지 말 것.** 그건 원래 에셋에 없고, 5.1.0 버그 때문에 수업 문서 팀이 직접 만들어 넣은 노드임.

**실제 제어점은 Conveyor Belt 노드의 `direction` 입력 (float3):**

```python
import omni.graph.core as og

og.Controller.set(
    og.Controller.attribute(
        "<Sorter경로>/ActionGraph/conveyor_belt_01.inputs:direction"
    ),
    (1.0, 0.0, 0.0)   # 목표 방향 벡터
)
```

bool과 달리 **임의의 방향**을 줄 수 있어 3갈래/4갈래 모두 대응 가능.

### 5.4 Return Line

- **짧은 반송 컨베이어**로 물리 구현
- 두 가지 역할:
  1. **reject** — 카메라2 검증 실패 박스를 라인 앞으로 재순환
  2. **버퍼 우회** — 목표 구역이 꽉 찼을 때 중재자가 우회시킴 (§7)
- 재시도 카운터는 **반드시 분리** (§6.3)

## 6. 인식 / 데이터베이스

### 6.1 단계별 범위

| | 1차 (Day 1~3) | 2차 (Day 4~) |
|---|---|---|
| 박스 크기·구역 | **ground truth** | RGB-D 추정 |
| 코드 인식 | 없음 | QR/바코드 디코딩 |
| DB | 없음 (또는 최소) | 전체 파이프라인 |

**1차에서 인식을 빼는 이유:** 로봇 제어와 패킹 알고리즘 검증에 집중. 인식 파이프라인은 독립적으로 개발 가능.

### 6.2 카메라 배치

| # | 종류 | 위치 | 역할 |
|---|---|---|---|
| 1 | RGB-D | 메인 라인 | 박스 크기 + 코드 인식 |
| 2 | RGB | 메인 라인 (분기 전) | 검증 |
| 3~5 | RGB-D | 각 구역 천장 | 도착 박스 위치 파악 |

**설계 제약 (반드시 지킬 것):**

```
카메라1 ↔ 카메라2 간격 ≥ 컨베이어 속도 × 최악 지연 × 안전계수 3
```

최악 지연 = 프레임(33ms) + ROS2 이미지 전송(5~20ms) + QR 디코딩(10~40ms) + DB 왕복(1~10ms) ≈ **100~150ms**
0.5 m/s 기준 → **0.23m 이상**. 실용적으로 1~2m 띄우면 여유가 넘침.

> 단, **FPS가 떨어지면 이 계산이 무너짐.** 렌더가 10 FPS로 주저앉으면 프레임 간격만 100ms이고 디코딩 큐가 밀리면 지연이 무한정 늘어남. → §8 C11이 중요한 이유.

### 6.3 DB — SQLite + WAL

**선택 근거:** 박스가 4초에 1개(0.25 건/s) 들어오는데 SQLite는 초당 수천 건 처리. **3~4 자릿수 여유.** 성능이 논점이 될 상황이 존재하지 않음. 반면 PostgreSQL은 팀원 4명 환경 세팅에 반나절(6일의 8%)이 듦.

**확장성 질문 대비 답변:** *"현재 규모에서는 SQLite로 충분하고, 실제 창고 규모로 확장할 때는 PostgreSQL로 교체합니다. DB 접근을 ROS2 서비스 노드로 추상화했기 때문에 교체 범위가 그 노드 하나로 격리됩니다."*

#### 스키마

```sql
PRAGMA journal_mode=WAL;

-- DB1: 사전 입력 마스터
CREATE TABLE boxes_master (
    box_id       TEXT PRIMARY KEY,   -- QR/바코드 인코딩 값
    address      TEXT NOT NULL,
    delivery_seq INTEGER NOT NULL,   -- 배송 순서
    zone         TEXT NOT NULL       -- 'A'|'B'|'C' (delivery_seq에서 파생)
);

-- DB2: 입고 순서 분류 (카메라1이 기록)
CREATE TABLE boxes_sorted (
    seq        INTEGER PRIMARY KEY AUTOINCREMENT,
    box_id     TEXT NOT NULL,
    zone       TEXT NOT NULL,
    size_w     INTEGER, size_d INTEGER, size_h INTEGER,   -- mm 정수
    status     TEXT NOT NULL,
        -- SPAWNED|SCANNED|VERIFIED|DIVERTED|PICKED|PLACED|REJECTED
    place_x    INTEGER, place_y INTEGER, place_z INTEGER, -- mm 정수, 실제 놓인 위치
    scanned_at REAL, placed_at REAL,
    FOREIGN KEY (box_id) REFERENCES boxes_master(box_id)
);

-- 재순환 / 우회 카운터
CREATE TABLE recirculation (
    box_id      TEXT PRIMARY KEY,
    retry_count  INTEGER NOT NULL DEFAULT 0,  -- 인식 실패 (3회 초과 시 영구 제거)
    bypass_count INTEGER NOT NULL DEFAULT 0,  -- 버퍼 우회 (실패 아님, 제거 대상 아님)
    last_seen   REAL
);
```

> ⚠️ **`retry_count`와 `bypass_count`는 반드시 분리.**
> 버퍼 우회는 정상적인 흐름 제어이지 실패가 아님. 같은 카운터를 쓰면
> **정상 박스가 3바퀴 돌았다는 이유로 폐기됨.**

#### `status` 컬럼의 가치

박스 하나의 전 생애가 한 행에 기록되므로, 데모 후 이 테이블만 덤프하면 **모든 발표 지표가 SQL 몇 줄로** 나옴:

- 처리량 = `PLACED` 개수 ÷ 총 시간
- 인식률 = `SCANNED` ÷ `SPAWNED`
- 재순환률 = `recirculation` 기록 비율
- **적재율** = `place_x/y/z` + 크기로 계산
- 사이클 타임 분포 = `placed_at - scanned_at`

별도 로깅 시스템을 만드는 것보다 훨씬 싸고, 발표 전날 *"데이터가 없네"* 를 방지함.

#### ROS2 서비스 노드로 감싸기 (필수)

```
/db/register_box  (box_id, size)  → (zone, seq, ok)      # 카메라1
/db/verify_box    (box_id)        → (found, zone)        # 카메라2
/db/next_box      (zone)          → (box_id, size, seq)  # 로봇
/db/mark_placed   (box_id, pose)  → (ok)                 # 로봇
/db/zone_queue    (zone)          → (count)              # 중재자
```

| 이유 | 설명 |
|---|---|
| **writer 단일화** | 5개 노드가 각자 파일을 열면 `database is locked` 디버깅에 반나절 소모 |
| **트랙 병렬화** ⭐ | 다른 트랙은 스키마를 몰라도 서비스만 호출하면 됨. **Day 1에 이 5개만 합의하면 4명이 완전 독립 작업 가능** |
| 교체 가능 | PostgreSQL/인메모리로 바꿔도 이 노드 내부만 수정 |
| Mock 가능 | DB 노드 완성 전에도 다른 트랙이 가짜 응답으로 진행 |

### 6.4 ⭐ FIFO 가정이 깨지는 문제

원래 시나리오는 *"DB에서 해당 구역 **첫번째** 박스를 찾아 크기 확인"* 이지만, 이는 **DB 순서 = 물리적 도착 순서**를 전제함.

**재순환(§5.4)과 버퍼 우회(§7)가 이 전제를 깨뜨림.**

깨진 결과: 로봇이 *"첫번째는 5호(480×380)"* 라고 믿고 자리를 비웠는데 실제로 온 건 3호(340×250) → **heightmap이 통째로 어긋남**

**채택 해결책: 집기 직전에 ID 확인**

- 순서를 믿지 않음. 눈앞 박스의 ID로 DB를 조회해 크기를 가져옴
- 1차: 박스 prim에 ID를 심어두면 공짜
- 2차: 천장 RGB-D가 읽음

> 지금 명시하지 않으면 **Day 4에 재순환을 붙이는 순간 원인 모를 버그로 터짐.**

## 7. 멀티로봇 — 분기기 백압 조율

### 7.1 왜 조율이 필요한가 (물리적 근거)

세 구역이 **단일 자원(메인 라인 + 분기기)** 을 공유하므로 head-of-line blocking이 발생:

```
1. 랜덤 배정으로 A에 박스가 연달아 몰림
2. A 버퍼가 꽉 참 → A 라인 정지
3. A로 갈 박스가 분기기에 걸림
4. 분기기가 막히니 뒤에 줄 선 B, C 박스도 못 지나감
5. 메인 라인 전체 정지 — B와 C 로봇은 놀고 있는데도
```

**한 구역의 지연이 나머지 두 구역을 굶긴다.** 억지로 만든 게 아니라 레이아웃에 내재된 구조.

> **배송 순서 기준 분류(§1.2)가 이걸 더 심하게 만듦.** 입고 순서와 구역이 무관해서 순간적으로 한 구역에 연달아 몰릴 수 있음.

### 7.2 중재자 설계

각 구역 로봇 노드가 publish:
```
/zone_a/status → queue_len: 3, buffer_cap: 5, est_free_time: 12.4, state: BUSY
```

분기기 중재자 노드의 판단:

| 상황 | 결정 |
|---|---|
| 목표 구역 버퍼에 여유 있음 | 통과 |
| 목표 구역 꽉 참 | **Return Line으로 우회** → 나중에 재진입 |
| 세 구역 다 막힘 | 메인 라인 정지 + 스폰 중단 |

> Return Line이 여기서 **두 번째 역할**을 얻음. 씬에 이미 있는 걸 재활용하므로 **추가 비용 0**이고, "왜 반송 라인이 필요한가"에 대한 답이 두 개로 늘어남.

### 7.3 성과 측정

| 지표 | 조율 없음 (naive) | 조율 있음 |
|---|---|---|
| 메인 라인 정지 횟수 | N회 | ↓ |
| 총 정지 시간 | T초 | ↓ |
| 처리량 (boxes/min) | X | ↑ |
| 로봇 유휴율 | Y% | ↓ |

**naive 버전은 공짜** — 중재자를 끄면 그게 naive. 별도 구현 불필요.

### 7.4 구현 비용 및 함정

**비용: 반나절~하루** (중재자 노드 100줄 + publisher 각 20줄). **일정은 Day 5** — 로봇 3대가 다 돌아가야 백압이 재현됨.

**함정 3개:**

1. **분기점 도착 감지** — 벨트에 트리거 볼륨(충돌 트리거)을 놓되, **분기점보다 앞에** 둘 것 (결정 시간 확보. §6.2 카메라 간격과 같은 논리)
2. **버퍼 상태 조회** — 별도 센서 불필요. `/db/zone_queue`로 `zone=A AND status IN (DIVERTED, PICKED)` 세면 끝
3. **무한 루프** — 재시도 카운터를 reject용과 반드시 분리 (§6.3)

### 7.5 ⚠️ 실험 설계 (놓치면 결과가 안 나옴)

**백압 상황을 일부러 만들어야 함.** 랜덤 스폰이면 평균적으로 잘 분산되어 병목이 안 생기고, 그러면 *"조율했는데 차이가 없네"* 로 끝남.

→ **A로 5개 연달아 보내는 식으로 스폰 패턴을 편향**시킬 것. 코딩이 아니라 실험 설계 문제이고 30분이면 됨.

**채택 방식 — 하이브리드:**

| 대상 | 방식 | 이유 |
|---|---|---|
| 베이스 씬 (바닥, 컨베이어, 트럭) | 트랙 A가 GUI로 만들고 Collect해서 **고정** | 한 번 만들면 거의 안 바뀜 |
| 로봇 / 카메라 / 팔레트 배치 | **파이썬 스크립트로 런타임 add** | 자주 바뀜 → 코드니까 git으로 병합됨 |
| 박스 | 런타임 스폰 | — |

**GUI 작업은 초반 한 번뿐**이 되고, 카메라 위치 5mm 옮기려고 씬 파일을 주고받는 일이 사라짐.

**파일 전달은 rsync** (Collect된 USD는 수백 MB~GB, git에 절대 올리지 말 것).
**`scripts/sync_scene.sh` 를 쓴다 — 직접 rsync 를 치지 않는다.**

```bash
./scripts/sync_scene.sh                     # 기본: GUI 데스크톱 2대
SCENE_HOSTS="rokey@10.10.0.2 jik@10.10.0.9" ./scripts/sync_scene.sh   # 노트북 포함
```

`.gitignore`: `*.usd`, `*.usda`, `*.usdc`, `Collected_*/`

> **★ 원격 경로를 절대경로로 박지 말 것.** `rsync ... host:isaac_scenes/` 처럼 **상대경로**로 주면
> 원격 `$HOME` 기준이라 사용자명이 달라도 깨지지 않는다.
> **GUI 데스크톱 2대는 `rokey` 지만 개인 노트북은 각자 사용자명이 다르다** —
> 그래서 대상은 IP 가 아니라 `사용자명@IP` 로 적는다. (2026-08-22 수정)

### 10.4 트럭 상차 시 적재물 붕괴

실제 물류는 스트레치 랩으로 감지만 시뮬에는 없음.

- **채택: 가속도 제한만** (종이박스 마찰계수 μ≈0.3~0.5 → 미끄러짐 한계 약 3~5 m/s²로 여유 있음)
- ⚠️ **진짜 위험은 관성이 아니라 PhysX 솔버 지터.** iteration이 부족하면 **가만히 서 있기만 해도** 더미가 무너짐 → **G2가 먼저**

### 10.5 흡착 release 시 박스가 튐

낙하 높이 10mm만 돼도 착지 속도 √(2×9.8×0.01) = **0.44 m/s**.

**대책 (효과 큰 순):**

1. **§3.4 실제 pose로 heightmap 갱신** ← 근본 해결. 오차 누적을 끊음
2. **release 조건을 "도착"이 아니라 "정지"로** — TCP 속도 < 5mm/s **그리고** 자세 오차 < 임계값
3. **release 직후 damping 스파이크** — 0.5초간 linear/angular damping 5.0으로 올렸다 원복. 세 줄, 효과 즉각적
4. **물리 파라미터** (§10.6)
5. 현실적 질량 (§2.1)

> 1~5는 **그리퍼 방식과 무관하게 전부 필요함.** fixed joint를 써도 놓는 순간 박스는 자유낙하함.

### 10.6 물리 파라미터 기준값

| 항목 | 값 | 비고 |
|---|---|---|
| solver **position** iterations | **16~32** (기본 4) | ⭐ 정지 상태 붕괴의 주범 |
| solver velocity iterations | 4 (기본 1) | |
| rest offset | 0 | |
| contact offset | 2mm | |
| 마찰 (골판지) | static 0.6 / dynamic 0.5 | |
| stabilization threshold | ON | |
| sleep threshold | 낮게 | |
| **CCD** | **OFF** | 박스가 저속이라 불필요, 비용만 먹음 |

### 10.7 분기 시 박스 회전

벨트 표면 속도 벡터를 꺾는 순간 박스가 관성으로 밀리며 회전함. 마찰이 낮으면 미끄러지고 높으면 모서리가 걸려 돌아감.

→ **분기 구간 양옆에 가이드 레일**(단순 정적 콜라이더 벽)을 세우면 대부분 해결. 구현 비용 거의 없음. **Day 1 씬 작업에 포함.**

## 11. 단위 / 좌표계 규약

| 층 | 단위 | 예 (3호) |
|---|---|---|
| 사람 · 문서 · **DB** | **mm 정수** | `340 × 250 × 210` |
| **코드 · Isaac · ROS2** | **m** | `0.34 × 0.25 × 0.21` |
| **heightmap** | **셀 (10mm)** | `34 × 25` 셀 |

**DB에 mm 정수로 저장하는 이유:** `0.34 m`를 10mm 셀로 나누면 부동소수 오차로 `33.999...` → `33`셀이 될 수 있음. 정수 `340 ÷ 10`은 **정확히 34**. 박스 3종이 전부 10으로 떨어지므로 **오차가 원천적으로 없어짐.**

**변환은 아래 세 함수로만. 다른 곳에서 절대 직접 나누지 말 것:**

```python
MM_PER_CELL = 10

def mm_to_m(v_mm):    return v_mm / 1000.0
def mm_to_cell(v_mm): return v_mm // MM_PER_CELL   # 정수 나눗셈
def cell_to_mm(c):    return c * MM_PER_CELL
```

| **팔레트 적재율** | **70% 이상** | `place_x/y/z` + 크기로 계산 |
| **베이스라인 대비** | 단순 순차 적재보다 높을 것 | ⭐ **"최적화했다"를 증명하는 유일한 물건** |
| 처리량 | boxes/min | `PLACED` ÷ 총 시간 |
| pick & place 성공률 | % | |
| (2차) 인식률 | % | `SCANNED` ÷ `SPAWNED` |
| 조율 효과 | 라인 정지 횟수·시간 감소 | naive vs 중재자 (§7.3) |

> **베이스라인 비교는 반나절이면 되고, 이게 없으면 "최적화"라는 단어를 쓸 수 없음.**
> 절대 컷하지 말 것.

### 13.2 인프라

- 4대가 2.5G 스위치 + 고정 IP `10.10.0.1~4` + FastDDS 유선 화이트리스트로 이미 묶여 있음 (ping 0.25ms)
- **노드 분산: Isaac Sim 전용 1대**, DB·중재자·패킹 알고리즘은 다른 PC
  → Isaac 머신 CPU를 렌더링/물리에 집중 → **G3(FPS)에 유리**
- 네트워크 지연 0.25ms는 §6.2의 지연 예산(100~150ms) 대비 무시 가능
