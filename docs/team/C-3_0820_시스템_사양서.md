## 2. 엔드이펙터 — 흡착식

| 항목 | 값 |
|---|---|
| 방식 | **진공 흡착 (Suction)** |
| 패드 | **Ø50 mm × 4패드** (실용 16 kgf) — §4-4 |
| Isaac Sim 구현 | `SurfaceGripper` |
| 유효 가반 | 20 kg − 그리퍼 자중 ≈ **18 kg** |
| **실질 상한** | **흡착력 16 kgf** (Ø50 × 4패드) — §4-4. 가반하중이 아니라 흡착력이 병목 |

### ⚠ 현재 에셋과 불일치

`~/cobot3_ws`의 기존 USD에 붙어 있는 그리퍼는 **OnRobot RG2 — 2지 평행 그리퍼**다
(`SubUSDs/onrobot_rg2*.usd`). 흡착식으로 교체하는 작업이 **D 담당의 첫 작업**이다.

### 흡착식이 알고리즘에 거는 제약 (C 담당 필독)

- **릴리스 후 보정 불가**: 흡착은 놓고 나서 밀어 정렬하는 동작이 안 된다.
  패킹 알고리즘은 **놓는 순간 위치가 확정된다**는 전제로 작성한다.
- **상판 조건**: 평평하고 기밀이 되는 면이 필요하다. 테이프 요철·비닐 포장·골판지 통기성은 실패 요인.
  1차 시뮬에서는 **전부 흡착 성공으로 가정**하고, 이 가정을 결과 문서에 명시한다.
- **패드 배치 기준**: **가장 작은 박스**(3호 340×250) 상판보다 패드 span이 작아야 한다. → §4-4

## 3. 도달범위 검증

### 3-1. 좌표 기준

```
파렛트 영역   x: 0 ~ 1200 mm,  y: 0 ~ 800 mm
파렛트 상면   z = 150 mm
적재 상단     z = 1450 mm   (트럭 내高 1600 − 파렛트 150)
로봇 베이스   (600, −300, 700)   ← 장변 중앙 · 이격 300 · 받침대 700
```

### 3-2. 검증 결과

| 검증 지점 | 좌표 | 베이스까지 거리 | 1700mm 대비 |
|---|---|---|---|
| 먼 쪽 **상단** 모서리 | (1200, 800, 1450) | **1,460 mm** | 86% ✓ |
| 먼 쪽 **하단** 모서리 | (1200, 800, 150) | 1,368 mm | 80% ✓ |
| 이격 200mm로 축소 시 상단 | (1200, 800, 1450) | 1,386 mm | 82% ✓ |

**결론: H2017은 파렛트 전체를 한 자세에서 덮는다. 턴테이블·리니어축 불필요.**

> 위 값은 관절 구조를 무시한 구면 근사다. 실제 관절 한계·자세 제약을 반영하면 이보다 불리하므로,
> D 담당이 Isaac Sim에서 실측 검증한 뒤 받침대 높이를 확정한다.

## 4. 화물 — 박스

> **2026-08-20 변경**: 기존 "5 kg 미만" 제한을 **해제**한다. 이 제한은 M0609(유효 가반 4kg) 때문에
> 걸었던 것으로, H2017(유효 가반 18kg) 채택으로 근거가 사라졌다.

### 4-1. 확정 규격 — 우체국 택배 3 · 4 · 5호 (잠정)

| 구분 | 규격 | 치수 (mm) | 부피 | 중량 | 혼입 비율 |
|---|---|---|---|---|---|
| 소 | **3호** | 340 × 250 × 210 | 17.9 L | **3 kg** | **50 %** |
| 중 | **4호** | 410 × 310 × 280 | 35.6 L | **5 kg** | **30 %** |
| 대 | **5호** | 480 × 360 × 340 | 58.8 L | **9 kg** | **20 %** |

- 부피비 **1 : 2.0 : 3.3**
- 중량은 화물 밀도 150 kg/m³ 가정값. **중량 상한 10 kg** (§4-4 흡착력 제약)
- 비율은 소형이 많은 실제 택배 분포를 반영

> 우체국 택배 박스는 국내 사실상 표준이며 현재 0~5호가 유통된다(6호는 폐지).

### 4-2. 선정 근거 — 후보 비교

파렛트 1200×800, 적재 가능 높이 1300 mm (상단 1450 − 파렛트 상면 150) 기준

| 규격 | 층당 개수 | 층수 | 단일종 총개수 | 층 면적 활용률 |
|---|---|---|---|---|
| 2호 270×180×150 | 16 | 8 | 128 | 81.0 % |
| **3호** 340×250×210 | 9 | 6 | **54** | 79.7 % |
| **4호** 410×310×280 | 4 | 4 | **16** | **53.0 %** |
| **5호** 480×360×340 | 4 | 3 | **12** | 72.0 % |

| 후보 | 부피비 | 최소 상판 | 판정 |
|---|---|---|---|
| A안 2·3·4호 | 1 : 2.4 : 4.9 | 486 cm² | 박스가 작아 **사이클 수 과다** (혼합 60~90개/파렛트) |
| **B안 3·4·5호** | **1 : 2.0 : 3.3** | **850 cm²** | **✓ 채택** |
| C안 2·3·5호 | 1 : 2.4 : 8.1 | 486 cm² | 편차는 크나 사이클 수 과다 |

**B안 채택 이유 3가지**

1. **사이클 수가 적다.** 혼합 시 파렛트당 25~35개로, 4일 스프린트 안에서 시뮬을 여러 번 돌릴 수 있다.
   A·C안은 60~90개라 반복 검증 시간이 부족하다.
2. **최소 상판이 850 cm²로 넉넉하다.** 흡착 패드 배치에 여유가 있다 (§4-4).
3. **4호가 층 면적 활용률 53%로 잘 맞지 않는다.** 이게 오히려 장점이다 —
   격자로 딱 떨어지지 않아야 **온라인 패킹 알고리즘의 가치가 드러난다.**

### 4-3. 단계적 도입 — 1종 → 3종

**치수 3종은 확정하되, 스폰은 1종(3호)부터 시작한다.**
치수 확정을 미루면 흡착 패드 배치·가반하중·도달범위를 정할 수 없다.

지켜야 할 3가지:

1. **박스 규격을 코드에 하드코딩하지 않는다.** 설정 파일에 배열로 두고, 처음엔 원소만 1개로 시작한다.
2. **패킹은 처음부터 일반 온라인 휴리스틱으로 짠다.** 1종 전용 격자 패턴으로 짜면 3종에서 코드를 버리게 된다.
3. **1종 적재율을 성능 수치로 발표하지 않는다.** 상한 참고치로만 쓰고, 최종 수치는 3종 혼합으로 재측정한다.

```yaml
# boxes.yaml — 1단계는 3호만, 확장 시 주석 해제
boxes:
  - name: 3호
    size_mm: [340, 250, 210]
    mass_kg: 3.0
    ratio: 1.0        # 3종 전환 시 0.5
  # - name: 4호
  #   size_mm: [410, 310, 280]
  #   mass_kg: 5.0
  #   ratio: 0.3
  # - name: 5호
  #   size_mm: [480, 360, 340]
  #   mass_kg: 9.0
  #   ratio: 0.2
```

> 1종만 있으면 인식 노드가 치수를 상수로 반환해도 테스트를 통과한다.
> **B(인식) 정확도 검증은 3종 투입 후 다시 수행한다.**

### 4-4. ⚠ 실질 상한은 가반하중이 아니라 흡착력이다

H2017의 유효 가반은 18 kg이지만, **흡착식에서는 흡착력이 먼저 한계에 걸린다.**

진공 −60 kPa, 안전계수 3, 골판지 통기성 감안한 개략값:

| 패드 | 실용 흡착력/패드 | 4패드 | 6패드 |
|---|---|---|---|
| Ø40 mm | 2.6 kgf | 10.2 kgf | 15.4 kgf |
| **Ø50 mm** | **4.0 kgf** | **16.0 kgf** ✓ | 24.0 kgf |
| Ø60 mm | 5.8 kgf | 23.1 kgf | 34.6 kgf |

**권장: Ø50 mm × 4패드** — 최대 박스 9 kg 대비 여유율 약 1.8배.
최소 상판(3호 340×250)에 사각 배치해도 간격이 충분하다.

추가 제약:
- **박스 상판 강성**이 무게보다 먼저 문제가 된다. 골판지 상판은 무거운 내용물을 흡착으로 들 때 뜯어질 수 있다.
  실무에서 흡착식이 다루는 중량이 보통 10 kg 이하인 이유다. → **중량 상한 10 kg** 근거.
- 위 값은 개략 계산이다. **실제 그리퍼 스펙 확보 후 D 담당이 재검증**한다.

## 5. 트럭 · 파렛트

### 5-1. 1t 트럭 적재공간

| 항목 | 값 |
|---|---|
| 적재공간 | **2,800 × 1,600 × 1,600 mm** |
| 개방 방식 | 옆문 전면 개방 (측면 상차) |

### 5-2. 파렛트 배치 — 일자 3개 (확정)

1200×800 파렛트를 2800×1600 바닥에 **길이 방향으로 3개 일자 배치**한다.

```
길이 방향   800 × 3 = 2400 mm   ≤ 2800 mm   → 여유 400 mm ✓
폭  방향    1200 mm             ≤ 1600 mm   → 여유 400 mm ✓
```

| 배치 | 길이 여유 | 폭 여유 | 판정 |
|---|---|---|---|
| **800×3 일자 (채택)** | 400 mm | 400 mm | **✓ 3개** |
| 1200×2 · 800×2 (2×2) | 400 mm | **0 mm** | ✗ 상차 불가 |

**2×2 배치는 성립하지 않는다.** 폭 방향이 800×2 = 1600 mm로 화물칸 폭과 정확히 같아
여유가 0이다. 파렛트 공차·내벽 요철·롤러 삽입 여유를 하나도 줄 수 없고,
측면 슬라이딩 상차 방식에서는 특히 불가능하다.

남는 공간은 400 mm 폭의 띠 두 개뿐이라 어느 쪽에도 파렛트가 추가로 들어가지 않는다.
**3개가 이 조합의 최대치다.**

- 바닥 활용률: 3 × (1200×800) / (2800×1600) = **64 %**
- 대안 검토: T11(1100×1100)은 폭 방향 1열만 가능해 **2개** — 더 나쁘다
- **A/B/C 3구역 = 파렛트 3개 = 트럭 3자리로 처음부터 일치한다.** 구역 수와 적재 자리 사이에 불일치는 없다.

> 트럭 체적 활용률을 계산할 때는 이 64 %가 파렛트 적재율에 곱해진다.
> 파렛트 적재율(패킹 알고리즘 성능)과 혼동하지 않는다.

### 5-3. 구역 배정 — 배송지 기준 (확정)

A/B/C 구역은 **배송지 기준**으로 나눈다. 크기 기준이 아니다.

#### 단계별 구역 정보원

| | 1차 (4일 스프린트) | 2차 |
|---|---|---|
| 정보원 | **색 태그** | **송장 바코드** |
| 구현 | 기존 `m0609_color_detector.py` 확장 (HSV 범위 1개 추가) | 송장 텍스처 + 바코드 디코딩 |
| B 추가 부담 | 거의 없음 | **1인분 — 배분 재조정 필요** |
| 발표 논리 | "구역 태그를 색으로 대체한 시뮬 단순화" | 실제 송장 |

**바코드 인식을 1차에 넣지 않는 이유 4가지**

1. B는 D2~D3 이틀에 3D 치수·자세 추정을 해야 한다. 바코드는 별개 파이프라인이라 이틀에 둘 다 안 들어간다.
2. **시뮬에서 바코드는 비싸다.** 바코드 선을 해상하려면 카메라 해상도를 올려야 하고,
   그만큼 렌더가 느려진다 → A(환경)의 부담으로 전가된다.
3. **1차 검증 목표(적재율 · 3대 병렬)에 기여하지 않는다.** 구역 정보를 어디서 얻는가의 문제일 뿐이다.
4. **단일 실패점이 된다.** 바코드 실패 → 구역 미정 → 분기 실패 → 적재 실패.
   D3·D4가 주말이라 회수 시간이 없다.

#### ⚠ 1차를 "정답 그대로 통과"로 두지 않는다

스폰 시 부여한 구역을 그대로 흘려보내면 **브리핑 핵심 기능 2번 "인식 정보로 구역 판정"이 증명되지 않는다.**
색 태그를 쓰면 1차에서도 인식 → 구역 판정 → 3라인 분기가 실제로 닫힌 루프로 돈다.

기존 자산: `~/cobot3_ws/src/m0609/m0609/m0609_color_detector.py`
`/rgb` 구독 → HSV 마스크 → 안정화 → `/color_id` 발행. 현재 2색이며 **HSV 범위가 파라미터로 분리**되어 있다.

#### 지금 지켜둘 것

- **인터페이스는 이미 준비됨.** `B → C` 메시지의 `구역` 필드는 정보원이 색이든 바코드든 동일하다.
  2차 전환 시 **B 내부만 교체**되고 C·D는 영향받지 않는다.
- **태그 위치를 랜덤화한다.** 항상 같은 자리에 붙으면 B가 ROI를 하드코딩해도 테스트를 통과한다.
  (1종 박스만 쓸 때와 같은 함정 — §4-3)

### 6-3. 모션 경로 — 두 갈래 (§7 선택 항목)

| | MoveIt2 경로 | Isaac Lula / RMPflow 경로 |
|---|---|---|
| 설정 작업 | **없음 (repo 그대로)** | descriptor · rmpflow 직접 생성 |
| 충돌 회피 | OMPL 내장 | 충돌 구체 수동 정의 |
| 팀 경험 | 없음 | **M0609로 이미 구현** (`lula_ik/1_ik_single_pose.py`) |

### 6-4. 에셋 이동 시 주의

**USD만 복사하면 IK가 붙지 않는다.** URDF + descriptor + rmpflow(또는 MoveIt config)를 세트로 가져가야 한다.
