# 깊이 교차검증 — RGB 추정을 깊이 실측으로 대조한다 (트랙 D, 2026-08-26)

## 1. 왜 넣었나

지금까지 인식은 **RGB 실루엣 하나로 박스 높이를 추측**했다.
`geometry.box_pose_from_corners` 는 사양 3종(3호 210 · 4호 280 · 5호 340)의 높이마다
가상 평면을 놓고 윗면 네 모서리를 거기에 투영한 뒤, 투영된 치수가 사양과 가장 가까운
종류를 고른다.

쓸 만한 방법이지만 전제가 둘 깔려 있다.

1. 박스는 반드시 사양 3종 중 하나다
2. 윗면 네 모서리 검출이 정확하다

둘 중 하나라도 깨지면 **종류를 틀리고, 종류를 틀리면 투영 평면이 60~130 mm 어긋나
중심 x·y 까지 함께 틀어진다.** 카메라에서 나간 시선이 실제와 다른 높이에서 평면과
만나기 때문이며, 어긋남은 화면 가장자리로 갈수록 커진다. 그렇게 나온 좌표가
관제탑을 거쳐 로봇이 집으러 가는 자리가 된다.

**깊이는 그 높이를 직접 잰다.** 사양 표를 참조하지 않고 모서리 검출에도 기대지
않는다(윗면 안쪽 픽셀만 쓴다). 그래서 두 경로가 **서로 독립**이고, 독립이라야
교차검증이 성립한다. 같은 전제를 공유하는 두 계산은 나란히 틀린다.

`pick_cam` 은 이미 `model: rsd455` — RealSense D455 다. 깊이를 안 쓰고 있었을 뿐이다.

## 2. 구조

```
<ns>/rgb   ─┐
            ├─> CameraSub ─> DepthCrossCheck ─┬─> BoxAtPickup   (지금까지와 같음)
<ns>/depth ─┘   (링 버퍼)      (판정 한 곳)    └─> VisionCheck   (새 진단 채널)
```

| 파일 | 무엇 | ROS 의존성 |
|---|---|---|
| `packing_vision/depth.py` | 깊이 계산·판정 코어 | **0** (detect·geometry 와 같은 층) |
| `packing_vision/vision_node.py` 의 `DepthCrossCheck` | 설정·판정·발행을 한 곳에 | ROS |
| `packing_msgs/msg/VisionCheck.msg` | 두 경로를 나란히 싣는 진단 타입 | — |

**라인 인식(cam1·cam2)과 구역 인식(pick_cam)이 같은 판정기를 쓴다.** 판정을 양쪽에
나눠 두면 한쪽만 고쳐진 채로도 에러가 나지 않는다 — 이 저장소가 반복해서 데인
종류의 버그다 (CLAUDE.md §10-3).

### 코어 3단계

1. `top_plane_z` — 윗면 폴리곤을 30 % 안쪽으로 수축해 그 안의 깊이 픽셀만 본다.
   중앙값 → **절대 게이트(±60 mm)** → MAD 배수 순으로 이상치를 자른다.
2. `pose_from_plane` — 실측한 평면에 모서리를 다시 투영해 중심·yaw·치수·종류를 낸다.
   RGB 의 순환(높이를 모르면 크기를 못 재고, 크기를 모르면 종류를 못 고른다)이
   실측 높이 하나로 끊긴다.
3. `cross_check` — 높이 → 종류 → 중심 → yaw 순으로 대조한다.
   **앞이 뒤의 원인**이라 순서 자체에 뜻이 있다. 높이가 어긋나면 중심도 따라
   어긋나므로, 중심 불일치를 먼저 보고하면 진짜 원인이 가려진다.

### 네 가지 모드 · 세 층 설정

| 모드 | RGB 가 답을 냈을 때 | RGB 가 포기했을 때 |
|---|---|---|
| `off` | 깊이 구독조차 안 만든다 (예전 동작 그대로) | 버린다 |
| **`crosscheck`** (기본) | RGB 를 쓴다 + 깊이로 채점 | 버린다 |
| `rescue` | **RGB 를 쓴다** (crosscheck 와 동일) | **깊이가 건진다** |
| `prefer` | 깊이를 쓴다 | 깊이가 건진다 |

★ `rescue` 가 `crosscheck` 와 **RGB 가 답을 낸 경우 한 글자도 다르지 않은 것**이
핵심이다. 그래서 재현성이 안 깨진다 — 깊이 프레임이 왔든 안 왔든 좌표가 같다.
깊이는 **어차피 버려질 박스**만 건지므로 손해 볼 것이 없다.

설정은 **DEFAULTS(코드) ← `recognition.depth`(yaml) ← ROS 파라미터(런치)** 순으로 덮어쓴다 —
오른쪽이 왼쪽을 이긴다.

```bash
ros2 launch packing_bringup bringup.launch.py depth:=false        # 통째로 끄기
ros2 launch packing_bringup bringup.launch.py depth_mode:=rescue  # 버려질 박스만 건짐
ros2 run packing_vision zone_detector --ros-args -p depth.z_tol_mm:=30.0
```

**깊이가 없으면 지금까지의 동작 그대로 돈다.** 붙였다가 라인이 멈추면 안 되므로
깊이가 없는 쪽이 기본 경로이고, 있을 때만 확인이 하나 더 얹히는 구조다.
두 경로가 어긋나도 기본값은 **좌표를 막지 않는다** (`reject_on_disagree: false`) —
데모가 멈추는 쪽이 더 나쁘다는 판단이고, 막을지는 팀이 정한다.

## 3. 검증 — 무엇을 어떻게 쟀나

### 3-1. 코어 (Isaac 없이 · `test_depth_core.py` 32건)

같은 장면의 RGB 와 깊이를 직접 투영해 합성한 뒤 파이프라인에 넣는다.
**테스트의 절반은 RGB 를 일부러 틀리게 만들어 깊이가 잡아내는지 본다** —
두 경로가 독립이 아니면 교차검증은 아무것도 못 잡는다.

| 잰 것 | 결과 |
|---|---|
| 윗면 z 실측 오차 (4케이스) | **< 3 mm** · 산포 < 5 mm |
| 깊이 평면에서의 중심 오차 | **< 8 mm** · yaw < 3° |
| 결측 25 % + NaN 2 % + 이상치 2 % 주입 | 오차 **< 3 mm** (중앙값이 버틴다) |
| 종류를 한 칸 틀린 RGB 주입 | 3/3 **잡아냄**, 깊이는 안 틀림 |
| `rescue` 가 RGB 답을 낸 경우 crosscheck 와 같은가 | **같다** (재현성의 근거) |
| `rescue` 가 버려질 박스를 건지는가 | 3/3 · 오차 **< 5 mm** |
| 광축거리/시선거리 규약 혼동 | 허용치를 벗어나 **검사가 잡아냄** |
| 기울어진 면 (95 mm 단차) | `NOT_FLAT` · 평평한 면에서는 울리지 않음 |

**★ 이득을 숫자로:** 모서리 검출 치수가 **8 % 부풀면 RGB 는 판정을 포기한다**
(사양 3종 허용 오차 밖). 포기 = `BoxAtPickup` 미발행 = **그 박스는 통째로 버려진다.**
에러는 나지 않는다. 같은 장면에서 깊이는 중심을 **5 mm 안**으로 잡고 종류도 맞힌다
(8·10·12·15 % 전부). `mode: prefer` 면 그 좌표가 그대로 로봇에게 간다.

**h_weight = 3.0 의 근거:** 종류를 고를 때 높이에 주는 가중치다. 1.0 이면 15 %
부풀림에서 **깊이마저 4호를 5호로 본다** — 폭·깊이는 RGB 와 같은 모서리에서 나오므로
높이를 같은 가중치로 두면 독립성이 희석된다. 3.0 이면 실측 높이가 이긴다.
(`test_h_weight_1_would_mistype` 이 이 값이 장식이 아님을 지킨다.)

## 4. 재면서 틀린 것 — 같은 실수 반복 금지

| 처음 생각 | 실제 |
|---|---|
| "허용 시차 0.2 초면 넉넉하다" | **틀렸다.** 깊이가 한 프레임 늦어도 0.2 초 안에 들어오므로, 박스가 **아직 도착하지 않았던 직전 프레임의 벨트 깊이**를 현재 RGB 와 짝지었다 → `dz +280 mm` 의 가짜 불일치. **0.02 초(한 프레임 안)** 로 좁혔다 |
| "깊이는 최신 한 장만 있으면 된다 (큐 1)" | **틀렸다.** 깊이 프레임만 24 % 를 더 잃었다. 지금은 링 버퍼가 stamp 로 짝을 고르므로 **RGB 와 같은 QoS(큐 5)** 가 낫다 |
| "깊이 사용률이 낮다 = 인식 코드 문제" | **아니다.** 카메라 4대가 rgb(장당 2.7 MB)와 depth 를 함께 내보내면 UDP 단편 손실이 나고 **rgb 도 같이 잃는다.** DDS 버퍼를 16 MB 로 키우자 커버리지 4/8 → **6/8** |
| "`ros2 topic hz`/카운터로 재면 된다" | 카운터의 `spin_once` 루프가 초당 ~20 콜백밖에 못 돌아 **계측기 자신이 병목**이었다. 노드가 찍는 "짝 최소 시차"(300~714 ms)가 진짜 신호였다 |

## 4-1. ★ 왜 기본값을 `prefer` 로 안 두는가 (2026-08-26 결정 · 뒤집으려면 여기부터)

"깊이가 더 정확하면 그냥 깊이를 우선순위로 쓰면 되지 않나" 는 자연스러운 질문이다.
지금은 아니다. 이유 셋, **마지막이 제일 크다.**

1. **아직 진짜 깊이로 재 본 적이 없다.** 지금까지의 검증은 정답에서 만든 합성
   깊이라 두 경로가 당연히 일치한다. "깊이가 더 정확하다" 는 **기대이지 실측이 아니다.**
   이 저장소는 데스크 지표와 Isaac 실측이 **부호까지** 어긋난 적이 있다 (CLAUDE.md §10-1).
2. **계통 오차에 무방비다.** tf 가 조금 틀렸거나 `is_range` 가 반대면 모든 박스가
   같은 방향으로 어긋난다. `crosscheck` 는 그것을 불일치로 **드러내지만**,
   `prefer` 는 그 값을 그대로 **따라간다.** 오류를 잡던 장치가 오류를 실행하는 장치가 된다.
3. ★ **재현성이 깨진다.** `prefer` 는 깊이 프레임이 도착한 박스만 깊이를 쓴다.
   실측 도착률이 **8 개 중 5~7 개**라, 같은 시드로 돌려도 박스마다 어느 경로가
   쓰였는지가 네트워크 타이밍에 좌우된다. 평가 항목 **"재현성(Play/Stop)"** (§13) 과
   정면으로 부딪친다. `random_seed: 42` 를 못 박은 것과 같은 이유다.

### `prefer` 로 승격할 조건 3개

- [ ] (a) 씬이 깊이를 실제로 발행한다 (트랙 A · §5-3)
- [ ] (b) **진짜 Isaac 깊이로** `crosscheck` 를 돌려 불일치 기록이 충분히 쌓인다
- [ ] (c) 깊이 도착률이 100 % 에 가깝다 (rgb 와 같은 render product 면 자연히 된다)

**그 기록을 만들어 주는 것이 지금의 `crosscheck` 다.** 지금 `prefer` 로 넘기면
대조군이 사라져 **승격 근거 자체를 못 만든다.**

### 그 사이의 자리 — `rescue`

| | 재현성 | 계통 오차 | 이득 |
|---|---|---|---|
| `crosscheck` | 안 깨짐 | 안 탐 (드러냄) | 없음 (관측만) |
| **`rescue`** | **안 깨짐** | **안 탐** | **버려질 박스를 건짐** |
| `prefer` | 깨짐 | 탐 | 전부 |

실측 (ROS 층 ⑧절): 윗면 모서리가 12 % 부푼 장면에서 RGB 는 포기하고
`crosscheck` 는 좌표를 안 낸다 (`used=NONE` — **설계대로다**). 같은 장면에서
`rescue` 는 좌표를 내고 **오차 0.0 mm**, 종류(4호)도 맞힌다.

⚠ **인식률 회계 주의.** `rescue` 가 건진 박스를 실패로 세면 안 된다.
`_measure` 가 즉시 `ReportMiss` 를 부르던 것을 **살리기 시도 뒤로** 미뤘다 —
안 그러면 같은 박스가 실패로도 세지고 등록으로도 세어 **인식률 분모가 부푼다**
(분모 = 등록 성공 + 실패. `ReportMiss.srv` 주석 참조).

## 5. 미결 · 팀 확인 필요

1. **`packing_msgs` 에 `VisionCheck.msg` 를 추가했다** — 기존 타입은 한 글자도 안
   바꿨고 덧붙이기만 했지만, 공용이라 **팀 전원 재빌드**가 필요하다 (CLAUDE.md §14).
2. **`recognition.depth` 를 `system.yaml` 에 넣을지** — 지금은 `depth.py` 의
   `DEFAULTS` 가 값을 갖고 있고, yaml 에 키가 있으면 그쪽이 이긴다.
   승인되면 yaml 에 블록을 붙이기만 하면 되고 **코드는 한 줄도 바뀌지 않는다**
   (붙일 블록은 `depth.py` 머리 주석에 그대로 적어 뒀다).
3. **씬에 깊이 카메라 헬퍼가 필요하다 (트랙 A)** — `scripts/setup_camera_graph.py`
   에 이미 선례가 있다 (`cameraHelperDepth` · `type: "depth"` · 32FC1 · m).
   cam1·cam2·pick_cam 에 rgb·camera_info 와 **같은 render product** 로 붙이면
   stamp 가 정확히 같아져 짝 맞추기가 저절로 100 % 가 된다.
   ⚠ 시선거리(range) 로 내는 헬퍼를 쓰면 `depth.is_range: true` 로 바꿔야 한다 —
   틀리면 **화면 가장자리에서만** 어긋나 눈으로는 안 보인다 (교차검증이 잡는다).
4. **다중 PC 배포 시 DDS 버퍼** — 이미지가 커서 단편 손실이 난다.
   `FASTRTPS_DEFAULT_PROFILES_FILE` 로 송수신 버퍼 16 MB + `net.core.rmem_max` 를
   올릴 것. 이건 깊이만의 문제가 아니라 **RGB 도 같이 잃고 있었다.**
5. `reject_on_disagree` 를 켤지 — 어긋났을 때 좌표를 막을 것인가. 기본은 안 막는다.
6. **`depth_mode` 를 `rescue` 로 올릴지** — §4-1 표대로 **순이득이고 위험이 없다.**
   씬에 깊이가 들어오면 바로 켜도 된다 (`depth_mode:=rescue` 한 줄).
   기본값을 안 바꾼 것은 깊이가 아직 안 오는 동안 기본값을 흔들 이유가 없어서다.
7. **`prefer` 승격은 §4-1 의 조건 3개를 채운 뒤에.** 그 전에는 켜지 말 것.

## 6. 덤으로 고친 것 (검증 중 드러남)

- `verify_vision.py` 가 **QR 라벨을 그리지 않았다.** 그래서 "cam1 등록" 검사가
