# 깊이 교차검증 — RGB 추정을 깊이 실측으로 대조한다 (트랙 D, 2026-08-26)

## 1. 왜 넣었나

지금까지 인식은 **RGB 실루엣 하나로 박스 높이를 추측**했다.
`geometry.box_pose_from_corners` 는 사양 3종(3호 210 · 4호 280 · 5호 340)의 평면에
윗면 네 모서리를 각각 투영해, 잰 치수가 사양과 가장 잘 맞는 것을 고른다.

잘 도는 방법이지만 가정이 둘 깔려 있다.

1. 박스는 반드시 사양 3종 중 하나다
2. 윗면 네 모서리 검출이 정확하다

둘 중 하나가 깨지면 **종류를 틀리고, 종류를 틀리면 투영 평면이 60~130 mm 어긋나
중심 x·y 까지 같이 틀어진다.** 광선이 다른 높이에서 끊기기 때문이고, 화면
가장자리일수록 크다. 그 좌표는 관제탑을 거쳐 로봇이 집으러 가는 자리가 된다.

**깊이는 그 높이를 직접 잰다.** 사양 표를 안 보고, 모서리 검출에도 안 기댄다
(윗면 안쪽 픽셀만 쓴다). 그래서 두 경로가 **독립**이고, 독립이라야 교차검증이
성립한다. 같은 가정을 공유하는 두 계산은 나란히 틀린다.

`pick_cam` 은 이미 `model: rsd455` — RealSense D455 다. 깊이를 안 쓰고 있었을 뿐이다.

## 2. 구조

```
<ns>/rgb   ─┐
            ├─> CameraSub ─> DepthCrossCheck ─┬─> BoxAtPickup   (지금까지와 같음)
<ns>/depth ─┘   (링 버퍼)      (판정 한 곳)    └─> VisionCheck   (새 진단 채널)
```

| 파일 | 무엇 | ROS 의존성 |
|---|---|---|
| `packing_vision/depth.py` | 깊이 수학·판정 코어 | **0** (detect·geometry 와 같은 층) |
| `packing_vision/vision_node.py` 의 `DepthCrossCheck` | 설정·판정·발행을 한 곳에 | ROS |
| `packing_msgs/msg/VisionCheck.msg` | 두 경로를 나란히 싣는 진단 타입 | — |

**라인 인식(cam1·cam2)과 구역 인식(pick_cam)이 같은 판정기를 쓴다.** 함수로 흩어
두면 한쪽만 고쳐지고 그 상태로도 에러가 안 난다 — 이 저장소가 반복해서 데인
종류의 버그다 (CLAUDE.md §10-3).

### 코어 3단계

1. `top_plane_z` — 윗면 폴리곤을 30 % 수축해 그 안의 깊이 픽셀만 본다.
   중앙값 → **절대 게이트(±60 mm)** → MAD 배수 순으로 이상치를 자른다.
2. `pose_from_plane` — 그 평면에 모서리를 재투영해 중심·yaw·치수·종류를 낸다.
   RGB 의 닭-달걀(높이를 모르면 크기를 못 재고, 크기를 모르면 종류를 못 고름)이
   깊이 한 방에 끊긴다.
3. `cross_check` — 높이 → 종류 → 중심 → yaw 순으로 대조한다.
   **위쪽이 아래쪽의 원인**이라 순서에 뜻이 있다. 높이가 어긋나면 중심도 자동으로
   어긋나는데, 중심 불일치를 먼저 보고하면 진짜 원인이 가려진다.

### 세 가지 모드 · 세 층 설정

```
crosscheck (기본)  RGB 가 정하고 깊이는 확인만 한다
prefer             깊이가 잰 평면으로 좌표를 낸다. RGB 가 포기한 자리도 살린다
off                깊이 구독조차 안 만든다 (예전 동작 그대로)
```

설정은 **DEFAULTS(코드) ← `recognition.depth`(yaml) ← ROS 파라미터(런치)** 순으로 겹친다.

```bash
ros2 launch packing_bringup bringup.launch.py depth:=false        # 통째로 끄기
ros2 launch packing_bringup bringup.launch.py depth_mode:=prefer  # 깊이가 좌표를 정함
ros2 run packing_vision zone_detector --ros-args -p depth.z_tol_mm:=30.0
```

**깊이가 없으면 지금까지의 동작 그대로 돈다.** 붙였다가 라인이 서면 안 되므로
없을 때가 기본 경로이고, 있을 때만 확인이 하나 더 붙는 구조다.
기본값은 어긋나도 **좌표를 막지 않는다** (`reject_on_disagree: false`) —
데모가 서는 쪽이 더 나쁘다는 판단이고, 켤지는 팀이 정한다.

## 3. 검증 — 무엇을 어떻게 쟀나

### 3-1. 코어 (Isaac 없이 · `test_depth_core.py` 28건)

같은 장면의 RGB 와 깊이를 직접 투영해 만들고 파이프라인에 넣는다.
**테스트의 절반은 RGB 를 일부러 틀리게 만들고 깊이가 잡아내는지 본다** —
독립이 아니면 교차검증은 아무것도 못 잡는다.

| 잰 것 | 결과 |
|---|---|
| 윗면 z 실측 오차 (4케이스) | **< 3 mm** · 산포 < 5 mm |
| 깊이 평면에서의 중심 오차 | **< 8 mm** · yaw < 3° |
| 결측 25 % + NaN 2 % + 튄값 2 % 주입 | 오차 **< 3 mm** (중앙값이 버틴다) |
| 종류를 한 칸 틀린 RGB 주입 | 3/3 **잡아냄**, 깊이는 안 틀림 |
| 광축거리/시선거리 규약 혼동 | 허용치 밖으로 벗어나 **검사가 잡음** |
| 기울어진 면 (95 mm 단차) | `NOT_FLAT` · 평평한 면은 안 울림 |

**★ 이득의 정량:** 모서리 검출이 **8 % 부풀면 RGB 는 포기한다** (사양 3종 허용
오차 밖). 포기 = `BoxAtPickup` 이 안 나감 = **그 박스는 통째로 버려진다.** 에러는
안 난다. 같은 장면에서 깊이는 중심을 **5 mm 안**으로 잡고 종류도 맞힌다
(8·10·12·15 % 전부). `mode: prefer` 면 그 좌표가 그대로 로봇에게 간다.

**h_weight = 3.0 의 근거:** 종류를 고를 때 높이에 주는 무게다. 1.0 이면 15 %
부풀림에서 **깊이도 4호를 5호로 본다** — 치수는 RGB 와 같은 모서리에서 나오므로
같은 무게로 두면 독립성이 희석된다. 3.0 이면 잰 높이가 이긴다.
(`test_h_weight_1_would_mistype` 이 이 값이 장식이 아님을 지킨다.)

### 3-2. ROS 층 (`scripts/verify_vision.py` · 32FC1 경로)

| 확인 | 결과 |
|---|---|
| 멀쩡한 장면에서 두 경로 일치 | `OK` · dz **+0.0 mm** · dxy 0.0 mm · dyaw 0.0° |
| 깊이가 잰 높이 | **280.0 mm** (사양 280) · 윗면 유효비율 1.00 · 52080 px |
| 일부러 어긋내기 (RGB 4호 / 깊이 5호 높이) | `HEIGHT_MISMATCH` · dz **−60.0 mm** (예상 −60) |
| 그때도 좌표는 계속 나가는가 | 나간다 (`used=RGB`) |
| 깊이를 끊으면 | 강등(`used=RGB`) · `BoxAtPickup` 계속 나감 |

### 3-3. 전 구간 (`scripts/verify_ros_graph.py` · 16UC1 경로 · 8박스)

깊이 **켬/끔을 짝지어** 각 2회 돌렸다.

| | 적재 | 깊이 일치율 | 최대 dz |
|---|---|---|---|
| `depth:=true` ×2 | 8/8 · 8/8 | **100 %** (7/7 · 5/5) | **0.0 mm** |
| `depth:=false` ×2 | 8/8 · 8/8 | — | — |

**깊이를 켜도 적재 결과가 안 바뀐다.** 확인 채널이라는 말의 뜻이 그것이고,
같은 하네스에서 실제로 그런지도 같이 본다.

### 3-4. 끄기 스위치

| 설정 | `/pick_cam/depth` 구독 |
|---|---|
| 기본 | 있다 |
| `depth.enabled:=false` | **없다** |
| `depth.mode:=off` | **없다** |

launch 인자 `depth:=false` · `depth_mode:=prefer` 가 **인식 노드 4개 전부**
(라인 1 + 구역 3)에 같은 값으로 간다.

## 4. 재면서 틀린 것 — 같은 실수 반복 금지

| 처음 생각 | 실제 |
|---|---|
| "허용 시차 0.2 초면 넉넉하다" | **틀렸다.** 깊이가 한 틱 늦으면 그것도 0.2 초 안이라, 박스가 **아직 도착하지 않았던 직전 프레임의 벨트 깊이**를 현재 RGB 와 짝지었다 → `dz +280 mm` 가짜 불일치. **0.02 초(한 프레임 안)** 로 고쳤다 |
| "깊이는 최신 한 장만 있으면 된다 (큐 1)" | **틀렸다.** 깊이만 24 % 를 더 떨어뜨렸다. 지금은 링 버퍼가 stamp 로 짝을 고르므로 **RGB 와 같은 QoS(큐 5)** 가 낫다 |
| "깊이 사용률이 낮다 = 인식 코드 문제" | **아니다.** rgb(2.7 MB)+depth 를 카메라 4대가 함께 내면 UDP 단편 손실이 나고 **rgb 도 같이 잃는다.** DDS 버퍼를 16 MB 로 키우자 커버리지 4/8 → **6/8** |
| "`ros2 topic hz`/카운터로 재면 된다" | 카운터의 `spin_once` 루프가 초당 ~20 콜백이라 **계측기 자신이 병목**이었다. 노드가 찍는 "짝 최소 시차"(300~714 ms)가 진짜 신호였다 |

## 5. 미결 · 팀 확인 필요

1. **`packing_msgs` 에 `VisionCheck.msg` 를 추가했다** — 기존 타입은 한 글자도 안
   바꿨고 덧붙이기만 했지만, 공용이라 **팀 전원 재빌드**가 필요하다 (CLAUDE.md §14).
2. **`recognition.depth` 를 `system.yaml` 에 넣을지** — 지금은 `depth.py` 의
   `DEFAULTS` 가 값을 갖고 있고, yaml 에 키가 있으면 그쪽이 이긴다.
   승인되면 아래를 붙이기만 하면 되고 **코드는 한 줄도 안 바뀐다** (`depth.py` 머리 주석 참조).
3. **씬에 깊이 카메라 헬퍼가 필요하다 (트랙 A)** — `scripts/setup_camera_graph.py`
   에 이미 선례가 있다 (`cameraHelperDepth` · `type: "depth"` · 32FC1 · m).
   cam1·cam2·pick_cam 에 rgb·camera_info 와 **같은 render product** 로 붙이면
   stamp 가 정확히 같아져 짝 맞추기가 자연히 100 % 가 된다.
   ⚠ 시선거리(range) 로 내는 헬퍼를 쓰면 `depth.is_range: true` 로 바꿔야 한다 —
   틀리면 **화면 가장자리에서만** 어긋나 눈으로는 안 보인다 (교차검증이 잡는다).
4. **다중 PC 배포 시 DDS 버퍼** — 이미지가 커서 단편 손실이 난다.
   `FASTRTPS_DEFAULT_PROFILES_FILE` 로 송수신 버퍼 16 MB + `net.core.rmem_max` 를
   올릴 것. 이건 깊이만의 문제가 아니라 **RGB 도 같이 잃고 있었다.**
5. `reject_on_disagree` 를 켤지 — 어긋났을 때 좌표를 막을 것인가. 기본은 안 막는다.

## 6. 덤으로 고친 것 (검증 중 드러남)

- `verify_vision.py` 가 **QR 라벨을 안 그렸다.** 그래서 "cam1 등록" 검사가
  **이전 실행이 남긴 DB 행을 보고 통과**하고 있었다. `gen_master_db --reset` 을
  넣자 드러났다 — 없는 기능이 통과로 위장한 경우다. 라벨을 그리게 고쳤다.
- `vision_node._spin` 이 종료 시 `rcl_shutdown already called` 트레이스백을 남겼다
  (`rclpy.ok()` 로 감쌌다).
- `packing_vision/package.xml` 에 `cv_bridge` 선언이 빠져 있었다 (계속 import 해 왔다).
- `verify_ros_graph.py` 의 카메라 타이머가 0.1 초 주기인데 **초당 55 회** 돌았다
  (`MultiThreadedExecutor` + `ReentrantCallbackGroup`). 벽시계로 스스로 막게 했다.
