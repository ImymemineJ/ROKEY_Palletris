### 2-2-2. ★ 실제 값이 아닌 것 — 우선순위 순

**① 배치 성공률이 구조적으로 100 % 에 고착된다 (가장 심각)**

`metrics.py:39-40` 의 분모가 **이력(`box_events`)이 아니라 현재값 한 칸(`boxes_sorted.status`)** 이다.
그 칸은 재시도·거부로 즉시 덮어써진다 (`orchestrator_node.py:578-582`).

```
box_events 의 PICK_FAILED :  377건 · 박스 77개
boxes_sorted 에 남은 것   :  0개
→ place_success_rate = 72/(72+0) = 1.0  → 화면에 100.0 % 초록
→ 같은 원인으로 화면의 "실패" 칸도 377번 실패했는데 0
```

**고치는 법:** 분모를 `box_events` 에서 세면 된다. `metrics.py` 한 곳만 바꾸면
실시간 화면과 최종 보고서가 같이 고쳐진다 (그게 그 파일이 분리된 이유다, `metrics.py:3-6`).

**② 유휴율이 100 % 에 고착되고 빨강으로 칠해진다**

분모 `box_events.ts` 가 **sim 시계(5,839행)와 벽시계(2,357행)를 섞고 있다** (`_now()` 폴백).
`elapsed_s` 가 17.9억 초(약 56년)가 되어 `1 − 500/1.79e9 ≈ 100 %`.
`db_service_node.py:202-224` 가 이 증상을 정확히 경고하지만 **경고가 화면에 전달되지 않는다** —
`MetricsSummary` 에 "오염됨" 필드가 없다.

**③ 헤더 경과시계도 같은 값에 오염된다**

`dashboard.js:291-292` 가 `startTime = Date.now() − elapsed_s×1000` 을 쓴다.
현 DB 로는 **496,602 시간**이 찍힌다.

**④ 인식률 분모가 비대칭이다**

분자는 `COUNT(DISTINCT box_id)` 로 박스당 1회인데, 분모의 miss 는 **`scan_misses` 에
`box_id` 컬럼이 없어**(`schema.sql:79-84`) 중복 제거가 원리적으로 불가능하다.
실측 4,487 miss / 150 박스 = 30배 → **3.2 %**.
(2026-08-27 `058f196` 의 2초 쿨다운은 새 기록만 줄인다. 누적은 `--reset` 으로만 사라진다.)

### 2-2-6. 픽업 좌표는 어느 경로로 오는가 (2026-08-27 정정)

⚠ **앞서 "카메라가 아니다" 라고만 적었는데 그건 오해를 부른다.** 실제는 이렇다.

> 픽업 QR 해상도 문제(**실측 판독 3/202**)로 존 좌표는 Isaac 실측 대역이 낸다
> — `docs/2026-08-27_시연_다중PC_배치.md:65-66`

그 상황을 원천 차단하도록 이미 들어와 있다 — 좌표는 카메라, 신원은 **다른 토픽**

| 모드 | 존 픽업 좌표 | 신원 | 언제 |
|---|---|---|---|
| `PL_GTPICK=1` (코드 기본) | 씬 실측 | 씬 | **지금 시연 조합** — 픽업 QR 3/202 이라 |

**→ 대시보드가 할 일은 "위험 경고" 가 아니라 "지금 어느 모드인가" 를 화면에 띄우는 것이다.**

## 3. 데이터가 어디 있는가

| 화면 요소 | ROS | SQLite | 판정 |
|---|---|---|---|
| 팔레트 카드 (상태·적재수·충전율·최고높이·accepting) | ✅ `/zone_*/status` 2 Hz | — | **오늘 된다** |
| 상단 KPI 5종 | ✅ `/metrics/summary` 1 Hz | ✅ `metrics.collect()` | 배선 OK · 숫자는 §2③ |
| **3D 적재 (박스별 위치·크기·yaw·종류)** | ❌ **불가능** | ✅ `boxes_sorted` | **DB 만** |

| 반송/폐기 수 | ✅ `ZoneStatus.rejected_count` | ✅ | 오늘 된다 |
| 대기 수 | ⚠ 상수 0 | ✅ `boxes_sorted` | **DB 로** |
| 로봇 관절 자세 | ❌ `JointState` 발행자 0개 | ❌ | **범위 밖** |

### 왜 ROS 로 "불가능" 인가

```
packing_msgs/msg/*.msg (9개) + srv/*.srv (17개) 안의 배열 필드 = 0개
```

**하나도 없다.** 목록을 실을 수 있는 타입이 프로젝트에 존재하지 않는다. 만들면 **팀 4명 전원 재빌드**다 (CLAUDE.md §11·§14).

- 가장 가까운 `/algo/heightmap/{z}` 는 **2.5D 높이 격자**다. `heightmap_core.py:564` 의 `np.maximum` 이 박스 경계를 이미 뭉갠다 — id·색·경계를 되살릴 수 없다.
- 알고리즘 노드 메모리에는 목록이 실제로 있다 (`heightmap_core.py:157`·`:565` 의 `self.placed`). 그런데 **`box_id` 도 `color` 도 없고**(`(pose, w, d, h)` 튜플뿐) 내보낼 서비스도 없다.
- `algo_service_node.py:256-282` 의 스냅샷 JSON 은 기본 꺼짐 · `box_id` 없음 · 좌표가 **최소 모서리**(다른 모든 경로와 규약이 다름) · 로컬 파일이라 다중 PC 불가.

### `boxes_sorted` 가 필요한 걸 전부 갖고 있다

`schema.sql:47-61` — `box_id · zone · size_w/d/h_mm · mass_g · color · dest · status · place_x/y/z_mm · place_yaw_deg · spawned/scanned/picked/placed_at`.

쓰기는 `db_service_node.py:486-494` (`on_mark_placed` UPDATE) + `:499` (`_set_status` → `box_events` 동시 기록). **현재 DB 실측: PLACED 72개 전부 좌표가 있다** (A 25 · B 32 · C 15, 좌표 없는 행 0).

읽기는 **이미 저장소 관례다** — `file:...?mode=ro` 로 여는 파일이 10곳 (`pallet_access.py:33`, `plan_route.py:41`, `report.py:114`, `db_peek.py:53`, `seed_registry.py:66`, `gen_qr_labels.py:62`, `verify_vision.py:280`, `verify_ros_graph.py:403`·`:442`, `sim_main.py:666`). `schema.sql:14` 가 `journal_mode=WAL` 이라 읽기가 쓰기를 막지 않는다. **CLAUDE.md §10 "유일 writer" 규약을 안 어긴다.**

### 좌표 규약 — 여기 틀리면 3D 가 통째로 어긋난다

- `place_x/y_mm` = 박스 **중심**, `place_z_mm` = 박스 **밑면** (`PlacePose.msg:2-6`). z=0 이 팔레트 상면.
- **팔레트 로컬 mm.** 월드 변환은 `packing_robot/cycle.py:140-148` 의 `pallet_place_to_world` 를 **import**.
- 팔레트 치수는 **설정에서 읽는다.** `test_3.yaml:419-420` 이 축을 맞바꾼다 (§2②).
- **박스 종류는 `(w,d,h)` 로 유일하게 역산된다** — 3종 치수가 안 겹친다 (`system.yaml:13-15`). `db_service_node.py:96-98` 이 같은 이유로 이미 역인덱스를 만들어 쓴다.
- ⚠ **`color` 컬럼은 지금 못 쓴다.** 150행 전부 `'red'` 다. `vision_node.py:508` 의 `dominant_color_name(bgr) or "red"` 폴백이 원인이고 CLAUDE.md §15 "색 팔레트 공유" 가 열려 있다. → **치수 역산 종류(3호/4호/5호)로 칠한다.**

## 3-1. ★ 팔레트 판갈이 — 확정 (2026-08-27)

### 결정 두 가지

| 질문 | 결정 |
|---|---|
| 화면의 "트럭 1대" 는 무엇인가 | **지금 쌓는 중인 A/B/C 3장.** 트럭으로 나간 팔레트는 아래에 "출고 완료" 목록으로 따로 |
| 시연에서 판갈이를 보여주는가 | **보여준다** → DB 에 판 번호를 기록한다 |

### 무엇이 문제인가

관제탑은 `PALLET_FULL` 이 나면 팔레트를 간다 (`orchestrator_node.py:384`). 몇 판까지 갈지는
`PL_MAX_PALLETS` 이고 **기본값이 3** (`:177`).

판을 갈면 알고리즘은 heightmap 을 비우고 좌표가 **다시 높이 0 부터** 시작한다.
그런데 **DB 에는 판이 갈렸다는 기록이 어디에도 안 남는다.** `boxes_sorted` 는 그냥 `zone='B'` 로 쌓인다.

→ `WHERE zone='B' AND status='PLACED'` 는 **여러 판의 박스를 한 뭉치로** 돌려준다.
좌표가 전부 팔레트 로컬이라 겹쳐 보인다.

**실측 (2026-08-27, 현재 `palletris.db`)**

- B구역 "적재됨" 32개 중 **몸이 서로 겹치는 쌍 16개.** 한 판이면 0 이어야 한다
- 예: `BOX041`(t=497, 높이 210) 과 `BOX103`(t=1089, 높이 210) 이 **같은 자리 (173, 1069)**
- 예: `BOX086`(t=1003, 높이 770) 위에 쌓인 자리에 `BOX097`(t=1105) 이 **높이 0** 으로 놓임

### ★ 실측으로 확증 (2026-08-27) — 판갈이가 맞다

겹치는 쌍을 시각 순으로 갈라 보니 **경계가 정확히 두 개**, 즉 **팔레트 3장**으로 나뉜다.

| | 박스 | 최고 높이 | 구간 |
|---|---|---|---|
| 1판 | 7개 | 420 mm | t 83~497 |
| **2판** | **15개** | **1,180 mm** | t 525~1003 |
| 3판 | 10개 | 900 mm | t 1089~1532 |

- **겹침 16쌍 → 판별로 세면 0쌍.**
- 판이 **정확히 3장** — `PL_MAX_PALLETS` 기본값 3 과 일치한다.

→ **A2 를 하면 이 분리가 자동으로 나온다.**

### ⚠ 다만 원인이 하나 더 섞여 있다

| 원인 | 지금 일어나 있나 |
|---|---|
| ㉮ 팔레트 판갈이 | 일어날 수 있다 |
| ㉯ **예전 실행 기록이 남아 있다** | **이미 일어나 있다** |

`box_events` 를 훑으면 **시간이 뒤로 점프한 지점이 30군데** — 이 DB 에 실행이 **최소 31번**
섞여 있다. 재등록되지 않은 박스는 예전 실행의 좌표를 그대로 들고 있다
(`db_service_node.py:414` 는 **재등록된** 박스만 NULL 로 되돌린다).

→ 겹침 16쌍이 ㉮ 때문인지 ㉯ 때문인지 **DB 만 봐서는 못 가린다.**
실행 번호도 판 번호도 안 적혀 있기 때문이다. **그게 문제의 핵심이고, 고칠 것도 그것이다.**

### 박스는 충분한가 — 충분하다

| | 개수 | 근거 |
|---|---|---|
| 정답지 풀 | **구역당 50개** (총 150) | 아파트 5곳 × `households_per_apt: 10` (`gen_master_db.py:68`·`:73`) |
| 팔레트 하나 채우는 박스 | **20~29개** | CLAUDE.md 실측 (20/20 으로 9단 1300mm) |
| → 구역당 | **약 2.3판** | |

`PL_MAX_PALLETS` 기본 3 이 이 계산과 맞는다.

⚠ 다만 **풀이 다 흐르는 건 아니다.** 실측 실행은 A 25 · B 32 · C 15 로 풀의 절반도 못 갔다.

★ **그리고 이건 "2판이 다 차야" 생기는 문제가 아니다. "1판이 나가는 순간" 생긴다.**
2판에 박스가 하나만 놓여도 DB 는 이미 섞인다.

### 해결 — DB 에 판 번호를 기록한다

**① 스키마에 칸 하나** (`schema.sql` 의 `boxes_sorted`)

```sql
pallet_seq INTEGER DEFAULT 1      -- 이 박스가 몇 번째 판에 놓였나
```

**② 판갈이를 어떻게 아는가 — 이미 듣고 있다**

`db_service_node` 는 `/zone_{a,b,c}/status` 를 **이미 구독한다** (`db_service_node.py:188-191`).
지표에 `fill_rate` 를 얹으려고 원래부터 듣고 있었다.

관제탑은 판을 갈 때 `placed_count` 를 **0 으로 되돌린다** (`orchestrator_node.py:768`).

```
... 10 → 11 → 12 → 0 ← 여기가 판갈이
```

→ **`placed_count` 가 줄어드는 것만 보면 된다.** 늘기만 하는 값이라 줄면 판갈이다.

★ **새 msg/srv 를 안 만든다 → 팀 전원 재빌드가 없다** (CLAUDE.md §11·§14).
고칠 파일은 `schema.sql` 과 `db_service_node.py` — **둘 다 트랙 D** 다.

**③ `MarkPlaced` 때 현재 판 번호를 같이 넣는다** (`db_service_node.py:486-494` UPDATE 에 한 칸)

**함정 3개**

| 함정 | 대응 |
|---|---|
| 관제탑이 재시작해도 `placed_count` 가 0 이 된다 | 판 번호가 하나 헛되이 늘 뿐 **데이터는 안 섞인다.** 안전한 쪽 오류다 |
| `ZoneStatus` 를 놓치면 판갈이를 못 본다 | 2 Hz · RELIABLE 이라 드물다. 보험으로 "새 박스의 z 가 현재 판 최고높이보다 확 낮으면" 도 판갈이로 본다 |
| 판갈이 직후 `MarkPlaced` 가 상태 방송보다 먼저 올 수 있다 | 판갈이 후 다음 박스까지 수 초, 방송은 0.5 초라 사실상 없다. 나면 위 보험이 잡는다 |

**④ 기존 스크립트 2개도 같이 고친다**

`scripts/pallet_access.py:35-41` 과 `scripts/plan_route.py:43-48` 의 쿼리에 **현재 판만** 조건을 넣는다.
지금 둘 다 **조용히 틀린 채로 돈다** — 이미 트럭에 실려 나간 박스까지 넣고 꺼낼 순서와 배송 거리를 계산한다.

### 실행 섞임(㉯)은 따로, 그리고 더 급하다

판갈이는 안 일어날 수도 있지만 **실행 섞임은 이미 일어나 있다.** 지금 지표가 이렇다:

```
인식률 3.2 % · 로봇 유휴율 100 % · 경과 1.787e9 초(약 56년)
```

해결은 **`gen_master_db --reset`** 이다 (`gen_master_db.py:129-133` 이 `boxes_sorted`·`box_events`·
`scan_misses`·`recirculation` 를 전부 지운다). **코드 0줄** — `docs/관제탑_사용법.md` §0 이
이미 절차로 적어 뒀는데 안 지켜졌을 뿐이다. §7 D 참조.

## 4. ★ 구조 — 실전용 결정

### 4-1. 죽은 배선 3개의 공통 원인

§2 의 셋을 다시 보면 원인이 하나로 모인다. **브라우저가 ROS 를 직접 상대하고 있다.**

- ①은 토픽 이름을 JS 문자열로 적어서 틀렸다. 파이썬이었으면 노드가 같은 규약 상수를 쓴다.
- ②는 roslibjs 로 QoS 를 제대로 표현하지 못해서 연결이 안 됐다. **rclpy 였으면 `QoSProfile` 한 줄이다.**
- ③은 브라우저가 DB 를 못 보니 실행 구간을 자를 수 없어서 생긴다.

거기에 rosbridge 자체의 부담이 붙는다 — 어느 `package.xml` 에도 없는 apt 의존이고(8개 전부 확인, 0건), `start_dashboard.sh:38-40` 이 `ROS_DOMAIN_ID` 도 `ROS_AUTOMATIC_DISCOVERY_RANGE` 도 안 넘긴 채 띄운다.

### 4-2. 결정: 백엔드가 ROS 노드이자 웹서버다

```
                            PC3 (관제탑 · algo · db · 모니터링)
                    ┌──────────────────────────────────────────┐
브라우저 ─ WS/HTTP ─┤  dashboard_node  (FastAPI + uvicorn)      │
  (ROS 를 모른다)   │    ├ rclpy 구독  /zone_*/status           │
                    │    │            /zone_*/robot/event       │
                    │    │            /metrics/summary          │
                    │    │            (QoS 를 파이썬에서 지정)   │
                    │    ├ sqlite3   palletris.db  (mode=ro)    │
                    │    └ import    packing_db.{metrics,       │
                    │                 accessibility, route}     │
                    └──────────────────────────────────────────┘
```

**rosbridge 를 걷어낸다.** 브라우저는 이미 모양이 잡힌 JSON 만 받는다.

| 얻는 것 | 왜 |
|---|---|
| **QoS 버그 계통이 사라진다** | `QoSProfile(durability=TRANSIENT_LOCAL)` 을 파이썬에서 한 번 정확히 쓴다. §2② 가 재발할 수 없다 |
| **토픽 이름을 한 곳에서 만든다** | `f"/zone_{z}/robot/event"` — §2① 이 재발할 수 없다 |
| **늦게 접속해도 다 보인다** | 서버가 이벤트를 들고 있다가 새 접속에 재생한다. `live_view.py:43-44` 가 적어 둔 "지난 이벤트를 다시 주지 않는다" 한계를 **제대로** 푼다 |
| **zone 귀속이 서버에서 끝난다** | 구역별 토픽을 각각 구독하므로 어느 팔레트인지 확실하다. §15 의 `RobotEvent.zone` 논의가 불필요해진다 |
| **환경변수를 자동 상속** | `bringup.launch.py` 에 노드로 넣으면 `ROS_DOMAIN_ID`·`DISCOVERY_RANGE` 문제가 사라진다 |
| **CDN 의존 1개 감소** | roslibjs 가 필요 없다 (§8) |
| **프로세스가 하나** | rosbridge + http.server 두 개를 관리하지 않는다 |

### 4-3. FastAPI 를 쓰는 게 맞나 — 실측 기준

**쓴다.** 이유와 확인한 사실:

| 항목 | 확인 결과 |

| WebSocket 푸시 | 실시간 상태를 밀어야 하는데 표준 라이브러리로 WebSocket 서버를 쓰는 건 합리적이지 않다 |
| 설치 가능성 | `apt` 에 있다 — `python3-fastapi 0.101.0-3`, `python3-uvicorn 0.27.1-1`, `python3-starlette 0.31.1-1` |

**권장 배포:**

```bash

PYTHONNOUSERSITE=1 .venv-dashboard/bin/pip install -r scripts/dashboard/requirements.txt
```

### 6-1. ★ 네이버 Directions — 공식 문서 정독 결과 (2026-08-27)

문서: [Directions 5](https://api.ncloud-docs.com/docs/application-maps-directions5) · [Directions 15](https://api.ncloud-docs.com/docs/application-maps-directions15)

**우리는 Directions 15 를 쓴다.** 배송지가 15곳인데 Directions 5 는 경유지 상한이 5다.

| | Directions 5 | **Directions 15** |
|---|---|---|
| 경로 | `/map-direction/v1/driving` | **`/map-direction-15/v1/driving`** |
| 경유지 상한 | 5 | **15** |
| 목적지(`goal`) | 최대 10 (그중 최저비용 1곳을 고름) | 최대 10 (같음) |

호스트는 둘 다 `https://maps.apigw.ntruss.com`. `route.py:16-17` 이 이미 맞게 쓰고 있다 (`route.py:29` 이 `naveropenapi.apigw.ntruss.com` 은 전부 401 이라고 실측을 적어 뒀다).

**★ 문서가 직접 말하는 것 — 재현성이 깨진다**

> "All routes reflect real-time traffic; identical parameters do not guarantee identical routes."
> (실시간 교통을 반영하므로 같은 파라미터가 같은 경로를 보장하지 않는다)

이게 §6-3 캐시 결정의 **결정적 근거**다. `delivery_points.py:11-19` 가 지오코딩을 실행 중에 안 부르는 이유로 재현성을 들었는데, **경로 API 는 벤더가 그 사실을 명시하고 있다.** CLAUDE.md §13 "재현성(Play/Stop)" 이 평가 항목이다.

**지금 `route.py` 가 버리고 있는데 실전에서 값어치 있는 응답 필드 3개**

| 필드 | 내용 | 화면에서 |
|---|---|---|
| `summary.bbox` | `[[minLon,minLat],[maxLon,maxLat]]` | **지도 뷰포트 자동 맞춤.** 좌표를 손으로 안 맞춰도 된다 |
| `section[]` | `name`(도로명) · `congestion` **0~3** · `speed` km/h · `distance` m | **경로를 혼잡도 색으로 그린다.** 실전 관제 화면다워진다 |
| `guide[]` | `instructions`(턴바이턴) · `distance` · `duration` | 방문 순서 상세의 안내문 |

`route.py:113-121` 은 `distance_m`·`duration_s`·`toll_won`·`taxi_won`·`fuel_won`·`path` 만 담고 `bbox`·`section`·`guide` 를 버린다. **딕셔너리에 세 줄 추가하면 된다.**

**그 밖에 확인된 파라미터 규격**

- `option` 은 `:` 로 **최대 3개 동시 요청** — `traoptimal`(기본) · `trafast` · `tracomfort` · `traavoidtoll` · `traavoidcaronly`. **한 번 호출로 3개 경로를 비교할 수 있다.** `route.py:24` 의 주석은 앞 3개만 알고 있다
- `cartype` 1~6 (기본 1) — **통행료 계산에만 영향**
- `fueltype` `gasoline`(기본) · `highgradegasoline` · `diesel` · `lpg`
- `mileage` 기본 14, **범위 1~99** km/L
- `lang` `ko`(기본) · `en` · `ja` · `zh` — `route.py` 는 안 넘긴다
- 좌표는 **`경도,위도`** 순 (`route.py:63` 의 "★ 네이버는 경도가 먼저다" 주석이 맞다)
- `duration` 은 **밀리초** (`route.py:117` 이 `/1000.0` 로 이미 처리)
- 경유지 포함 직선 합계 **1500 km 상한** — 구로구는 무관
- ⚠ Directions 15 문서에 "**VPC 환경에서만 제공**" 이 있다. Application 등록 시 확인 필요 — **확인 안 된 사항이라 팀이 실제로 키를 발급해 봐야 안다**

**에러 코드가 진단이 된다 (`route.py:110-111` 은 지금 뭉뚱그린다)**

| code | 뜻 | 실전 대응 |
|---|---|---|
| 0 | 성공 | |
| 1 | 출발지와 도착지가 같다 | 왕복을 한 번에 부를 때 걸릴 수 있다 (§6-2) |
| **2** | **출발/도착이 도로에서 멀다** | **좌표가 틀렸다.** `delivery_points.py` 를 봐야 한다 |
| 3 | 자동차 경로 없음 | |

★ **2·4 는 "좌표가 틀렸다" 는 뜻인데 지금은 그냥 `RouteError` 로 뭉개진다.** `delivery_points.py:25-28` 이 "틀린 좌표를 넣으면 경로 API 가 엉뚱한 거리를 돌려주는데 에러는 안 난다" 고 경고한 그 상황을, **이 코드로는 잡을 수 있다.**

### 6-2. 15곳 통합 순서 — 계산 가능하다

지금 코드는 **구역별**이다 (`plan_route.py --zone B`). 목표는 트럭 1대 15곳 통합인데, `accessibility.best_visit_order` 는 전수 탐색이고 상한이 9곳이다 (`accessibility.py:186`). **15! ≈ 1.3조 — 못 돈다.** 상한을 넘으면 `ValueError` 를 내는 건 의도된 설계다 (`route.py:39-41` "조용히 어림짐작으로 갈아타지 않고 에러를 낸다").

**★ 그런데 통합 문제는 15! 이 아니다. 들어내기 제약이 팔레트 단위이기 때문이다.**

A 팔레트에서 박스가 깔려 있다고 C 팔레트 박스를 못 꺼내는 게 아니다. 그러니:

1. 팔레트마다 배송지가 **정확히 5곳**이다 (`delivery_points.py:49-52`, A 5 · B 5 · C 5)
2. 팔레트 안의 순서는 **전수로 정확히 푼다** — 5! = 120 가지. 지금 코드 그대로
3. 남은 건 **세 수열을 어떻게 끼워 넣느냐**뿐이다. 내부 순서를 유지한 채 섞는 경우의 수는

   ```
   15! / (5!·5!·5!) = 756,756 가지
   ```

   **전수로 돈다.** 직선거리로 75만개를 평가하고 상위 몇 개만 도로거리로 잰다.

★ 어림짐작이 아니라 **주어진 팔레트별 순서 아래에서 정확한 답**이라 발표에서 방어된다. 몇 개를 추렸는지는 `best_order` 가 이미 `trimmed` 로 알린다 (`route.py:161`).

**API 호출 횟수 — 앞서 "1회" 라고 한 것을 정정한다.**

`route.py:20` 의 `STOPS_PER_CALL = 16` (경유지 15 + 도착 1) 로 `measure()` 를 따라가면:

- 1회차: 출발=물류센터 · 경유지=1~14번 · 도착=15번
- 2회차: 출발=15번 · 도착=물류센터 (복귀)

→ **15곳 = 2회.**

이론상 "출발=물류센터 · 경유지 15곳 전부 · 도착=물류센터" 로 **1회**가 가능해 보이지만, 문서의 **code 1 "출발지와 도착지가 같다"** 에 걸릴 수 있다. **경유지가 있으면 어떻게 되는지는 문서에 없다 — 실제로 불러 봐야 안다.** 2회로 잡아 두고, 되면 줄인다.

### 6-3. 캐시 — 시연 중 네트워크에 기대지 않는다

**경로를 미리 계산해 `route_cache.json` 에 저장하고 대시보드는 읽기만 한다.**

근거 셋:
1. **벤더가 재현성을 보장하지 않는다** (§6-1 인용문)
2. `delivery_points.py:11-19` 가 같은 논리로 지오코딩을 이미 배제했다
3. 네트워크가 끊겨도 화면이 멀쩡하다

캐시에 **계산 시각 · 시드 · 박스 수 · 사용한 `option`** 을 같이 넣고 화면에 표시한다 — **어느 실행의 경로인지** 보여야 한다.

### 6-4. 지도

**타일 서버를 쓰지 않는다.** 배송지 15곳이 전부 구로구 안(위도 37.476~37.508, 경도 126.821~126.890)이라 **등장방형 투영 + `bbox` 정규화**면 충분하다 (§6-1 의 `bbox` 필드가 이걸 공짜로 준다). 인터넷 의존이 하나 더 사라진다.

선은 `path` 좌표열로 실제 도로 모양을 그리고, `section[].congestion` 으로 색을 나눈다.
