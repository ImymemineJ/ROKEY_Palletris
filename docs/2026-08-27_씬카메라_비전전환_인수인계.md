# 씬 카메라로 비전 돌리기 — 먼저 밟게 될 함정들

> 2026-08-27 김병직. 오늘 하루 풀 비전(등록 cam1 · 검증 cam2 · 픽업 좌표 pick_cam)을
> 끝까지 돌려 보며 **실측으로** 걸러낸 것들이다. 씬 쪽에서 카메라를 쏘기로 했다면
> 아래 ①②가 **지금 인식이 안 되는 직접 원인일 확률이 높다.** 그다음 ③~⑧은
> 이미지가 나오기 시작한 뒤에 순서대로 만나게 될 것들이다.

---

## ① 씬 카메라 그래프 7개가 전부 같은 토픽·같은 frameId 다 (치명)

새 `test_3.usd`(09:14) 를 뜯어본 결과다:

| 그래프 | 가리키는 카메라 | topicName | frameId |
|---|---|---|---|
| `ROS_Camera` | `rsd455_a` | `/rgb` `/depth` `camera_info` | `sim_camera` |
| `ROS_Camera_01` | `rsd455_b` | **같음** | **같음** |
| `ROS_Camera_02` | `rsd455_c` | **같음** | **같음** |
| `ROS_Camera_03` | `rsd455_b` (← `_01` 과 **중복**) | 같음 | 같음 |
| `ROS_Camera_04` | `rsd455_c` (← `_02` 와 **중복**) | 같음 | 같음 |
| `ROS_Camera_05` | `rsd455_1` | 같음 | 같음 |
| `ROS_Camera_06` | `rsd455_2` | 같음 | 같음 |

**문제가 둘인데 두 번째가 더 나쁘다.**

1. **토픽 충돌** — `/rgb` 한 곳에 발행자 7개. 구독자는 서로 다른 카메라 이미지를
   섞어서 받는다. 게다가 `vision_node` 는 `/cam1` · `/cam2` · `/pick_cam_{a,b,c}` 를
   보므로 **애초에 아무것도 안 온다.**
2. ★ **frameId 충돌** — `vision_node`(정확히는 `geometry.py`)는 **이미지 헤더의
   `frame_id` 로 tf 를 조회해서** 카메라 자세를 얻는다. 카메라 위치를 코드에 안 박는
   설계라서다. 7대가 전부 `sim_camera` 라고 말하면 **전부 같은 자세로 계산된다** —
   토픽을 갈라도 좌표가 통째로 틀린다. 그리고 `ROS2PublishTransformTree` 는
   프레임 이름을 **prim 이름**으로 정하므로, frameId 는 **prim 이름과 같아야 한다.**

### 맞는 값 (우리 `ros_graph.build_cameras()` 가 쓰는 정본)

| 용도 | 카메라 prim | nodeNamespace | 최종 토픽 | frameId |
|---|---|---|---|---|
| 투입부 등록 cam1 | `/World/rsd455_1/RSD455/Camera_OmniVision_OV9782_Color` | `/cam1` | `/cam1/rgb` · `/cam1/camera_info` | 리그 이름 (`rsd455_1`) |
| 투입부 검증 cam2 | `/World/rsd455_2/.../OV9782_Color` | `/cam2` | `/cam2/rgb` · `/cam2/camera_info` | `rsd455_2` |
| 픽업 A | `/World/rsd455_a/.../OV9782_Color` | `/pick_cam_a` | `/pick_cam_a/rgb` · `/camera_info` | `rsd455_a` |
| 픽업 B | `/World/rsd455_b/...` | `/pick_cam_b` | 〃 | `rsd455_b` |
| 픽업 C | `/World/rsd455_c/...` | `/pick_cam_c` | 〃 | `rsd455_c` |

- 해상도 1280×720 (`recognition.resolution`)
- **중복 그래프 `_03`·`_04` 는 지울 것** — 같은 카메라를 두 번 렌더한다. 렌더는
  프레임당 30~60 ms 로 **이미 병목**이라 렌더 프로덕트 하나가 그대로 배속을 깎는다.
  (1280×720 5대가 프레임당 약 33 ms 를 먹은 실측이 있다)

> 참고: 지금 우리 코드는 `PL_CAMROS=2` 일 때 **씬 카메라 그래프를 런타임에 끈다**
> (`ros_graph._mute_scene_camera_graphs`, PR #36). 씬이 제대로 쏘게 되면
> `PL_SCENE_CAMS=1` 로 살리거나 그 코드를 걷어내면 된다. 파일은 안 건드린다.

## ② `ROS2CameraHelper` 는 `camera_info` 를 안 쏜다

`ROS2CameraInfoHelper` 를 **따로** 붙여야 한다. `vision_node` 는 내부 파라미터(K)를
코드에 안 박고 `camera_info` 에서 읽으므로, 없으면 조용히 **"camera_info 대기 중"**
으로 멈춘다 — 이미지는 오는데 좌표가 안 나가는 상태다.

## ③ 광학 프레임이 tf 에 있어야 한다

`geometry.py` 의 좌표 규약은 **ROS 광학 프레임**(x 오른쪽 · y 아래 · z 앞)이다.
tf 에 그 프레임이 없으면 인식이 전부 `평면이 카메라 뒤에 있다` 로 죽는다.
우리는 `_ensure_optical_frames()` 로 만들어 **씬의 tf 노드 targetPrims 에 추가**한다
(`ros_graph.py:298` 부근). 씬이 tf 를 소유한다면 그쪽에도 같은 프레임이 들어가야 한다.

## ④ 오프스크린 렌더는 GUI 조명을 못 받는다

돔 라이트가 없으면 **눈으로는 멀쩡한데 카메라 이미지만 캄캄하다.** 지금 씬에는
`/Environment/defaultLight`(DistantLight) 하나뿐이고 **DomeLight 는 없다.**
인식이 "아무것도 검출 안 됨" 이면 이것부터 의심할 것 (CLAUDE.md §5).

## ⑤ 카메라 토픽 QoS 는 `qos_profile_sensor_data` (BEST_EFFORT)

기본 RELIABLE 로 구독하면 이미지가 **하나도 안 온다.** 이건 구독자 쪽 이야기지만
"토픽은 보이는데 콜백이 안 돈다" 면 여기다.

# 이미지가 나오기 시작한 뒤 만날 것들 (전부 오늘 실측)

## ⑥ ★ 실루엣 부풀기 — 오늘 인식 실패의 **최대 원인**이었다

박스가 카메라 축에서 옆으로 벗어나면 **먼 쪽 옆면이 실루엣에 끼어** 측정이 부푼다.

```
부풀기 ≈ 박스높이 × 축오프셋 ÷ 카메라높이
```

이게 서로 달라 보이는 증상 셋의 **공통 뿌리**였다:

| 증상 | 실측 | 처방 |
|---|---|---|
| cam1 이 3호를 4호로 등록 | 장변 343 → 397 (간극 +72 = 높이차 70) | **중앙 게이트**: 화면 중앙 1/3 폭 밖이면 측정 자체를 건너뛴다. 2/3 폭에서는 3/4호 경계(375mm)에서 재발했다 → 1/3 로 좁혀 **54/0** 달성 |
| 픽업 5호 인식 0/443 | 오프셋 170mm 에서 +40mm | 치수 맞춤 상한 60 → 110 → **340mm** |
| 정위치 5호도 기각 | 541×445 (오차 126~133) | 위와 같음 (원근 옆면) |

★ 상한을 크게 올려도 **안전한 이유**: 존 인식의 "종류" 는 **좌표 투영 평면**에만
쓰이고, 로봇에 가는 치수·높이는 **DB**(cam1 등록값)에서 온다. 오분류의 해악은
중심이 수십 mm 밀리는 정도라 흡착 패드 여유 안이다. 종류 간 간격이 70mm 라
부푼 5호도 최근접은 여전히 5호다.

## ⑦ 병합 실루엣 — 존이 **조용히** 죽는다

두 박스가 붙어 스토퍼에 오면 실루엣이 합쳐져 `857×712` 같은 값이 나온다.
사양 3종 어느 것과도 안 맞으니 detector 는 **`box_at_pickup` 을 한 번도 안 낸다** —
에러도 없고 관제탑은 영원히 기다린다. 처방 둘:

- **원인 제거**: 점유 기반 지선 제어(`PL_SPUR_STOP=2`) — 스토퍼에 박스가 있으면
  지선을 세우고, 비면 재가동. 애초에 둘이 안 붙는다.
- **자가 회복**: 관제탑이 신원 대역(`/zone_*/box_ident`)으로 12초 감시 → 치운다.

## ⑧ 팔레트 위 박스를 스토퍼 박스로 오검출

C존에서 `541×445` 가 잡혔는데 계산해 보니 **5호 × 1.148** — 팔레트 위 박스였다
(상면 1290 vs 가정 1140). 처방: **픽업 ROI 마스크** — 스토퍼 창 8점을 K·R·t 로
픽셀에 투영해 그 밖을 지우고 검출한다 (`vision_node._pickup_roi`).

## ⑨ 로봇 팔이 카메라를 가린다

풀 비전에서 대기 자세가 스토퍼 위면 픽 실패 후 **재인식이 영영 안 온다.**
→ `PL_GTPICK=2` 일 때 대기 자세 자동 오프. 더 근본적으로는 **"스토퍼에서 한 번
인식했으면 흡착 실패해도 재인식 없이 바로 재시도"** 로 설계를 바꿨다.

## ⑩ 픽업에서 QR 재판독은 포기하는 게 맞다

해상도상 판독률이 **3/202** 였다. 사양(§5)도 `pick_cam` 은 **좌표 실측만** 한다고
정해 놨다. 그래서 **좌표 = 카메라 · 신원 = DB/씬** 으로 대역을 갈랐다
(`/zone_*/box_ident`). 픽업에서 box_id 를 못 읽는 건 버그가 아니다.

## 진단할 때 제일 도움이 된 것

**기각 사유에 실측치를 실은 것** (`geometry.LAST_REJECT` → 경고 문구):

```
사양 3종 어느 것과도 안 맞는다 — 좌표를 내지 않는다 [실측 857x712 mm (최근접 5호 오차 713)]
```

이 숫자 하나로 **병합(700mm대) · 부풀기(+40) · 완전 오측**이 즉시 갈린다.
없을 때는 "인식이 안 된다" 로만 보여서 어디를 봐야 할지 몰랐다.

## 빠른 점검 순서

```bash
ros2 topic list | grep -E "cam|rgb"          # 토픽 이름이 갈려 있나
ros2 topic hz /cam1/rgb                       # 실제로 오나
ros2 topic echo /cam1/camera_info --once      # info 가 나오나 (K 없으면 멈춘다)
ros2 run tf2_ros tf2_echo world rsd455_1      # frameId 로 tf 가 잡히나
```

넷 다 통과하면 그다음은 ⑥ 부풀기다.
