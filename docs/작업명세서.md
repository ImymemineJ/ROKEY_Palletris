```python
# packing_common/units.py — 전원 import. 다른 곳에서 직접 나누기 금지
MM_PER_CELL = 10
def mm_to_m(v_mm: int) -> float:   return v_mm / 1000.0
def m_to_mm(v_m: float) -> int:    return int(round(v_m * 1000))
def mm_to_cell(v_mm: int) -> int:  return v_mm // MM_PER_CELL
def cell_to_mm(c: int) -> int:     return c * MM_PER_CELL
```

> **왜 DB가 mm 정수인가:** `0.34 m`를 10mm로 나누면 부동소수 오차로 `33.999…` → `33`셀이 될 수 있다.
> 정수 `340 // 10`은 **정확히 34.** 박스 3종이 전부 10으로 떨어지므로 오차가 원천 소멸.

### 1.5 ★ 서비스 호출 규약 — 어기면 데드락

**rclpy에서 `spin_until_future_complete()`를 콜백 안에서 부르면 응답이 영원히 안 오고 에러도 안 난다.**
구독 콜백이든 **타이머 콜백이든 똑같다.** executor 스레드가 그 콜백 안에 갇혀 응답을 처리하지 못하기 때문.

**방법 1 — 권장. 블로킹이 필요하면 이것만.**
```python
from rclpy.callback_groups import ReentrantCallbackGroup
from rclpy.executors import MultiThreadedExecutor

cb = ReentrantCallbackGroup()
self.cli = self.create_client(GetBoxInfo, '/db/get_box_info', callback_group=cb)
self.sub = self.create_subscription(BoxAtPickup, '/zone_b/box_at_pickup',
                                    self.on_box, 10, callback_group=cb)
# main:
rclpy.spin(node, executor=MultiThreadedExecutor())
```

**방법 2 — 논블로킹. `call_async` 후 즉시 return.**
```python
def on_timer(self):
    if self._fut is None:
        self._fut = self.cli.call_async(req)
        self._fut.add_done_callback(self._on_done)     # 또는 다음 틱에 .done() 폴링
        return                                          # ★ 여기서 반드시 return
```

> ❌ **금지:** 어떤 콜백 안에서도 `spin_until_future_complete` / `rclpy.spin_once`.
> §6.7의 2 Hz 타이머에서 `/db/zone_queue`를 부르는 것도 여기 해당된다.

**김학민이 Day 1 A2 스켈레톤에 방법 1·2 예제 노드를 각각 하나씩 포함시킨다.**

**공통 규약:**

| 항목 | 값 |
|---|---|
| 타임아웃 | **2.0초** (`service.timeout_s`) |
| 재시도 | 1회 |
| 최종 실패 시 | B는 `ZoneStatus.state="BLOCKED"` 발행 + 벨트 재가동, ERROR 로그 |
| **예외** | `/diverter/request`는 **0.6초** (§8.9) — 박스가 분기점을 지나가버리기 때문 |

### 2.2 서비스

#### DB — 제공: **민범진**

```
/db/register_box     (box_id, size_w_mm, size_d_mm, size_h_mm)
                  →  (ok, zone, db_seq, message)

/db/verify_box       (box_id)                → (found, zone, retry_count)
                     # 호출자: 중재자(동일 프로세스면 내부 함수). 별도 프로세스일 때만 서비스

/db/get_box_info     (box_id)                → (found, BoxInfo info)
                     # found=false → B는 집지 않고 state=BLOCKED 발행 후 벨트 재가동

/db/set_status       (box_id, status)        → (ok)          ★ 신규. §2.4 상태 전이표
/db/mark_placed      (box_id, PlacePose)     → (ok)
/db/zone_queue       (zone)                  → (count, placed_count)
/diverter/request    (box_id)                → (target, reason)
                     # target: "A"|"B"|"C"|"RETURN" / reason: "NORMAL"|"BUFFER_FULL"|"REJECT"
```

#### 알고리즘 — 제공: **정정인**

```
/algo/plan_placement   (zone, box_id, size_w_mm, size_d_mm, size_h_mm)
                    →  (ok, PlacePose pose, score, message)
                       # message: "OK"|"PALLET_FULL"|"NO_FEASIBLE_POSE"
                       # 응답 200ms 이내 (§7.9)

/algo/update_heightmap (zone, box_id, size_w_mm, size_d_mm, size_h_mm,
                        PlacePose actual_pose)
                    →  (ok, fill_rate, placed_count)
                       # ok=false = yaw 오차 초과 경고 (§7.6). B는 로그만 남기고 계속 진행

/algo/cancel_plan      (zone, box_id)        → (ok)   ★ 신규. 픽 실패/BLOCKED 시 계획 폐기
/algo/reset            (zone)                → (ok)
```

> `box_id`를 넣는 이유: C가 "직전 계획"을 숨은 상태로 들고 있으면 픽 실패·타임아웃 때 **영원히 stale** 해진다.
> `box_id`로 키를 잡고, 버릴 때 `cancel_plan`을 부른다.

#### 씬 — 제공: **김학민**

```
/conveyor/set_velocity (seg, velocity_mps)   → (ok, actual_mps)
   # seg: "main"|"a_pickup"|"b_pickup"|"c_pickup"|"return"
   # ★ 토픽 아님. 응답 ok를 확인한 뒤 진행할 것 — 벨트가 안 멈춘 채 흡착하면 박스가 끌려간다

/sim/swap_pallet       (zone)                → (ok)      Day 2
/sim/set_spawn_enabled (enabled)             → (ok)      Day 2
/sim/despawn_box       (box_id)              → (ok)      Day 4
```

### 2.4 ★ 상태 전이표 — 누가 언제 무엇으로 바꾸는가

**이게 없으면 `zone_queue`가 항상 0이 되고 조율 실험이 0을 측정한다.**

| status | 설정자 | 시점 |
|---|---|---|
| `SPAWNED` | D | `/sim/spawn_event` 수신 즉시 (행 생성) |
| `SCANNED` | D | `register_box` 성공 |
| `VERIFIED` | D | stage 1 = `register_box`와 동시 / stage 2 = 카메라2 통과 |
| **`DIVERTED`** | D | stage 1 = `VERIFIED`와 동시 / stage 2 = 중재자가 `target != "RETURN"` 반환 시 |
| **`PICKED`** | **B** | `grasp()`가 true 반환 직후 → `/db/set_status` |
| `PLACED` | B | `mark_placed` |
| **`PICK_FAILED`** | **B** | `grasp()` 실패, 또는 이송 중 `is_holding()==false` |
| `REJECTED` | D | `retry_count > max_retry` |

> **`zone_queue.count = status IN ('DIVERTED','PICKED')`.**
> stage 1에는 중재자가 없으므로 **D가 `register_box` 시점에 `DIVERTED`까지 한 번에 올린다.**
> 안 그러면 Day 3에도 `queue_len`이 0이고 `ZoneStatus`가 무의미해진다.

### 2.5 정상 시퀀스 (stage 1 · B구역)

```
A: 스폰 → /sim/spawn_event
D: 행 생성 status='SPAWNED' → register_box → 'SCANNED' → 'VERIFIED' → 'DIVERTED'
        ↓
A: 스토퍼 도달 → /zone_b/box_at_pickup {present:true, box_id, pose}
        ↓  (B는 콜백에서 플래그만 — §1.5)
B: /conveyor/set_velocity {b_pickup, 0.0}   → ok 확인
B: /db/get_box_info(box_id)                 → 크기      ★ 순서 아닌 ID로
B: /algo/plan_placement(zone, box_id, 크기) → PlacePose
B: pallet_place_to_world() 변환 (§3.3)
B: approach → 하강 → grasp()
      grasp 성공 → /db/set_status(box_id,'PICKED')
      grasp 실패 → set_status('PICK_FAILED') + /algo/cancel_plan → 벨트 재가동 → 종료
B: 상승 → 배치 approach → 하강 → TCP속도<5mm/s 대기 → release()
B: damping 스파이크 0.5s → 안정화 0.5s → 실제 pose 측정
B: /algo/update_heightmap(box_id, actual_pose) → fill_rate
B: /db/mark_placed(box_id, actual_pose)
B: /conveyor/set_velocity {b_pickup, 0.5}
B: /zone_b/status 갱신
```

### 2.6 예외 시퀀스

**팔레트 만석 — stage 1 (중재자·Return Line 없음):**
```
plan_placement → ok=false, "PALLET_FULL"
  → B: /algo/cancel_plan
  → B: state="PALLET_FULL" 발행
  → B: /sim/set_spawn_enabled(false)
  → B: /sim/swap_pallet(zone) → /algo/reset(zone)
  → B: /sim/set_spawn_enabled(true), state="IDLE"
```

**팔레트 만석 — stage 2:**
```
B: state="PALLET_FULL" → D 중재자가 해당 구역행을 RETURN으로 우회
  → B: swap_pallet → algo/reset → state="IDLE"
```

**재순환 한도 초과 (stage 2):** `retry_count > max_retry` → `/sim/despawn_box` + `status='REJECTED'`

**세 구역 모두 포화 (stage 2):** 중재자 → `/sim/set_spawn_enabled(false)`, 여유 생기면 `true`

**서비스 타임아웃:** B는 `state="BLOCKED"` 발행 + 벨트 재가동 + `cancel_plan` + ERROR 로그

### 3.3 ★ 팔레트 좌표계 (B ↔ C 최중요 계약)

```
원점 = 팔레트 상면의 (X최소, Y최소) 모서리
B구역 = 월드 (10300, 300, 150)

Px : 0 → 1200 mm   (월드 +X)
Py : 0 → 800 mm    (월드 +Y)
Pz : 0 → 1300 mm   (max_stack_mm)
```

**heightmap:** `hm[120][80]`, `hm[px_cell][py_cell]` = 셀 높이(mm)
> 축 규약(Px=+X, Py=+Y)은 **그대로다.** 90° 회전으로 바뀐 것은 어느 쪽이 1200 이냐뿐이다.

**`PlacePose` 의미:**
- `x_mm, y_mm` = 박스 **중심** / `z_mm` = 박스 **밑면**
- `yaw_deg=0` → `size_w`가 Px / `yaw_deg=90` → `size_d`가 Px

**★ 변환 함수는 짝으로. `packing_common/frames.py`에 넣고 B·C가 같은 걸 import.**

```python
def world_to_pallet_place(center_xyz_m, yaw_deg, h_mm, origin_mm) -> PlacePose:
    """Isaac에서 읽은 박스 pose(중심) → PlacePose(밑면)"""
    return PlacePose(
        x_mm=m_to_mm(center_xyz_m[0]) - origin_mm[0],
        y_mm=m_to_mm(center_xyz_m[1]) - origin_mm[1],
        z_mm=m_to_mm(center_xyz_m[2]) - origin_mm[2] - h_mm // 2,   # ★ 중심→밑면
        yaw_deg=yaw_deg)

def pallet_place_to_world(place, h_mm, origin_mm):
    """PlacePose(밑면) → 월드 박스 중심"""
    return (mm_to_m(place.x_mm + origin_mm[0]),
            mm_to_m(place.y_mm + origin_mm[1]),
            mm_to_m(place.z_mm + origin_mm[2] + h_mm // 2))          # ★ 밑면→중심
```

> `h_mm // 2`를 빼먹으면 **박스가 팔레트에 반쯤 파묻히거나 공중에 뜬다.**
> Day 1 저녁에 B·C가 같은 함수를 import하는지 확인.

### 7.3 배치 규칙 — heightmap-greedy

후보: 모든 (px, py, yaw), yaw ∈ {0, 90}

```
① 경계    — 팔레트 밖으로 나가지 않는가
② 높이    — base_z = 점유 영역 최대값,  base_z + size_h ≤ max_stack_mm
③ 지지율  — §7.4
④ 통로    — §7.5

score = w_height * (1 - base_z/max_stack_mm) + w_support * support_ratio
동점이면 (px, py)가 작은 쪽 (Deepest-Bottom-Left)
```

> 논문 용어: **DBLF(Deepest-Bottom-Left-Fill) + Max-Contact-Area 하이브리드.**

### 7.4 ★ 지지율 — 허용오차가 없으면 2층부터 전부 탈락한다

실측 pose(§7.6)로 갱신하면 이웃 박스 상면이 210이 아니라 211, 213이 된다.
`base_z`는 최댓값이 되고 210인 셀은 지지로 안 세진다 → `support_ratio` 붕괴 → **`NO_FEASIBLE_POSE`만 반환.**

**두 대책을 함께 적용하되, 허용오차는 반드시 `cell_mm` 이상이어야 한다:**

```python
# ① 갱신 시 셀 격자로 양자화
h_q = round(h_mm / MM_PER_CELL) * MM_PER_CELL

# ② 지지 판정 허용오차 = support_tol_mm = 10 (= MM_PER_CELL)
supported = np.abs(hm[footprint] - base_z) <= cfg.support_tol_mm
```

> ⚠️ **`support_tol_mm`을 5로 두면 안 된다.** 양자화 후 이웃 높이 차이는 **0 아니면 10 이상**이므로,
> 실제로는 2mm 차이인 두 박스가 210/220으로 갈리면 차이 10 > 5 → 탈락한다.
> 양자화 **1칸(=10mm)** 을 허용해야 두 대책이 함께 동작한다.

**C1 수용 기준:** *"박스 pose에 ±3mm 랜덤 오차를 주입한 상태에서 5층까지 정상 배치"*

```python
def corridor_clear(hm, px0, py0, w_cells, d_cells, base_z_mm, cfg):
    c = cfg.gripper_clearance_mm // MM_PER_CELL       # 30mm → 3셀
    x0, x1 = max(0, px0 - c), min(hm.shape[0], px0 + w_cells + c)
    y0, y1 = max(0, py0 - c), min(hm.shape[1], py0 + d_cells + c)
    return hm[x0:x1, y0:y1].max() <= base_z_mm + cfg.support_tol_mm
```

**마진 팽창보다 나은 이유:** 주변이 비어 있으면 손해가 **0**이다.

### 8.4 SQLite를 쓰는 이유 (발표 대비)

박스가 4초에 1개(0.25 건/s)인데 SQLite는 초당 수천 건 — **3~4 자릿수 여유.** 성능이 논점이 될 상황이 없다. 반면 PostgreSQL은 4명 환경 세팅에 반나절(6일의 8%)이 든다.

**확장성 질문 대비:** *"현재 규모에서는 SQLite로 충분하고, 실제 창고 규모로 확장할 때는 PostgreSQL로 교체합니다. DB 접근을 ROS2 서비스 노드로 추상화했기 때문에 교체 범위가 그 노드 하나로 격리됩니다."*

### 8.6 ★ 지표 — `box_events` 없이는 측정이 불가능

**함정: `boxes_sorted` 행을 `register_box`에서만 만들면 인식률이 항상 100%로 나온다.**
인식 실패한 박스는 행 자체가 없어 분모에서 빠지기 때문이다.

**→ `/sim/spawn_event` 수신 즉시 `status='SPAWNED'` 행을 만든다** (mass_g 포함).
**→ 모든 상태 전이를 `box_events`에 append.** `status` 단일 컬럼은 덮어써져 이력이 남지 않는다.

```sql
-- 인식률 = SCANNED 도달 / 전체 SPAWNED
SELECT CAST((SELECT COUNT(DISTINCT box_id) FROM box_events WHERE status='SCANNED') AS REAL)
     / (SELECT COUNT(DISTINCT box_id) FROM box_events WHERE status='SPAWNED');

-- pick&place 성공률 (B가 PICKED/PICK_FAILED를 보고해야 성립)
SELECT CAST(SUM(status='PLACED') AS REAL) / SUM(status IN ('PLACED','PICK_FAILED'))
FROM boxes_sorted;

-- 사이클 타임
SELECT AVG(placed_at - picked_at) FROM boxes_sorted WHERE status='PLACED';

-- 로봇 유휴율 = 1 − (PICKED→PLACED 시간 합 / 총 실행 시간)
```

### 8.7 인식 파이프라인 (Day 4)

stage 1에는 만들지 않는다 (`recognition.enabled: false`).

```
카메라 간격 ≥ 벨트 속도 × 최악 지연 × 안전계수 3
최악 지연 = 프레임(33ms) + 전송(5~20ms) + QR 디코딩(10~40ms) + DB(1~10ms) ≈ 150ms
0.5 m/s → 225mm 필요.  config는 800mm (600 → 1400) — 여유 3.5배
```

> ⚠️ **FPS가 10 아래로 떨어지면 이 계산이 무너진다.** → G3 합격선 25 FPS (§11).

### 8.8 ★ reject line — 프레임당 드롭은 아무것도 하지 않는다

```
카메라 높이 1m, HFOV 60° → 촬영 폭 2 × 1.0 × tan30° = 1.155 m
벨트 0.5 m/s → 체류 2.31초 → 30fps에서 69프레임
```

**프레임당 5% 드롭이면 69프레임을 전부 놓칠 확률은 0.05⁶⁹ ≈ 10⁻⁹⁰.** 즉 절대 안 터진다.

**→ 박스당 1회 판정으로 구현한다:**

```python
# 통과(pass)마다 한 번만 주사위를 굴리고, 그 박스의 나머지 프레임은 전부 무시
key = (box_id, pass_index)          # ★ 재순환할 때마다 다시 굴린다
if key not in self.decided:
    self.decided[key] = (random.random() >= cfg.recognition.cam1_box_miss_rate)
if not self.decided[key]:
    return                          # 이 통과에서는 이 박스를 인식하지 않는다
```

**`cam1_box_miss_rate: 0.10`** — 45개 중 기대 4.5개가 reject를 타므로 3분 데모에서 확실히 보인다.
`pass_index`로 키를 잡아 **재순환 때 다시 굴린다.** 안 그러면 놓친 박스가 결정론적으로 4번 다 놓쳐 항상 despawn된다.

### 8.9 ★ 중재자 (D6 — Day 5)

```python
def on_diverter_request(box_id):
    db.touch_last_seen(box_id)
    if not db.verified(box_id):
        db.increment_retry(box_id)                          # ★ bypass 아님
        if db.retry_count(box_id) > cfg.recognition.max_retry:
            call('/sim/despawn_box', box_id)
            db.set_status(box_id, 'REJECTED')
        return ("RETURN", "REJECT")

    zone = db.get_zone(box_id)
    if zone_status[zone].queue_len < cfg.zones.buffer_capacity:
        db.set_status(box_id, 'DIVERTED')                   # ★ 이게 없으면 queue_len이 0
        return (zone, "NORMAL")

    db.increment_bypass(box_id)
    if all(zone_status[z].queue_len >= cfg.zones.buffer_capacity for z in "ABC"):
        call('/sim/set_spawn_enabled', False)
    return ("RETURN", "BUFFER_FULL")
```

**함정 4개:**
1. **트리거를 분기점보다 앞에** — `trigger_x_mm: 2000` vs Sorter 3000 → **2.0초** 여유
2. **결정 타임아웃은 0.6초** — `service.timeout_s`(2.0)를 쓰면 응답이 올 때 박스는 이미 X 4000, **분기점을 지나쳐 있다.** 0.6초에 응답이 없으면 김학민 쪽에서 `(zone,"NORMAL")` 기본값 적용
3. **`DIVERTED` 설정 누락** — 하면 `queue_len`이 항상 0이라 우회가 절대 발생하지 않고 실험이 0을 측정한다
4. **`bypass_count` / `retry_count` 분리** (§8.2)

**★ 실험 설계:** `run_profile: "coordination"` (bias A 0.6) — A가 0.15 boxes/s를 받아 능력 0.1을 초과해 확실히 포화된다.
**naive는 공짜:** `arbiter.enabled: false`.

## 13. 성공 기준 — ★ 실험을 두 번 돌린다

**하나의 실행으로 두 지표를 다 뽑으려 하면 서로를 망친다.**
`zone_bias`를 편향시키면 A는 팔레트를 2번 갈아야 하고 B·C는 60%밖에 안 차서 **적재율 70%가 원천적으로 불가능**하다.

| Run | `run_profile` | 설정 | 측정 지표 |
|---|---|---|---|
| **Run 1 — 패킹** | `packing` | zone_bias 균등, 중재자 OFF, 45개 | **적재율 70%↑**, 베이스라인 대비, pick&place 성공률 |
| **Run 2 — 조율** | `coordination` | zone_bias A 0.6, 중재자 ON/OFF 2회 | 라인 정지 횟수·시간, 처리량, 로봇 유휴율 |

| 지표 | 목표 | Run | 측정 |
|---|---|---|---|
| **팔레트 적재율** | **70% 이상** | 1 | `place_*` + 크기. 분모는 **실제 최고 높이** |
| **베이스라인 대비** | 단순 순차 적재보다 높을 것 | 1 | ★ **"최적화했다"를 증명하는 유일한 물건** |
| pick & place 성공률 | % | 1 | `PLACED / (PLACED + PICK_FAILED)` |
| 처리량 | boxes/min | 2 | `PLACED` ÷ 총 시간 |
| 조율 효과 | 정지 횟수·시간 감소 | 2 | naive vs 중재자 |
| 인식률 | % | 2 | `box_events` SCANNED ÷ SPAWNED |
