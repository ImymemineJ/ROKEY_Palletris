# 관제탑 (orchestrator) — 사용법

> 박스 하나가 스토퍼에 도착해서 팔레트에 놓이기까지 **7 단계를 지휘하는 노드**.
> `/robot/cmd` 를 발행하는 **유일한 노드**다 (CLAUDE.md §8). 트랙 B.

---

## 0. 세 줄 요약

```bash
# ① Isaac 없이 ROS 그래프만 볼 때  ★ use_sim_time:=false 를 꼭 붙인다
ros2 launch packing_bringup bringup.launch.py use_sim_time:=false

# ② Isaac 을 띄워 놓고 붙일 때 (기본값이 true 라 인자 불필요)
ros2 launch packing_bringup bringup.launch.py

# ③ 상태 들여다보기
ros2 topic echo /zone_b/status
```

**관제탑만 따로 띄우는 일은 거의 없다.** `bringup.launch.py` 가 algo·db·인식과
함께 올려 준다. 혼자 띄우면 부를 서비스가 없어 아무것도 못 한다.

---

## 1. 무엇을 하는 노드인가

박스 하나마다 이 7 단계를 돈다:

```
① IDLE      벨트 가동 · 박스 도착 대기
② FETCHING  벨트 정지 + DB 에 박스 정보 조회
③ PLANNING  algo 에 "어디 놓을까" 요청
④ PICKING   로봇에게 집기 지시
⑤ PLACING   로봇에게 놓기 지시
⑥ UPDATING  algo 에 heightmap 갱신 (실측 좌표로)
⑦ DONE      팔레트 만재 → 종료
```

실제 로그 (구역 B, 박스 1 개):

```
[orchestrator.b]: [①→②] 박스 도착: BOX001 (9780, -12) yaw 10.7°
[orchestrator.b]: [②→③] 크기 340×250×210
[orchestrator.b]: [③→④] 놓을 자리 (175, 670, 0)
[orchestrator.b]: [④→⑤] 집기 성공 (1.0초)
[orchestrator.b]: [⑤→⑥] 놓기 성공 (1.0초)
[orchestrator.b]: [⑥→①] 적재 1개 · 충전율 9.5% · 최고 210mm
[orchestrator.b]: [→①] 대기
```

`[①→②]` 처럼 **단계 번호가 로그에 찍힌다.** 어디서 멈췄는지 바로 보인다.

### ★ 노드는 하나, 구역은 셋

```
[orchestrator.a]: 사이클 준비 — 상태: IDLE
[orchestrator.b]: 사이클 준비 — 상태: IDLE
[orchestrator.c]: 사이클 준비 — 상태: IDLE
[orchestrator]:   관제탑 시작 — 구역 A, B, C (3 개) · 노드는 하나다
```

구역마다 프로세스를 띄우지 **않는다.** 상태머신이라 하나여야 로봇 명령이 겹치지
않는다. 대신 노드 안에 `ZoneCycle` 이 구역 수만큼 들어 있고, 로그 앞머리
(`orchestrator.b`)로 어느 구역인지 구분한다.

> 인식 노드는 반대다 — 이미지 추론이라 GIL 때문에 **구역마다 프로세스를 나눈다.**

## 2. 띄우는 법

### 보통은 이것만

```bash
ros2 launch packing_bringup bringup.launch.py
```

algo · db · 인식(cam1/cam2) · 구역 인식 3 개 · 관제탑이 한꺼번에 뜬다.

### launch 인자

| 인자 | 기본값 | 언제 바꾸나 |
|---|---|---|
| `use_sim_time` | `true` | **Isaac 없이 돌릴 때 `false`** ← 제일 자주 쓴다 |
| `zones` | `['a','b','c']` | 1 구역만 볼 때 `"['b']"` |
| `pick_cam_ns` | `['/pick_cam_a','/pick_cam_b','/pick_cam_c']` | `zones` 와 **짝을 맞춰** 바꾼다 |
| `zone` | `b` | `zones` 가 비었을 때만 쓰는 폴백 |
| `log_level` | `info` | 자세히 보려면 `debug` |
| `algo` `db` `vision` `orchestrator` | 전부 `true` | 특정 노드만 빼고 띄울 때 `false` |

예 — 관제탑만 빼고 띄우기 (관제탑을 손으로 디버깅할 때):

```bash
ros2 launch packing_bringup bringup.launch.py orchestrator:=false
ros2 run palletris_orchestrator orchestrator_node --ros-args -p use_sim_time:=false
```

예 — 1 구역(B)만:

```bash
ros2 launch packing_bringup bringup.launch.py \
    zone:=b zones:="['b']" pick_cam_ns:="['/pick_cam']"
```

> ⚠ `zones` 와 `pick_cam_ns` 는 **개수와 순서가 짝**이어야 한다. 어긋나면 launch 가
> 시작할 때 막는다. 하나만 바꾸면 관제탑과 인식 노드가 서로 다른 토픽을 봐서
> **에러 없이 아무 일도 안 일어난다.**

## 3. ★ `use_sim_time` — 제일 많이 걸리는 함정

기본값이 `true` 다. 그런데 **`/clock` 을 발행하는 쪽(Isaac)이 없으면 모든 타이머가
멎는다.** 노드는 멀쩡히 살아 있고 에러도 안 난다.

실제로 재현해 봤다 — Isaac 없이 기본값으로 띄운 상태:

```bash
$ ros2 topic info /clock
Publisher count: 0          ← 아무도 시계를 안 준다
Subscription count: 7

$ ros2 topic echo /zone_b/status --once
(아무것도 안 나온다)
```

`use_sim_time:=false` 로 다시 띄우면:

```bash
$ ros2 topic echo /zone_b/status --once
zone: b
state: IDLE
accepting: true
...
```

### 무엇이 같이 죽나

| 죽는 것 | 결과 |
|---|---|
| `ZoneStatus` 2 Hz 발행 | 중재자가 구역 상태를 못 본다 |
| 지표 발행 | 평가 항목 "정량 분석"이 안 나온다 |
| **로봇 20 초 타임아웃 감시** | 로봇이 응답을 안 해도 **영원히 기다린다** |

세 번째가 제일 위험하다. "예외 처리(크래시 없음)" 가 통째로 무력해진다.

### 규칙

```
Isaac 을 띄웠다        → 기본값 그대로 (use_sim_time:=true)
Isaac 없이 그래프만    → use_sim_time:=false
verify_ros_graph.py   → 하네스가 /clock 을 스스로 내주므로 true 로 둬도 된다
```

```yaml

box_id: BOX001

y_mm: -12
z_mm: 1010               # ★ 박스 밑면
yaw_deg: 10.7
```

## 5. 다른 노드와 어떻게 붙나

```
        인식 노드                          관제탑                        로봇
  /zone_b/box_at_pickup  ────────────▶  ①→②
                                          │ /db/get_box_info
                                          │ /algo/plan_placement
                                          ▼
                          /zone_b/robot/cmd  ─────────────────────▶  집기
                          /zone_b/robot/event ◀─────────────────────  결과
                                          │ /algo/update_heightmap
                                          │ /db/mark_placed
                                          ▼
                          /zone_b/status ────▶ 중재자·모니터링
```

부르는 서비스 8 종:

| 서비스 | 언제 |
|---|---|
| `/conveyor/set_velocity` | ② 벨트 정지 · ⑥ 재가동 |
| `/db/get_box_info` | ② 박스 크기 조회 |
| `/algo/plan_placement` | ③ 놓을 자리 계산 |
| `/algo/update_heightmap` | ⑥ 실측 좌표로 갱신 |
| `/algo/cancel_plan` | 실패·타임아웃 시 계획 취소 |
| `/db/set_status` | 상태 기록 |
| `/db/mark_placed` | ⑥ 적재 완료 기록 |
| `/sim/despawn_box` | 폐기 박스 치우기 |

## 6. 정상적인 "이탈" 3 가지 — 에러가 아니다

| 신호 | 뜻 | 관제탑이 하는 일 |
|---|---|---|
| `NO_FEASIBLE_POSE` | **이 박스만** 자리가 없다 | 그 박스만 치우고 **계속 돈다** |
| `PALLET_FULL` | 가장 작은 박스로도 안 된다 | 지표 찍고 종료 (`DONE`) |
| 타임아웃 (20 초) | 로봇이 응답 없음 | `CancelPlan` 후 `IDLE` 복귀. **노드는 안 죽는다** |

★ **`NO_FEASIBLE_POSE` 에서 멈추면 안 된다.** 팔레트가 반만 찬 채 데모가 선다.
셋 다 `CancelPlan` 을 부른 뒤 복귀한다.

## 7. 안전장치

| 장치 | 값 | 무엇을 막나 |
|---|---|---|
| `ROBOT_TIMEOUT_S` | 20 초 | 로봇 무응답. 넘으면 계획 버리고 복귀 |
| `CALL_TIMEOUT_S` | 2 초 | 서비스 무응답 |
| `STUCK_TIMEOUT_S` | 12 초 | **IDLE 인데 스토퍼에 박스가 서 있으면 치운다** |
| `seq` 대조 | — | 늦게 온 이전 응답을 새 박스 것으로 오인하는 것 |

`seq` 는 특히 중요하다. 없으면 **에러 없이 엉뚱하게 도는** 버그가 된다 —
타임아웃 뒤 늦게 도착한 응답을 다음 박스의 결과로 처리해 버린다.

## 8. 처음부터 돌려보기

```bash
# ① 빌드
colcon build --symlink-install && source install/setup.bash

# ② 정답지(운송장번호 + 주소) 깔기

# ③ 그래프 띄우기  ★ Isaac 없으면 use_sim_time:=false
ros2 launch packing_bringup bringup.launch.py

python3 scripts/verify_ros_graph.py
```

④ 가 성공하면 이렇게 나온다:

```
  ✓ 로봇이 놓은 수 = PLACED 수 — 로봇 3 · DB 3
  ✓ DB 에 행이 다 생겼다 — 3 행
  ✓ 모든 박스가 결말을 봤다 (PLACED 또는 REJECTED) — 적재 3 · 폐기 0
  ✓ 실측 pose 가 기록됐다
전부 통과
```

> ③ 에서 `use_sim_time` 을 기본값(`true`)으로 둬도 된다 —
> `verify_ros_graph.py` 가 `/clock` 을 스스로 발행하기 때문이다.

## 9. 자주 나오는 문제

| 증상 | 원인 |
|---|---|
| **노드는 살아 있는데 아무 일도 안 난다** | `use_sim_time:=true` 인데 `/clock` 발행자가 없다. `ros2 topic info /clock` 으로 `Publisher count: 0` 확인 |
| `ZoneStatus` 가 안 나온다 | 위와 같은 원인 |
| **박스 도착 알림이 안 온다** | `zones` 와 `pick_cam_ns` 가 어긋났다. 관제탑은 `/pick_cam_b`, 인식은 `/pick_cam` 을 보고 있을 수 있다 |
| `box_at_pickup 에 box_id 가 비어 있다` | 인식이 QR 을 못 읽었다. 라벨 없이 스폰됐거나 `LABEL_FLIP_V` 문제 |
| 로봇이 안 움직인다 | 로봇 노드가 `/zone_<z>/robot/cmd` 를 구독하는지 확인. 예전엔 `/robot/cmd` 였다 |
| 로봇 응답이 엉뚱한 박스 것으로 처리된다 | 로봇이 `RobotEvent.seq` 에 `RobotCmd.seq` 를 복사해 주지 않았다 |
| **노드 이름이 중복이라는 경고** | 이전 실행이 안 죽고 남아 있다. 프로세스를 확인할 것 — `ps -eo pid,comm,args \| grep palletris_ws/install/` |
| 실제 더미가 계산보다 높다 | `has_actual == true` 일 때만 `actual_*` 를 `UpdateHeightmap` 에 넣어야 한다 |
| 첫 `NO_FEASIBLE_POSE` 에서 데모가 멈춘다 | 그건 종료 신호가 아니다. `PALLET_FULL` 만 종료다 |

### 남은 프로세스 확실히 죽이기

```bash
ps -eo pid,comm,args | grep "palletris_ws/install/" | grep -v grep
```

★ **`pkill -f palletris` 같은 건 조심.** 그 명령줄 자체가 패턴에 걸려 자기 셸이
죽는다. 그리고 ROS 노드의 프로세스 이름은 `python3` 가 아니라 실행 파일 이름
(`orchestrator_no` · `zone_detector` ...)이라, `comm` 으로 `python3` 만 찾으면
**하나도 안 죽는데 다 죽은 것처럼 보인다.**

## 10. 코드 위치

| 파일 | 무엇 |
|---|---|
| `src/palletris_orchestrator/palletris_orchestrator/orchestrator_node.py` | 관제탑 본체. `Orchestrator`(노드 1 개) + `ZoneCycle`(구역마다) |
| `src/packing_bringup/launch/bringup.launch.py` | 기동 launch |
| `scripts/verify_ros_graph.py` | Isaac 대역 + 전 구간 검증 하네스 |

### 코드를 고칠 때 지킬 것

1. **모든 서비스 호출은 `call_async` + `add_done_callback`.**
   `spin_until_future_complete` 를 콜백 안에서 부르면 executor 가 자기 자신을
   기다려 **에러 없이 조용히 멈춘다.**
2. `MultiThreadedExecutor` + `ReentrantCallbackGroup` 유지.
3. **로거를 감싸지 말 것.** rclpy 는 `once`/`throttle` 을 **호출 지점**으로
   캐싱한다. 래퍼로 감싸면 모든 로그가 한 줄로 뭉쳐
   `ValueError: Logger severity cannot be changed between calls` 로 **프로세스가
   죽는다.** 구역 구분은 `get_logger().get_child(zone)` 으로 한다.
4. 구독 콜백은 입력을 검증한다. rclpy 가 콜백 예외를 삼켜서, 잘못된 메시지 하나에
   박스가 영영 안 오는데 에러는 안 뜬다.
