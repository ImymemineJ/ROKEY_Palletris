### 왜 이 숫자인가

- **팔레트가 로봇 옆(−X)에 있다.** test1-1 에서 팔레트는 벨트 **옆**이라 로봇 스윙이
  90°다. 지선 뒤에 두면 180°가 되는데, 흡착 패드에 매달린 박스는 감쇠가 0이라
  스윙이 클수록 착지가 흔들린다 (CLAUDE.md 실측 22~76 mm).
- **팔레트는 1200 × 800 그대로**다. 지선이 +Y 라 월드에서 90° 돌아 있을 뿐이다
  (월드 X 800 · 월드 Y 1200). `test_3.yaml` 의 `pallet.width/depth` 가 그것을 담는다.
- **이격 400** (2026-08-24 팀 합의). test1-1 은 Y 로 뺐지만 여기선 X 로 뺀다.
- **페데스탈 1950** (2026-08-25 에 1250 에서 올렸다). 팔레트가 셀 컨베이어 위(950)라
  로봇 베이스보다 높다. 도달만 보면 1250 으로 충분했다(최원점 1673.3 ≤ 1700).
  ⚠ 그런데 **팔 스윙 한계**가 걸렸다. 진짜 규칙은 "기둥 윗면(월드) ≤ 페데스탈 상면"
  인데 계산식이 `페데스탈 − 150`(= test1-1 의 팔레트 상면)으로 굳어 있었다. test_3 은
  팔레트 상면이 **950** 이라 한계가 1100 으로 잘못 나와, 팔이 이송 중 기둥을 쓸어
  박스를 **1452 mm** 밀어냈다. 식을 `페데스탈 − 팔레트상면` 으로 고치니 1250 에서
  적재 한계가 **고작 300 mm** 였다. 도달 1700 안에서 최대인 값이 **1950** 이고,
  그때 적재 한계 **1000 mm** · 최원점 1673.3(2000 이면 1703.7 로 초과)이다.
  ※ 이 식 수정은 test1-1 에서 `1250 − 150 = 750` 으로 **값이 그대로**라 회귀가 없다.
- **셀 컨베이어 프레임 1000.** 페데스탈(로봇 X ± 200)을 피하려면 반폭 ≤ 500 이다.
- **합류 라인 프레임 1000 · 적재함 2800 (1톤 규격).** 코너 턴테이블에서 90° 돌리므로
  적재함을 가로지르는 치수가 팔레트의 **width 800** 이다. 800 × 3 = 2400, 피치 1000 으로
  2800 안에 들어가고 여유 400 이 남는다 (§6 코너 턴테이블).
  ⚠ 안 돌리면 1200 × 3 = 3600 이라 1톤 트럭에 **못 싣는다.**

### 4-A. 소터 분류 — 지금 방식

A47 은 분기 조각 안에 **소터**를 들고 있다. 소터는 자기 `IsaacConveyor` 를 가진
**독립 컨베이어**다:

```
<junction>/Sorter/ActionGraph/conveyor_belt   (omni.isaac.conveyor.IsaacConveyor)
    inputs:conveyorPrim -> <junction>/Sorter/Sorter_physics
    inputs:velocity     <- SorterSpeed (ConstantFloat)
    inputs:direction    =  로컬 (-1,0,0) = 월드 -X   ← 우리가 쓴다
    inputs:onStep       <- on_tick
```

`conveyor_ctl.set_sorter(zone, divert)` 가 이 노드의 `direction` 만 −X ↔ +Y 로 바꾼다.
**본선 롤러는 계속 −X 로 돈다.**

| | 옛 조각 꺾기 | 소터 |
|---|---|---|
| 옆으로 밀리는 구간 | 조각 전체 **6925 mm** | 소터 **1491.7 mm** |
| 배타 구간(상류 여유 1200 포함) | 6925 | **2692 mm** |
| 필요한 투입 간격 | 20 s | **8 s** |
| 뒤차 | 같이 밀린다 → 기다려야 한다 | 본선을 그대로 흘러온다 |

실측 (12 박스 · 로봇 3 대): **꺾기 5 회 · 지선 진입 5 회 · 타임아웃 0**.

#### ★★ A47 을 쓰려면 반드시 알아야 하는 세 가지 (전부 실측)

오전에 A47 을 세 번 붙였다가 세 번 다 라인이 막혀 A23 으로 되돌렸다. 애셋을 열어 보고
원인이 나왔다.

1. **본선 롤러에 구멍이 있다.** A47 의 `Rollers` 는 로컬 X 1651.4~2555.3 (월드 약
   1571 mm)이 **비어 있고**, 그 자리를 받치는 것이 소터다.
   → 소터를 비활성화하면 박스가 **바닥까지 떨어진다** (실측 z 0.14 m).
   → 소터가 **속도 0 으로 서 있어도 라인이 거기서 막힌다** (실측: X −6.62 에서 165 s).
2. **`SorterSpeed` 의 애셋 기본값이 0.0 이다.** "높이를 맞췄는데도 관성으로 굴러가다
   멎는다" 의 정체가 이것이었다. 소터가 안 도는 게 아니라 **0 으로 돌고 있었다.**
   → `conveyor_ctl` 이 **`main` 의 속도를 바꿀 때 소터도 같이 바꾼다**
   (`sorter_follow_seg`). 소터는 물리적으로 본선의 일부이기 때문이다.
   `run_all` 만 고쳤을 때는 데모가 seg 별로 켜서 안 불렸다 (실측: X −6.89 에서 90 s).
3. **애셋 기본 `direction` 이 로컬 (1,0,0) = 월드 +X 인데 이 라인은 −X 로 흐른다.**
   그대로 켜면 소터가 본선과 **맞서 민다** (실측: X −7.11 에서 75 s 정지, 뒤로 3 개).
   → 씬에 (−1,0,0) 으로 저장하고, `run_all` 도 `thru_world` 로 세운다.

그리고 **높이**. 애셋 그대로면 소터 롤러 윗면이 본선보다 **7.2 mm 높아** 턱이 된다.
`Sorter` 를 내려 맞추는데, 그 값은 분기 조각의 `scale.z`(1.0399)만큼 곱해져 나가므로
**재고 고치기를 반복**해서 맞춘다 (한 번에 쓰면 1.2 mm 가 남는다).

| | 실측 |
|---|---|
| 소터 구간 | A −8316~−6824 · B −14316~−12824 · C −20316~−18824 (각 **1491.7**) |
| 소터 윗면 | **800.0** (본선 롤러와 같음) |
| SorterSpeed | 0.4026 × 배율 1.7387 = **0.70 m/s** |

적용·검증: `scripts/fix_test3_sorter_a47.py` · 게이트는 `verify_test3_layout.py` 의
`=== 소터 ===` 항목.

> **왜 애셋의 `reroute` 스위치를 안 쓰나.** A47 에 분류 배선이 반쯤 들어 있다 —
> `reroute`(ConstantBool) → `to_float` → ×`Direction`(90°) → 축 (0,0,1) →
> `rotate_vector` 가 (1,0,0) 을 돌린다. 그런데 **`rotate_vector.outputs:result` 가
> 어디에도 연결돼 있지 않다.** `reroute` 를 켜도 아무 일이 안 난다. 끊긴 사슬을 잇는
> 대신 `inputs:direction` 을 직접 쓴다 — 본선에서 이미 검증된 것과 같은 경로다.
> (`reroute` 값은 애셋 상태가 어긋나 보이지 않게 같이 맞춰만 둔다.)

### 4-B. (구) 위치변환 레일 — 조각 꺾기

**QR 의 배송지**로 목적지를 정한다. `SEOUL → A · BUSAN → B · DAEJEON → C`
(`test_3.yaml` 의 `routing.by_dest`). 박스 색은 **하나로 통일**돼 있다 — 색은 더 이상
분류 근거가 아니다. 실제 QR 텍스처·디코딩은 트랙 D 몫이고, 지금은 스폰이 심은
`box_dest` 속성을 정답으로 쓴다.
> 구 방식(`by_color` · `by_type`)도 설정에 남아 있지만 `by_dest` 가 우선한다.

분기점 전용 짧은 벨트를 넣을 수 **없다** — 본선과 지선이 프레임 메시
`SM_ConveyorBelt_A23` 를 L 자 한 덩어리로 공유해서, 본선 쪽만 떼면 지선 측면 레일까지
사라진다. 대신 **본선 조각 하나에 분기점이 정확히 하나씩** 있다:

| 조각 | X 범위 | 분기 |
|---|---|---|
| `ConveyorTrack_09` | −11204~−4279 | A |
| `ConveyorTrack_08` | −17204~−10279 | B |
| `ConveyorTrack_03` | −23204~−16279 | C |

그래서 그 조각의 **표면속도 방향을 통째로 −X ↔ +Y 로 꺾는다.** 그게 위치변환 레일이다.
`conveyor_ctl.set_direction(seg, world)` 가 월드 방향을 각 조각 로컬 축으로 환산해 쓴다.

### 꺾기가 성립하려면 — 네 가지 조건 (전부 실측으로 하나씩 드러났다)

1. **그 조각에 목표 박스만 있어야 한다.** 조각 전체가 옆으로 흐르므로 뒤차도 같이 밀린다.
2. **박스가 본선 띠(Y ±500) 안에 있어야 한다.** 씬에는 순환 루프
   (`ConveyorTrack_04/05/06`, Y −6109~−4139)가 있어 분기점을 지나친 박스가 돌아온다.
   X 만 보면 루프 위 박스에게 "꺾어라" 를 내는데 그 박스는 이 조각에 없다.
   **대기 판정(1번)에도 같은 띠를 적용해야 한다** — 안 그러면 루프에 박스가 하나라도
   있는 한 영원히 안 꺾는다.
3. **`main` 이 돌고 있어야 한다.** 꺾기는 방향만 바꾼다. 계량 운전이 `main` 을 세워
   두면 방향만 바뀐 채 그대로 선다. → 꺾는 동안 계량을 잡아 둔다(`_S["diverting"]`).
4. **박스가 지선 폭 안에 완전히 들어와야 한다.** 가장 큰 5호가 480 mm 라 경계에서
   바로 꺾으면 몸통 일부가 레일 밑으로 들어가 걸린다 (양쪽 250 mm 물림).

## 6. 팔레트 반출 — 셀 → 합류 → 적재함 (2026-08-25)

`PL_PER_PALLET` 개를 놓으면 그 팔레트를 트럭으로 내보내고 시나리오를 끝낸다.
패킹 알고리즘을 아직 안 받아서 기본값은 **1** 이다 (알고리즘이 붙으면 0 = 반출 안 함).

```
셀 컨베이어 +Y  ──▶ 합류 라인 코너  ──▶ 합류 라인 +X  ──▶ 적재함
```

### 왜 벨트가 아니라 좌표로 옮기나 (실측 2026-08-25)

| 시도 | 결과 |
|---|---|
| 팔레트를 **동적** 강체로 두고 벨트로 민다 | 롤러 사이로 **22 mm 가라앉아** 배치 Z 오차가 허용(20)을 넘고, 표면속도로는 **60 s 동안 Y 5.06 그대로** — 아예 안 움직였다 |
| `sleepThreshold = 0` | 변화 없음 |
| **키네마틱 + 좌표 이송** (`move_prim`) | 됨. 지금 방식 |

### ★ 적재물도 같이 옮겨야 한다

팔레트만 옮기면 그 위 박스는 **동적 강체**라 PhysX 가 제자리에 붙들어, 팔레트가
밑에서 빠져나가고 박스는 벨트 위로 떨어진다
(사용자 관측: "팔레트에 놓았는데 박스가 안착 안 하고 움직임").

→ 반출 직전에 적재물을 **키네마틱으로 얼려**(`set_kinematic`) 팔레트와 **같은 틱에
같은 변위**로 민다(`move_prim` 이 `paths` 리스트를 받는다). 실물로 치면 스트레치 랩으로
감아 통째로 옮기는 것이다. 도착 뒤에도 풀지 않는다 — 지금은 팔레트를 받쳐 줄
적재함 바닥 말고는 아무것도 없어서 풀면 미끄러진다.

한 번에 하나씩 `move_prim` 을 부르면 **호출 사이에 틱이 끼어** 화물이 밀린다.
그래서 팔레트와 화물을 한 요청에 담는다.

### 코너 턴테이블 — 90° 회전 (2026-08-25 팀 결정)

**1톤 트럭 적재함은 2800** 이다 (작업명세서 §3.2 · CLAUDE.md). 팔레트를 안 돌리면
적재함을 가로지르는 치수가 팔레트 Y 변 **1200** 이라 3장 = **3600 > 2800** 으로
상차가 성립하지 않는다. 코너에서 돌리면 그 치수가 **800** 이 되어 3장 2400, 여유 400.

```
셀 컨베이어 +Y ──▶ [코너 턴테이블 1500x1500] ──▶ 합류 라인 +X ──▶ 적재함
                     팔레트 X800xY1200                X1200xY800
                          └─ 90° ─┘
```

| 항목 | 값 |
|---|---|
| 팔레트 자리 (적재함 안) | A 8501~9301 · B 9501~10301 · C 10501~11301 (각 800) |
| 합류 라인 중심 / 폭 | 8901 · 9901 · 10901 / **950** (팔레트 800 + 여유 150) |
| 라인 사이 | 50 mm (피치 1000) |
| 적재함 | Y 8501~11301 = **2800** · X −2400~−800 = 1600 |
| 코너판 `Corner_*` | 1500 × 1500 · 상면 797.5 (회전 대각선 1442 를 담는다) |

회전은 물리 장치가 아니라 **키네마틱**이다 (`rotate_prim`). 팔레트와 적재물이 이미
얼려져 있으므로 같은 요청에 담아 함께 돌린다. op 는 `[translate, orient, scale]` 이고
로컬 원점이 물체 중심이라 **둘 다** 손봐야 한다:

```
translate' = c + Rz * (translate - c)      자리를 원둘레로 옮기고
orient'    = orient * Rz                   자세도 같이 돌린다
```

`translate` 만 돌리면 팔레트가 자세는 그대로인 채 원을 그리며 미끄러진다.

### 도착 판정은 **뒤끝** 기준

앞머리(max) 기준으로 멈추면 팔레트가 문턱에 걸쳐 선다
(실측: 팔레트 X −3190~−2390, 적재함 −2400~−800 → **10 mm** 만 얹혀 있었다).
뒤끝(min)이 적재함 입구를 넘을 때까지 민다.

### 실측 (존 A · 3호 1 개 · `PL_PER_PALLET=1`)
```
PLACED    오차 XY 2.2 mm · Z 0.0 mm   knock 0.0 mm
[반출] 적재물 1 개 고정 (키네마틱 1)
[반출] 끝 — 팔레트 X -2.39~-1.59 · Y 8.31~9.51 · 적재함 -2.40~-0.80  완전히 실림
[반출]   BOX00001 팔레트 대비 이동 [+0.0 -0.0 +0.0] mm  안착
```

## 8. 계량 — 본선을 세우지 않는다 (2026-08-25)

예전에는 픽업 구간이 차면 **본선(`main`)을 통째로 세웠다.** 그래서 팔이 집는 동안
라인 전체가 멎었고(사용자 관측), 로봇을 3 대 돌리면 한 존이 집는 사이 나머지 두
존이 굶는다.

지금은 본선을 **안 세운다.** 대신 라우팅이 존별로 계량한다:

```
꺾기 직전에 그 존 지선(pickup_cross_mm x pickup_range_mm)의 박스를 센다
  >= PL_METER(1) 이면 **안 꺾는다** -> 그 박스는 순환 루프를 한 바퀴 돌고 다시 온다
```

실제 물류 라인의 recirculation 과 같은 동작이다.

> ⚠ 이때 **`done` 처리된 박스의 pose 도 읽어야 한다.** 지선에 올라탄 박스가 곧 그
> 존의 부하인데, 예전 코드는 `done` 을 건너뛰어서 존이 꽉 차 있어도 계속 꺾어 보냈다.

```
[계량] 본선 상시 가동 — 존 계량은 라우팅이 한다
[라우팅] 존 A 가 차 있다 (1 대) — BOX00002 는 한 바퀴 돈다
```

## 9. 로봇 3 대 동시 운전 (2026-08-25)

```bash
./scripts/run_test3.sh              # 기본이 A,B,C 세 대
PL_ZONES=A ./scripts/run_test3.sh   # 한 대만
```

존마다 **워커 스레드 · 팔 · 팔레트**가 따로다. 목표는 각 로봇이 박스 **1 개**를
자기 팔레트에 놓고(`PL_PER_PALLET=1`) 그 팔레트를 트럭까지 보내는 것이다.
여러 개를 최적 배치하는 것은 패킹 알고리즘 몫이라 여기서 안 한다.

### `cycle.py` 를 한 줄도 안 고친 방법 — `ZoneLink`

소켓 핸들러 이름(`move_ee`·`grasp`…)이 로봇마다 겹친다. 그래서

1. `setup()` 이 존마다 `SingleArticulation` · `LulaKinematicsSolver` ·
   `RobotMotion` 을 한 벌씩 만든다.
2. 서버는 요청의 `zone` 을 보고 그 존의 `RobotMotion` 으로 넘긴다.
3. 워커는 `SimLink` 를 `ZoneLink` 로 감싼다 — 모든 요청에 자기 존이 자동으로 실린다.
   이미 zone 을 넣어 보내는 명령(`pickup_check`)은 `setdefault` 라 안 덮인다.

### 존별로 갈라야 했던 것

| 대상 | 왜 |
|---|---|
| `Spawner._pickup` | 존마다 픽업 감지가 따로 있어야 한다 (`zones=` 인자 추가) |
| `targets` · `rows` · `ships` · `_CUR` | 남의 박스를 자기 몫으로 세면 안 된다 |
| 사이클 워치독 | 한 대가 멈췄다고 전체를 끝내면 안 된다 |
| 워커 종료 | **전부** 끝나야 `done`. 한 대가 먼저 끝나면 남은 로봇의 소켓이 닫혀 죽는다 |
| 팔레트 원점 | 월드 좌표를 만드는 곳만. 팔 기하 계산은 세 존이 **같다** (원점−베이스 = (−1200, −600) 고정) |

> ⚠ **투입·계량·라우팅 스레드는 라인 전체에 하나씩이다.** 워커마다 띄우면
> 스포너가 3 개가 되어 박스가 3 배로 쏟아진다. 첫 존이 대표로 띄운다.

> ⚠ 워커 예외는 **즉시** 찍는다. 마지막 워커가 `_S["result"]` 를 덮어써서 먼저
> 죽은 존의 traceback 이 통째로 사라진 적이 있다.

```

존 A 몫 5 개(SEOUL) · 존 B 몫 1 개(BUSAN) · 존 C 몫 3 개(DAEJEON)
```
