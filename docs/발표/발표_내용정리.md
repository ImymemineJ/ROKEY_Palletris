## 슬라이드 3 — 01. 프로젝트 개요 / 한 줄 요약 & 핵심 수치

### 한 줄 요약
컨베이어로 오는 박스를 로봇 팔이 집어, 3D 빈패킹 알고리즘이 계산한 자리에 쌓고, 팔레트째 트럭에 넣는다.

### 핵심 수치

| 지표 | 결과 | 비고 |
|------|------|------|
| 적재율 (Isaac 실측, 3시드) | **75.5%** | 시드별 80.3 / 73.1 / 73.2% |
| 베이스라인 대비 | **+30.6%p** | 대조군 39.7% → 최종 70.3% |
| 사이클 타임 | **8.2 ~ 10.6 s** | 목표 10.0 s 달성 |
| 종료 조건 (3시드 전부) | PALLET_FULL | 빈자리 부족 아닌 팔레트 포화 |
| 계획 재현성 | 4/4 동일 | 개수·적재율·좌표까지 완전 재현 |

★ 오늘 하루 궤적: 64.5% → 70.9% → **75.5%** (낙하 완화 도입 전후)

### 환경 요약

- 다중 PC ROS 2 통신 · ROS_DOMAIN_ID 115 통일

## 슬라이드 4 — 01. 프로젝트 개요 / 시스템 전체 구조

### 박스 1개 사이클 흐름

```
박스 스폰
  → 컨베이어 이송 (0.5 m/s · 9.5 m)
  → cam1 투입부 인식 (크기/ID 판정) → DB 등록
  → cam2 검증
  → 중재자: 목적지 판단 (A/B/C 구역, 응답 제한 0.6초)
  → 스토퍼 정지
  → pick_cam: 픽업 좌표 실측 (x·y·yaw)
  → 벨트 정지
  → 적재 알고리즘: 자리 계산 (평균 163 ms)
  → 로봇 집기 → 놓기 (wrist_cam 확인)
  → 실측 pose로 heightmap 갱신
  → 벨트 재가동 → 반복
  → PALLET_FULL → 트럭 상차
```

### 노드 구성

| 노드 | 개수 | 담당 | 역할 |
|------|------|------|------|
| 관제탑 | 3 | 트랙B | 로봇 명령 유일 발신자 · 상태머신 7단계 |
| 구역 인식 | 3 | 트랙D | 도착 감지 + 픽업 좌표 발행 |
| 라인 인식 | 2 | 트랙D | cam1 판독 · cam2 검증 |
| 중재자 | 1 | 트랙D | 목적지 배분 · 되돌림 판단 |
| 적재 알고리즘 | 1 | 트랙C | heightmap 3장 소유 · 자리 계산 |
| DB 서비스 | 1 | 트랙D | palletris.db 를 여는 유일한 프로세스 |

관제탑 상태 7단계:
`IDLE → FETCHING → PLANNING → PICKING → PLACING → UPDATING → IDLE / DONE`

## 슬라이드 7 — 04. 수행 경과 / 패킹 알고리즘

### 우리 문제 특수성 (교과서와 다른 3가지)

| | 교과서 (offline) | 우리 문제 |
|--|----------------|-----------|
| 박스 목록 | 전부 미리 안다 | **하나씩 도착** (온라인) |
| 되돌리기 | 배치 바꿔가며 최적화 | **한 번 놓으면 끝** |
| 배치 주체 | 없음 (기하만) | **6축 로봇 팔** — 못 가는 자리 있음 |

### 알고리즘 구성 5단계

**① Heightmap** — 팔레트를 10mm 격자 120×80으로 나눠 각 칸 높이를 정수로 유지. plan() 평균 2ms

**② DBLF + 가중합 점수**

| 항 | 가중치 | 역할 |
|----|--------|------|
| w_height | 0.6 | 낮은 자리 우선 (바닥부터 채움) |
| w_support | 0.4 | 밑면이 잘 받쳐지는 자리 우선 |
| w_wall | 0.2 | 가장자리 밀착 (가운데 큰 박스 자리 남김) |
| w_far | 0.1 | 로봇에서 먼 쪽부터 (팔이 놓인 박스 위 안 넘게) |
| w_level | 0.05 | 윗면이 이웃과 평평하면 가점 (절벽 억제) |

**③ Lookahead Rollout** — 상위 k개 후보를 각각 놓아보고 가상 박스를 굴려 미래 부피가 큰 쪽 선택
k=4 · rollouts=3 · depth=8 → plan() 평균 163ms (로봇 모션 8s와 비교해 여유 충분)

**④ `_corridor_ok` — 로봇 통로 검사 (핵심 차별점)**
그리퍼 몸통 Ø245mm 기준, 주변 벽이 `박스 윗면 + 그리퍼 길이(150mm)` 이하여야 배치 허용

**⑤ 낙하 완화 (2026-08-25 신규, 최대 단일 개선)**
가벼운 박스(3.5kg 이하)는 협곡 입구에서 놓고 떨어뜨림
drop_relief_mm=200 · drop_max_kg=3.5
**적재율 70.8% → 75.5% (+4.7%p)**

### 대표 알고리즘 비교

| 계열 | 우리에게 맞나 | 이유 |
|------|--------------|------|
| Wall building | X | 오프라인 전제 |
| Layer building | △ | 같은 높이 박스가 모여야 함 |
| DBLF | **대조군 채택** | 베이스라인으로 사용 |
| Heightmap + 가중합 | **채택** | 팔레타이징 실무 표준 |
| 심층강화학습 DRL | X | 6일 일정 · 재현성 요구 불가 |

## 슬라이드 9 — 04. 수행 경과 / 로봇 제어

### 협곡 문제 해결

**문제:** 다층 적재 → 박스 사이 협곡(~250mm 슬롯)
→ 그리퍼 몸통 Ø245mm라 팔이 못 내려감

**시도한 것들 (전부 적재율을 깎음)**

| 시도 | 팔 걸림 | 적재 개수 |
|------|---------|----------|
| 통로 반경 122→200mm 일괄 | 0회 | 26 → 22개 |
| 2단 통로 (250/271mm) | 1회 | 25개 |

**해결: 협곡 입구에서 놓고 떨어뜨린다**
- 대상: 3.5kg 이하 (3호 박스만) — 무거우면 낙하 충격으로 스택을 침
- 높이 기준: 박스 윗면을 `협곡 입구 − 그리퍼 길이 150mm` 까지 내림
- 결과: 480mm 낙하(이탈 22.3mm) → **120mm 낙하(이탈 1.5mm)**

### 접촉 감지 (Lula IK 한계 우회)
- Lula IK: `supports_collision_avoidance() = False`
- 해결: 툴 정지 감지 → 6틱 안에 지령을 현재 관절각으로 되돌려 힘을 뺌
- 이전 문제: 잔차 < 50mm 조건 → 55.6mm로 막히면 탈출 안 걸리고 2.5초를 밀었음

### 사이클 타임 개선: 18.3 s → 8.2 s

| 개선 항목 | 사이클 | 근거 |
|----------|--------|------|
| 초기 | 18.3 s | 베이스라인 |
| 도착 판정: 절대오차 → 수렴 정체 | 12.6 s | 정착 잔차 실측 1.03~2.05mm (임계 1mm가 최소보다 작았음) |
| 구간별 허용오차 (이송 8mm) | 11.7 s | 웨이포인트 6/8개가 이송인데 하강과 동일 정밀도 요구 |
| joint_speed_scale 0.8 → 1.0 | 10.6 s | 정격 상한 |
| 협곡 낙하 도입 후 | **8.2 s** | 픽→놓기 경로 단축 |

계측(--diag-time) 없이 엉뚱한 곳 최적화 방지 —
실제 관절 이동은 19.5s 사이클 중 4.8s뿐이었음

## 슬라이드 10 — 04. 수행 경과 / 비전·인식·DB

### 카메라 4종

| 카메라 | 위치 | 역할 |
|--------|------|------|
| cam1 | x=600 (투입부) | 크기 측정 · QR 인식 → DB 등록 |
| cam2 | x=1400 (검증) | cam1 결과 교차 검증 |
| pick_cam | 스토퍼 위 (0, 2300) 하향 | 픽업 좌표 실측 (x·y·yaw) |
| wrist_cam | 그리퍼 몸통 offset(170,0,30) · tilt 18° | 집는 순간 hand-eye 확인 |

주의사항
- QoS: BEST_EFFORT (RELIABLE로 구독하면 이미지가 하나도 안 옴)
- 오프스크린 렌더: 돔 라이트 꺼지면 카메라 캄캄 (강도 1000 필수)
- wrist_cam: 형상 파묻힘 → x 100→170mm 이동으로 해결
- 해상도 1280×720 · HFOV 60° · 30Hz

### DB 설계 (SQLite + WAL)

박스 투입 0.25건/s vs SQLite 처리 한계 수천 건/s → 3~4자릿수 여유

핵심 서비스 5개 (Day 1 합의 → 4인 완전 독립 작업 가능)

| 서비스 | 역할 |
|--------|------|
| /db/register_box | 카메라1이 박스 등록 |
| /db/verify_box | 카메라2가 검증 |
| /db/next_box | 로봇이 다음 박스 조회 |
| /db/mark_placed | 로봇이 적재 완료 기록 |
| /db/zone_queue | 중재자가 구역 대기 수 조회 |

boxes_sorted.status 로 전 생애 추적 → 데모 후 SQL 몇 줄로 발표 지표 전부 추출

## 슬라이드 12 — 04. 수행 경과 / 검증 방법론 & 교훈

### 이 프로젝트에서 배운 것

**① 데스크 계산과 시뮬 결과가 부호까지 다르다**
- 방향성 통로 실험: 데스크 예측 −0.8%p → Isaac 실측 +3개 (부호 반대)
- 원인: 데스크에서 실패는 공짜지만, 실측 실패 2건이 적재 3개를 깎음
- 결론: **데스크 스윕은 후보를 좁히는 용도, 채택 판정은 Isaac이 한다**

**② 사람 눈을 한 번은 넣는다**
- 돌아갈 때 이송 고도 버그 → 숫자만 보면 위장됨, 화면이 잡아냄
- 고친 뒤 knock 700.8mm → 0.8mm
- "계측은 '무엇이 얼마나'를 답하고, 화면은 '무엇이 빠졌는지'를 답한다"
- "빠진 것은 로그에 안 찍힌다 — 없는 동작은 없는 줄로 나타나지 않는다"

**③ 계측 없이 최적화하지 않는다**
- --diag-time 없었으면 엉뚱한 곳 최적화
- 실제 관절 이동 4.8s / 전체 19.5s — 나머지 14.7s가 숨어 있었음
