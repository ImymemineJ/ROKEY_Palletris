## 확인된 것

### 1. URDF 확보 · tool0 활성화

`h2017.urdf` + 충돌 메시 10개 + 시각 메시 10개를 jazzy 브랜치에서 받았다.

- **`tool0` 는 상류에서 주석 처리되어 있었다.** M0609 와 동일한 EE 프레임을 쓰기 위해
  주석을 풀었다. joint_6 오프셋이 두 기종 모두 `[0, -0.121, 0]` 으로 동일해서
  링크·조인트 이름이 M0609 와 완전히 같아진다 (사양서 §6-3 전제).
- **2026-08-20: tool0 의 rpy 를 `3.1416 -1.5708 0` → `0 0 0` 으로 고쳤다.**
  m0609.urdf 에서 그대로 가져온 값이었는데, 이 값은 tool0 z 를 link_6 의 +X(옆구리)로
  보낸다. 실제 플랜지는 link_6 원점에 있고 바깥 방향은 link_6 **+Z** 다:

  ```
  link_6/visuals (link_6 로컬)  Z ∈ [-0.0596, +0.0001]   반지름 45.6mm 원판, Z=0 면이 플랜지
  link_5/visuals (link_6 로컬)  Z ∈ [-0.2374, -0.0554]   팔은 전부 뒤(-Z)
  link_6 무게중심                z = -0.049               (m0609 도 -0.054, 같은 규약)
  ```

  상류가 이 tool0 를 주석 처리해 둔 이유로 보인다. 이제 `tool0 z = 흡착 접근 방향`
  이고 ROS-Industrial 의 tool0 규약(z 가 플랜지 바깥)과 일치한다 —
  `rmpflow/h2017_rmpflow_controller.py` 의 전제가 비로소 참이 된다.
  `descriptor/h2017_description.yaml` 의 tool0 충돌 구체도 이걸로 접근 방향에 놓인다
  (그리퍼가 tool0 의 **+z** 로 뻗는다는 §2 의 전제가 여기서 나온다). Isaac 씬(`usd/h2017_cell.usd`)의 `tool0` Xform 도
  Orient 를 항등으로 맞춰야 한다.
- `meshes/h2017_white/H2017_2_2.dae` 는 상류 파일 자체가 XML 선언 앞에 3바이트
  쓰레기가 붙어 있어 파서가 거부한다. 로컬에서 제거했다.

정기구학 검증 (zero pose, `tools/fk.py`):

```

수평 도달 = 0.845 + 0.734 + 0.121 = 1.700 m                        ✓ 사양서 1,700 mm
링크 질량 합 76.3 kg                                                ✓ 사양서 약 76 kg
```

### 2. 충돌 구체 — 전면 재작성

M0609 구체를 스케일해서 만들지 않았다. 상완 0.411 → 0.845 m, 전완 0.368 → 0.734 m 로
링크가 약 2배라 좌표 재사용이 성립하지 않는다 (사양서 §6-3).
`gen_collision_spheres.py` 가 충돌 메시 표면에서 직접 유도한다. 총 **22개**
(메시 링크 16 + `tool0` 그리퍼 6).

작업 중 걸린 함정 두 가지 — 다시 만질 때 같은 데 빠지지 말 것:

- **`.dae` 하나에 geometry 가 여러 개 들어 있다.** `H2017_2_1.dae` 는 상완 튜브와
  두산 로고가 따로 들어 있다. positions source 를 하나만 읽으면 상완이 통째로 빠진다.
- **정점만 쓰면 안 된다.** 상완 튜브는 긴 삼각형 몇 장이라 중간 구간에 정점이 하나도
  없다. 그대로 두면 팔 한가운데 0.36 m 가 충돌 판정에서 비어, RMPflow 가 적재된
  박스를 그냥 통과한다. 큰 삼각형은 표면을 격자로 샘플링해 채운다.

`verify_spheres.py` 결과 — 표면점 전부 구체 안, 구체 사이 끊김 0:

```
base_link ✓ 1개 · link_1 ✓ 1개 · link_2 ✓ 6개 · link_3 ✓ 1개
link_4    ✓ 5개 · link_5 ✓ 1개 · link_6 ✓ 1개 · tool0  ✓ 6개
```

#### tool0 — 실물 그리퍼 치수로 교체 (2026-08-21)

`tool0` 만 충돌 메시가 없다. 그리퍼를 URDF 가 아니라 Isaac 씬에서 붙였기 때문이다.
그래서 유도가 안 되고 **치수를 적어 구체를 계산한다** —
`gen_collision_spheres.py` 의 `GRIPPER_*` / `PAD_*` 상수와 `tool0_spheres()`.
치수는 `usd/h2017_cell.usd` 실측이다.

| | 옛 값 | 실물 | 새 값 |
|---|---|---|---|
| 구체 | 2개 (r 0.105, z 0.045 / 0.115) | — | 6개 (몸통 축 위 균등) |
| 몸통 반지름 | 0.0900 | **0.1225** | — |
| 최대 반경 | 0.1050 | **0.1225** | 0.1242 |
| `body_collision_controllers` | 0.10 | | 0.125 |

몸통 원기둥은 2026-08-21 에 `usd/h2017_cell.usd` 에서 **0.090 → 0.1225** 로 키웠다.
패드 중심이 반경 0.0971 이라 옛 몸통은 자기 패드를 지탱하지 못하는 치수였다.
이제 패드가 몸통 안에 들어와서 패드 구체가 따로 필요 없다 —
`tool0_spheres()` 가 그 판정을 직접 한다.

**옛 값은 패드를 못 덮었다.** 몸통 원기둥(r 0.09)만 보고 잡은 값인데, 패드 중심이
`(±0.08, ±0.055)` = 반경 0.0971 로 **몸통 밖**에 있었다. Ø50 패드까지 치면 0.1221 이라
22 mm 가 샜다 — 그리퍼 표면점 6,840 개 중 **1,048 개(15%)가 구체 밖**.
그대로 두면 팔이 옆에 쌓인 박스를 스치고 지나간다. 눈으로는 안 보이는 종류의 결함이다.

구체 개수(`GRIPPER_BODY_N = 6`)에는 상한이 있다. 몸통 밑면이 흡착 접촉면과 **같은 평면**
이라 박스 상판에 얹히는데, 가장 작은 3호 박스(340×250) 반폭이 y 로 **0.125** 다.
모델 반경이 이걸 넘으면 배치할 때 옆 박스와 충돌한다고 판정한다.
n 을 키울수록 반경이 조여지고(n=1 → 0.1436, n=4 → 0.1239, n=6 → 0.1231) 축방향은 늘어나는데,
여유까지 얹고 0.125 아래로 떨어지는 최소가 6 이다. 축방향으로 나오는 부분은 반경이
0.125 를 안 넘으므로 **지금 들고 있는 박스 안쪽**을 향한다 — 무해하다.

> 원형 판이라 여유가 2.5 mm 뿐이다. 실물처럼 **사각 판 210×160** 으로 바꾸면
> y 여유가 45 mm 로 벌어진다. 다음에 다듬을 후보.

검사는 `verify_spheres.py` 가 한다 — 치수에서 그리퍼 표면점을 만들어 포함 여부를 세고,
모델 반경이 실물보다 가늘면 실패시킨다. 메시가 없는 링크라 이 검사가 유일한 안전망이다.

> ⚠ **씬 쪽 확인 필요.** USD 의 몸통 원기둥은 r 0.09 인데 패드가 반경 0.0971 에 붙어 있다.
> 실물이라면 패드를 지탱할 판이 최소 반경 0.122 는 돼야 한다. 몸통을 키우든지
> 패드 간격을 좁히든지 둘 중 하나가 맞다 (현재 배치는 사양서 §4-4 의 3호 상판 조건은 만족).

### 3. joint_2 제한 — URDF 로 들어간다

`joint_2` 의 **±2.1817** 은 M0609 에 없던 제한이다 (M0609 는 ±6.28 무제한).
누락하면 IK 가 도달 불가능한 해를 낸다 (사양서 §6-3).

**이 값을 descriptor 에 적지 않는다.** Lula 는 위치·속도 한계를 URDF 의 `<limit>` 에서
읽어가고, descriptor 스키마에는 해당 키가 없다. 적어봐야 조용히 무시되면서
"제한을 넣었다"고 착각하게 된다 (Isaac 5.1 의 기본 제공 descriptor 20개를 확인했다 —
`acceleration_limits` · `jerk_limits` 외에 한계 키를 쓰는 파일이 없다).

→ **h2017.urdf 를 물리는 것 자체가 제한을 넣는 일이다.** descriptor 에는 확인용 메모만 남겼다.

속도도 M0609 보다 35~45% 낮다 — **사이클 타임에 M0609 측정값을 재사용하지 않는다**
(사양서 §7-3).

| | M0609 | H2017 |
|---|---|---|
| joint_1~3 속도 (rad/s) | 2.62 / 2.62 / 3.14 | **1.75 / 1.40 / 1.75** |
| joint_2 가동범위 | ±6.28 | **±2.18** |

### 4. 도달범위 책상 재확인 (사양서 §3-2)

사양서의 86% 는 관절 구조를 무시한 구면 근사다. `reach_check.py` 로 URDF 실제
오프셋과 관절 한계를 넣고 수치 IK 를 돌렸다. **툴 z축 수직 하강**(흡착 조건)을 걸었다.

받침대 700 mm · 베이스 (600, −300, 700) mm 기준, 파렛트 8개 꼭짓점 전부 도달:

| 지점 | 거리 | 판정 |
|---|---|---|
| 먼 쪽 상단 (1200, 800, 1450) | 1,460 mm | ✓ |
| 먼 쪽 하단 (1200, 800, 150) | 1,368 mm | ✓ |
| 가까운 쪽 상·하단 | 1,006 / 867 mm | ✓ |

그리퍼 길이 **0 / 150 / 250 mm** 모두 통과했다. joint_2 제한은 파렛트 도달을 막지 않는다.

> **이 값은 책상 계산이지 실측이 아니다.** 사양서 §8 의 Isaac Sim 실측 검증은 그대로 남아 있다.

> **2026-08-22 교차검증 — 이 표가 지금도 맞는다.** 기준 통일로 받침대(700)와 적재 상단(1450)이
> 위 계산과 같아졌다. 먼 쪽 상단 점에 **approach 200 mm + 그리퍼 150 mm** 를 얹어 tool0 로 환산하면
> `√(0.60² + 1.10² + 1.10²) = 1667 mm` 로, Isaac/Lula 실측 **1667 mm** 와 정확히 일치한다.
> 표의 1460 mm 와 다른 이유는 오차가 아니라 **재는 점이 다르기 때문**이다(approach·tool0 포함 여부).
> 여기서 확인한 것은 "관절 한계 때문에 못 닿는 지점은 없다" 까지다.
> 자기충돌 · 파렛트/박스와의 간섭 · 실제 속도는 Isaac 에서 봐야 한다.

### 5. RMPflow 설정 · 경유점 방식

**`h2017_rmpflow_common.yaml`** — M0609 판에서 실제로 고친 곳은 다음이다.

| 항목 | M0609 | H2017 | 이유 |
|---|---|---|---|
| `joint_velocity_cap_rmp.max_velocity` | 3.927 | **1.40** | 그대로 두면 joint_2(한계 1.3963)를 초과하는 지령이 나간다 |
| `canonical_resolve.max_acceleration_norm` | 20 | **12** | 자중 76 kg — M0609(27 kg)의 약 2.8배 |
| `joint_limit_buffers` | `[.02 .05 .03 .03 .03 .03]` | `[.01 .03 .02 .01 .01 .01]` | 기본 제공 설정은 전부 .01. joint_2·3 만 좁아서 더 준다 |
| `axis_target_rmp` p/d 게인 | 210 / 60 | **300 / 70** | 흡착은 상판에 수직으로 내려앉아야 한다 |
| `body_cylinders` | base 2개 (0.11 / 0.14) | **pedestal + base_column** | 아래 |

`body_cylinders` 는 메시 실측으로 다시 잡았다.

- **`base_column`** `[0,0,0] → [0,0,0.488]` r 0.14 — base_link(z 0~0.221, r 0.124) + link_1(z 0.223~0.488, r 0.128).
  link_1 은 joint_1 축 대칭이라 회전과 무관하게 원통 하나로 덮인다.
- **`pedestal`** `[0,0,-0.700] → [0,0,0]` r 0.20 — **새로 넣었다.** 받침대 700 mm 위에 로봇이 서므로
  파렛트 상면이 로봇 로컬 z = −0.55 다. 팔이 받침대 옆으로 내려가는데 M0609 설정에는 이게 없었다.
  받침대는 **원기둥 Ø400 × 700 mm 로 확정**(2026-08-20). 충돌 모델과 형상이 일치해 근사 오차가 없다.

**`h2017_palletizing_controller.py`** — 사양서 §6-3 의 "경유점 방식으로 설계한다"를 구현했다.

```
픽 위 접근 → 수직 하강 → 흡착 → 안전 고도까지 수직 상승
          → 수평 이동 → 수직 하강 → 릴리스 → 수직 상승
```

Isaac 기본 제공 `PickPlaceController` 를 쓰지 않았다. 그쪽은 안전 고도가 **고정값**
(`end_effector_initial_height`)인데, 팔레타이징은 쌓일수록 안전 고도가 올라간다.
관제탑 하이트맵의 `stack_top_z` 를 박스마다 받아 매번 다시 잡는다.

**릴리스 억제**: 흡착은 놓고 나서 못 고친다 (사양서 §2). 배치 위치 오차가 허용치(3 mm)를
넘으면 릴리스하지 않고 실패로 보고한다 → 관제탑이 재배정한다.

`test_palletizing.py` 결과 (Isaac 없이 가짜 팔로 돌린다):

```
1. 자세     ✓ yaw 7종 전부 툴 z축 (0,0,-1) · 오른손계 · yaw 일치
2. 단위     ✓ mm·deg → m·rad, 변환 지점 1곳 (AST 로 확인)
3. 경유점   ✓ 단계 9개 순서대로 · 수평 이동 최저 1,250 mm = 적재 최상단 위 150 mm
4. 릴리스   ✓ 배치 오차 3.5 mm — 경유점 판정(4 mm)은 통과하지만 릴리스는 막힘
```

작업 중 잡은 것 하나: 이 자세는 **항상 180° 회전**이라 (trace = −1 → w = 0)
일반적인 행렬→쿼터니언 변환의 w 분기가 통째로 죽는다. 실제로 yaw = −90° 가 +90° 로
뒤집혔다. 닫힌 형태 `q = (0, cos(yaw/2), sin(yaw/2), 0)` 로 바꿨다.

RG2(2지 평행)를 버리고 `isaacsim.robot.surface_gripper` 로 교체했다. 씬은 `usd/h2017_cell.usd`.

패드 위치는 `tool0` 로컬 `(±0.08, ±0.055, 0.15)`. 사양서 §2 "Ø50 × 4패드", 바깥 210×160 mm 로
3호 박스(340×250) 상판 안에 들어간다. 그리퍼 자중 2 kg 은 `/World/gripper` 가 갖고,
`link_6` 질량은 URDF 원값 0.897 그대로 둔다.

#### ★ 흡착 대상 프림에 `xformOp:scale` 을 걸지 말 것

**가장 오래 헤맨 버그다.** 대상 프림에 스케일이 걸려 있으면 흡착하는 순간 물체가
그리퍼 쪽으로 **수십 mm 순간이동**한다. 디지털 트윈으로서는 치명적이다 — 팔이 박스에
닿지도 않았는데 박스가 날아와 붙는 것처럼 보인다.

| `test_box` | 흡착 시 튀는 양 |
|---|---|
| `Cube size=1.0`, `scale=(0.34, 0.25, 0.2)` | **+42.8 mm** |
| `Cube size=0.2`, `scale=(1, 1, 1)` — 반높이 동일 | **−0.0 mm** |

높이 방향 기하(반높이 0.1 m, 윗면 world z)를 완전히 동일하게 두고 `scale` 만 뺐더니
오프셋이 사라졌다. 원인은 치수가 아니라 **스케일 자체**다.

USD 만 들여다봐서는 절대 안 잡힌다. **SurfaceGripper 는 USD 의 attachment point 조인트를
건드리지 않기 때문이다.** 잡은 뒤에도 패드의 `physics:body1` 은 여전히 팔 링크를 가리키고
`localPos1` 도 그대로다. 실제 구속은 PhysX 안에서 따로 만들어지고, 그 앵커 계산이
프림 스케일을 처리하지 못한다.

그래서 **`limit:transZ = [0, 0.005]` 가 44 mm 나 위반돼도 아무 저항이 없다.**
그 조인트는 물체를 잡고 있는 조인트가 아니다. USD 패드는 "여기에 흡착판이 있다"는 명세일 뿐이다.
`isaac:clearanceOffset` 도 범인이 아니다 — `0` 으로 놔도 똑같이 튄다.

> 직육면체가 필요하면 `UsdGeom.Cube`(한 변만 지정 가능) 대신 점을 직접 박은 `Mesh` 를 쓴다.
> 흡착이 이상하면 파라미터를 만지기 전에 **대상 프림의 scale 부터 확인할 것.**

#### 반드시 이렇게 해야 하는 것 셋

**① `mount` 는 아티큘레이션에서 빼지 않는다 (`excludeFromArticulation = False`).**
빼면 그리퍼 몸통이 최대좌표 구속으로만 매달려 팔을 **55 mm 뒤처져** 따라간다. 그 상태에서는
패드–대상 간격이 40~50 mm 로 벌어져 흡착이 절대 성립하지 않는다. `Closing` 에서 영영 안 나온다면
십중팔구 이것이다. NVIDIA 예제(`SurfaceGripper_gantry.usda`)의 `Gantry_x → Gripper_Cones`
고정 조인트도 제외하지 않는다. 고정 링크라 DOF 는 안 늘고, Lula 는 URDF 에서 기구학을 읽으므로
IK 에는 영향이 없다.

**② 패드 D6 조인트는 반드시 뺀다 (`excludeFromArticulation = True`).**
안 빼면 팔 관절로 오인돼 IK 가 망가진다. `mount` 와 반대라는 점이 헷갈리는 부분이다.

**③ 그리퍼 몸통을 `link_6` 하위에 둘 수 없다.** `link_6` 에 이미 RigidBodyAPI 가 있고 PhysX 는
강체 중첩을 허용하지 않는다. 그래서 Add > Physics 메뉴에 Rigid Body 항목이 아예 안 뜬다.
아티큘레이션 **밖**(`/World/gripper`)에 두고 `mount` 로 매단다.

NVIDIA 예제(`exts/isaacsim.robot.surface_gripper/data/SurfaceGripper_gantry.usda`)와
대조해 맞춘 값이다. 괄호 안은 예제 값.

| 프림 | 속성 | 값 |

| `pads/pad_*` | `physics:localPos0` / `localPos1` | `(±0.08, ±0.055, 0.15)` — 두 값이 같아야 한다 |

#### 흡착력 상한(사양서 §4-4, 16 kgf)은 물리로 못 건다

두 방향 다 실패했다. 기록해 둔다.

- **`coaxialForceLimit`** — 단위가 불투명하고 실제로 구속하지 않는다. `0.008` 까지 낮춰도
  16 kg 이 붙어 있고, `1000000` 으로 올려도 어떤 조건에서는 떨어진다. 재현성이 없다.
  `transZ` 하드 리미트가 하중을 대신 받아버려서 이 값에 힘이 도달하지 않는다.
- **`physics:breakForce`** — 런타임에 조인트 프림을 만들거나 수정할 때마다 재파싱 과도응답이
  걸려서, 하중과 무관하게 그 순간 끊어진다.

**결론: 컨트롤러에서 규제한다.** `rmpflow/h2017_palletizing_controller.py` 에 구현했다.

| 상수 | 값 | 근거 (사양서 §4-4) |
|---|---|---|
| `SUCTION_LIMIT_KG` | `16.0` | Ø50 × 4패드 실용 흡착력. **안전계수 3 이 이미 포함된 값**이라 |
| | | 동적 여유율을 또 곱하지 않는다. 패드가 받는 건 박스뿐이므로 |
| | | 그리퍼 자중 2 kg 도 더하지 않는다 |
| `BOX_MASS_LIMIT_KG` | `10.0` | 골판지 상판 강성. 10 < 16 이라 **먼저 걸리는 쪽은 이쪽**이다 |
| `ASSUMED_BOX_MASS_KG` | `9.0` | 배치 지시에 `mass_kg` 이 없을 때 가정. 사양서 최대 박스(5호) 중량 |

`start()` 에서 검사해 초과하면 `Phase.REJECTED` 로 **팔을 한 스텝도 움직이지 않고** 거절한다.
집었다가 떨어뜨리면 박스가 깨지고 쌓아 둔 적재물까지 무너뜨리기 때문이다.
관제탑에 올라가는 메시지 ④ 는 성공/실패/만재 셋뿐이므로 `is_failed()` 는 거절도 참으로 돌려주고,
재배정이 의미 없는 경우를 가르려면 `is_rejected()` 를 같이 본다.

> ⚠ **인터페이스 구멍 — C 담당 확인 필요.**
> 업무분배안 §5 에서 동결한 메시지 ③(배치 지시)의 필드는
> `id · 픽 위치 · 배치 좌표 · 배치 회전` 뿐이라 **중량이 없다.**
> 중량은 관제탑이 메시지 ①의 치수와 화물 밀도 150 kg/m³(§4-1)로 이미 계산해 갖고 있으므로,
> `mass_kg` 하나만 같이 실어 주면 이 검사가 실제로 작동한다.
> 그때까지는 `ASSUMED_BOX_MASS_KG = 9.0` 으로 도는데, 사양서 범위(3/5/9 kg) 안의 박스는
> 전부 통과하므로 **규제가 사실상 무효**다.

검사는 `tools/test_palletizing.py` 5번 항목이다 (3/5/9 kg 완주 · 12/25 kg 거절 시 팔 0 스텝).

`tools/fk.py` 로 계산하고 Isaac 에서 실측했다. `base_link` 는 월드 z = 0.7,

| 자세 | joint_1..6 (도) | tool0 world z | 흡착면 z |

| `HOME` | `0, -21.25, -90.00, 0, -68.77, 42.4` | 1.4450 | 1.2950 |
| `ABOVE` | `0, -32.00, -100.50, 0, -47.52, 42.4` | 1.1441 | 0.9941 |

튀면서 박스를 쳐서 날려버린다.

#### 함정

- **Play 중에 저장하지 말 것.** 그 순간의 런타임 상태(공중에 뜬 박스, 걸려 있는 흡착 조인트)가
  초기 상태로 저장된다. Play 프레임 0 에서 구속 위반으로 씬이 터진다.
  `Stop → 초기화 스크립트 → Ctrl+S` 순서를 지킨다.
- **`asyncio.ensure_future(run())` 의 반환값을 전역에 붙들어야 한다.** Script Editor 에서
  참조를 안 잡으면 태스크가 GC 돼서 **에러 한 줄 없이 중간에 사라진다.** 코루틴 안의 예외도
  조용히 삼켜지므로 `try/except + traceback.print_exc()` 로 감싼다.
- **`print()` 에 한글을 쓰면 `???` 로만 나온다.** Script Editor 콘솔은 ASCII 만 찍힌다.
- **Property 패널의 `Status` 는 갱신되지 않는다.** `Open` 으로 굳어 있어도 실제로는 잡혀 있을 수 있다.
  `isaac:grippedObjects` 나 `get_gripper_status()` 로 확인한다.
- **`close_gripper` 직후 같은 줄에서 상태를 읽으면 항상 `Closing`** 이다. 물리 스텝이 한 번도
  안 지났기 때문. Isaac 내장 테스트도 `simulate_async(1.0)` 뒤에 확인한다.
- **드라이브 타깃과 `state:angular:physics:position` 이 어긋난 채 저장하면** Play 순간 팔이
  그 차이만큼 확 움직인다. 저장 전에 둘을 같게 맞춘다.
- **붙어 있는 물체의 프림을 `RemovePrim` 하지 말 것.** 씬이 폭발한다. 먼저 `open_gripper` 하고
  물리 스텝을 한 번 보낸 뒤에 지운다.
- **`Create > Mesh > Cylinder` 는 Mesh** 라 반지름·높이 파라미터가 없다. `Create > Shape > Cylinder` 를 쓴다.
- 기하가 의심되면 추측하지 말고 `omni.physx` 의 `raycast_closest` 로 패드에서 직접 쏴본다.
  컴포넌트가 하는 일과 같다.

### 8. joint_2 토크 — 상류 URDF 값을 대체

|---|---|---|
| h2017 | 20 kg / 1700 mm | 372 372 372 163 96 50 |
| h2515 | 25 kg / 1500 mm | 372 372 372 163 96 50 |
| m1013 | 10 kg / 1300 mm | 346 346 163 50 50 50 |
| m1509 | 15 kg / 900 mm | 346 346 163 50 50 50 |
| a0912 | 9 kg / 1200 mm | 411 411 194 50 50 50 |
| h2017.sdf (gazebo) | — | 30 30 30 30 30 30 |

20 kg 기종과 25 kg 기종이 같고, 9 kg 기종이 15 kg 기종보다 높다. Gazebo SDF 는 전 축 30 이다.

**적재 0 kg 로 수평으로 뻗기만 해도 joint_2 가 한계의 99% 를 쓴다.** 사양서 §1 "가반하중 20 kg"

부족한 축은 joint_2 하나다 — j3 는 233/372, j4 는 12/163 으로 여유가 있어 건드리지 않았다.
`joint_1` 은 중력토크가 0 이지만 20 kg 를 1.7 m 에서 휘두를 때 유효관성이 약 77 kg·m² 라
372 N·m 로는 각가속 4.8 rad/s² (정격속도까지 0.36 s) 다. 지금은 충분하지만 여유가 없다.

#### 씬에도 반영해야 한다

URDF 를 고쳐도 이미 임포트된 USD 씬의 드라이브는 안 바뀐다. **Stop 상태에서**:

```python
import omni.usd
omni.usd.get_context().get_stage() \
    .GetPrimAtPath("/World/h2017_isaac_sim/joints/joint_2") \
    .GetAttribute("drive:angular:physics:maxForce").Set(1000.0)
```

#### 왜 중요한가

이 값이 낮으면 적재 시험에서 **흡착력 부족과 토크 포화가 구분되지 않는다.** 16 kg 을 걸면
joint_2 가 382.8 N·m 를 요구하는데 한계가 372 라 포화되어 팔이 처지고, 박스가 떨어진 원인이
흡착인지 관절인지 알 수 없게 된다. §7 의 흡착력 보정을 하기 전에 반드시 고쳐야 한다.
