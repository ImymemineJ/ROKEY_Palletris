## 방향 전환 — 왜 강의 방식으로 돌아갔나

> **[영상 3 — `test1.mp4`]**
> 강의 방식으로 갈아탄 첫 완주. 박스를 집어 옮기는 데는 성공했지만
> 배치 오차가 82.6 mm 였고 시작할 때 팔이 튄다.

처음에는 `PalletizingController` 라는 **경유점 상태기계를 직접 만들었다.**
이유는 하나였다 — "내장 `PickPlaceController` 는 안전 고도가
`end_effector_initial_height` **고정값**이라, 적재가 쌓이면 못 따라간다."

**그 전제가 틀렸다.** 내장 컨트롤러의 `reset()` 이 안전 고도를 받는다.

```python
ctrl.reset(end_effector_initial_height=stack_top + clearance)
```

박스마다 이걸 부르면 적재 높이를 그대로 따라간다. 소스를 안 읽고 단정한 것이
자체 구현을 만든 이유였고, 그 구현이 아래 ①②를 그대로 불러왔다.

**교훈: 같은 6축이면 M0609 판을 먼저 읽고 수치만 바꾼다.**
게인(`rmp_params`)은 실제로 M0609 에서 가져왔는데 **컨트롤러 구조를 안 봤다.**
바꾼 곳은 세 군데뿐이다.

| | M0609 | H2017 |
|---|---|---|
| 그리퍼 | `ParallelGripper` | `SurfaceGripper` |
| EE 프레임 | `link_6` | `tool0` |
| `events_dt` | `[0.008, 0.005, 1.0, 0.1, 0.05, 0.05, 0.0025, 1.0, 0.008, 0.08]` | `[0.004, 0.0025, 0.02, 0.05, 0.0025, 0.002, 0.0025, 0.02, 0.002, 0.01]` |

링크가 약 2배이고 `joint_1~3` 속도가 35~45% 낮으므로(사양서 §7-3) 전 구간을 늘렸다.

## 문제 ① 경유점을 영영 못 넘어간다

> **[영상 1 — `error1.mp4`]**
> 팔이 픽 지점 위에서 멈춘 채 30초를 태우고, 그 사이 박스를 106 mm 밀어낸다.
> 로그 끝줄은 `RESULT: FAILED — PICK_APPROACH 단계에서 1800 스텝 안에 경유점에 못 갔다`.

### 현상

자체 상태기계가 첫 단계에서 타임아웃했다. 남은 오차 **19.4 mm**.

### 원인 — RMPflow 는 정상상태 오차가 남는다

단계 전환을 **위치 오차 4 mm** 로 걸었는데, RMPflow 는 적분항이 없는 반응형
정책이라 **정상상태 오차가 원래 남는다.** 실측으로 하나씩 지웠다.

| 후보 | 판정 | 근거 |
|---|---|---|
| 드라이브 게인이 약하다 | ✗ | 지령↔실제 관절 차이 **0.04°** — 관절은 지령을 따라간다 |
| `default_q` 가 당긴다 (`cspace_target_rmp`) | ✗ | `set_cspace_target` 로 껐는데 15.3 → 15.3 mm, **변화 0** |
| 충돌 RMP 반발 | ✗ | 최근접 링크가 570 mm, 반발 구간(500 mm) 밖 |
| 관절 한계 반발 | ✗ | 전부 한참 멀다 |
| Lula 모델이 실제와 다르다 | ✗ | RMPflow 자신의 FK vs USD 실제 = **0.00 mm** |

남은 결론은 하나다. **RMPflow 가 14.9 mm 를 알면서 버틴다.**

```
model vs real        0.00 mm   <- Lula 모델 = 실제, 완전 일치
err seen by RMPflow 14.88 mm   <- RMPflow 도 알고 있다
command falls short 14.30 mm   <- 지령 자체가 낮다
```

즉 **4 mm 판정은 영원히 통과 못 한다.**

### 조치

내장 컨트롤러로 교체했다. 이쪽은 **위치 오차를 아예 안 본다.**

```python
self._t += self._events_dt[self._event]
if self._t >= 1.0:
    self._event += 1        # 시간으로 넘어간다
```

강의 방식이 시간 기반인 이유가 이것이다.

## 문제 ② 팔이 목표에서 1.9 m 벗어난다

> **[영상 2 — `error2.mp4`]**
> 자세를 지령하자 팔이 목표를 버리고 통째로 다른 데로 날아간다.

### 현상

시작 자세의 손목이 **yaw +137.5°** 인데 `down_quat(0)`(yaw 0)을 지령했더니:

```
step   err_mm  ori_deg   gap_mm   j6_deg
   0     15.3     1.85    385.2    42.48
  60   1405.9    65.73   -552.9   206.10
 120   1861.8   111.15   -928.1   206.26   <- 흡착면이 바닥 밑까지
```

툴이 목표에서 **1,864 mm** 벗어나고, 흡착면이 박스 상판보다 **928 mm 아래**
(즉 바닥 밑)까지 내려갔다. `joint_6` 는 42° → 288° → −170° 로 헤맸다.

### 원인 — 자세 계단 입력

RMPflow 는 반응형이라 **큰 계단 입력을 주면 최대 가속으로 끌려간다.**
그리고 자세 오차를 자세로 못 풀면 **위치를 희생해서 푼다.** 그게 저 궤적이다.

### 조치 두 가지

**(1) 요 180° 대칭을 쓴다.** 흡착 패드가 사각 배치(210×160)라 `yaw` 와 `yaw+180`
은 흡착에 완전히 동등하고, 직육면체 박스도 180° 돌리면 같은 자리를 차지하므로
적재에도 동등하다. 가까운 쪽을 고르면 **회전량이 항상 90° 이하**가 된다.

> 참고로 내장 컨트롤러의 기본 자세 `euler_angles_to_quat([0, π, 0])` 가 마침
> **yaw 180** 이다. 처음부터 강의 값을 썼으면 이 문제 자체가 없었다.

**(2) 워밍업 램프.** 내장 컨트롤러의 `_mix_sin` 보간은 **event 1·4·6·8 에만**
걸리고 **event 0 은 목표를 그대로 던진다.** 그래서 실행하는 순간 높이 250 mm +
자세 42.5° 계단이 들어간다. 현재 포즈에서 event 0 목표까지 같은 사인 곡선으로
3초에 걸쳐 직접 이어 붙였다.

효과:

| | 램프 전 | 램프 후 |
|---|---|---|
| 최대 이탈 | 1,864 mm | **218 mm** |
| 최저 간극 | −928 mm | **+286 mm** |
| 배치 오차 | 82.6 mm | **13.0 mm** |

## 문제 ④ 박스를 놓은 뒤 손목이 뒤집힌다

> **[영상 4 — `test2.mp4`]**
> 박스는 제자리에 잘 놓는데, 물러나는 구간에서 **손목이 접혀 그리퍼가 옆으로 눕는다.**
>
> **[영상 5 — `test3.mp4`]**
> 같은 붕괴. 이 실행에 관절·툴축 계측을 붙여 원인을 잡았다.

### 현상

배치까지는 완벽한데(오차 13.7 mm, 박스 상판 높이 정확) **물러나는 event 8** 에서
자세가 무너진다. 흡착면이 박스 상판보다 100 mm 아래로 내려간다(`minGap −100.7 mm`).

### 원인 — 손목 특이점

관절을 찍어보니 명확했다.

```
t e8  +40   tilt  6.42   j5 -15.2   j4  +7.9
t e8  +60   tilt 24.60   j5 +10.8   j4 +15.4   <- joint_5 가 0 을 통과
t e8 +100   tilt 88.12   j5 +91.3   j4 +60.8   <- 툴이 거의 수평
t e8 +120   tilt 91.50   j5 +93.1   j4 +84.0   <- 최악
```

`joint_5 = 0` 이면 `joint_4` 와 `joint_6` 축이 겹쳐 **손목이 1자유도를 잃는다.**
야코비안이 특이해지면서 RMPflow 가 손목을 통째로 뒤집는다.

세 가지가 겹쳤다.

**(1) 배치 자세가 특이점에 가까웠다.** 배치 높이별 `joint_5`:

| 배치 접촉면 z | `joint_5` | |
|---|---|---|
| 0.20 (맨바닥) | **−22°** | 특이점에서 22° 뿐 |
| 0.35 (파렛트 1층) | **−24°** | 여전히 위험 |
| 0.89 (컨베이어와 같은 높이) | **−47°** | 안전 |

**(2) 바닥에 찍는 충격이 방아쇠였다.** 배치 하강 끝에서 박스가 바닥에 닿는 순간
`tool0` 가 32 mm 튀고 기울기가 1.4° → 5.4° 로 올라간다. 그 킥 한 번에 넘어간다.

**(3) `default_q` 가 넘는 방향을 정해줬다.** 강의 값의 `joint_5` 는 **+90** 인데
이 셀에서 팔이 실제로 일하는 j5 는 픽 −48.9, 배치 −22~−56 으로 **전부 음수**다.
즉 `cspace_target_rmp` 가 j5 를 **0 을 통과해서** +90 쪽으로 당기고 있었다.
평소엔 태스크 항에 눌려 안 보이다가(그래서 앞선 측정에서 기여 0 으로 나왔다)
특이점 근처에서 주도권을 잡는다.

### 조치

| | 전 | 후 |
|---|---|---|
| 테스트 조건 | 컨베이어(0.89) → **맨바닥(0.20)**, 690 mm 낙하 | 컨베이어(0.89) → **파렛트(0.89)**, 같은 높이 수평 이송 |
| `default_q` j5 | +90 (특이점 **통과** 방향) | **−90** (멀어지는 방향) |
| 배치 목표 | 안착 높이 정확히 | **+10 mm** (받침에 안 찍는다) |

**테스트 조건 변경이 제일 컸다.** 실제 작업은 컨베이어에서 파렛트로 거의 같은
높이를 옮기는 것이라, 맨바닥으로 떨어뜨리던 옛 조건은 현실과도 안 맞았고
불필요하게 어려운 자세를 만들고 있었다. 현실성과 안정성이 같이 해결됐다.

## 문제 ⑤ 흡착에 성공했는데 실패로 보고된다

### 현상

`gripper didn't close successfully` 경고가 20줄씩 쏟아지고 상태가 계속 `open`
으로 찍히는데, **박스는 멀쩡히 붙어서 0.58 m 를 따라온다.**

### 원인

`get_gripper_status()` 는 **문자열이 아니라 enum** 을 돌려준다
(`str()` 하면 `"GripperStatus.Open"`). 문자열과 비교하면 **영원히 거짓**이다.
게다가 상태는 `Open → Closing → Closed` 로 몇 스텝에 걸쳐 바뀌는데
스톡 `close()` 가 호출 직후 바로 확인해서 경고를 찍는다.

### 조치

스톡 `isaacsim.robot.manipulators.grippers.SurfaceGripper` 래퍼를 쓴다.
이쪽은 `== surface_gripper.GripperStatus.Closed` 로 제대로 비교한다.
로그에도 `Open/Closing/Closed` 세 상태를 그대로 찍는다 — 두 상태로 뭉개면
판단이 안 된다.

## 문제 ⑥ 파일을 고쳤는데 옛 코드가 돈다

### 현상

컨트롤러 파일을 고치고 다시 실행했는데 **옛 값으로 6번을 돌았다.**
`PP.__file__` 은 올바른 경로를 가리키는데 내용이 옛것이다.

### 원인

`__pycache__` 의 `.pyc` 가 **소스 검증 없이 재사용**된다
(PEP 552 hash-based pyc). `importlib.reload()` 도, `sys.modules.pop()` 도 부족하다.

### 조치 — 세 겹으로 막는다

```python

importlib.invalidate_caches()
```

## 재발 방지 체크리스트

- [ ] **위치 오차로 단계를 전환하지 않는다.** RMPflow 잔류는 15 mm 다. 시간으로 넘긴다
- [ ] **RMPflow 에 계단 입력을 주지 않는다.** 목표는 `_mix_sin` 으로 옮긴다.
      내장 컨트롤러도 **event 0 은 보간을 안 하므로** 시작 램프를 직접 붙인다
- [ ] **EE 프레임과 실제 접촉면의 차이를 `end_effector_offset` 으로 넣는다**
- [ ] **`default_q` 의 관절 부호를 실제 작업 구간과 맞춘다.**
      특히 `joint_5` — 반대 부호면 특이점을 통과하는 방향으로 당긴다
- [ ] **`joint_5` 가 ±15° 안에 들어오는 자세를 피한다.** 손목 특이점이다
- [ ] **그리퍼 상태는 enum 이다.** `Open/Closing/Closed` 세 상태를 그대로 본다
- [ ] **모듈을 고쳤으면 pyc 를 지우고 디스크와 대조한다**
- [ ] **같은 6축이면 M0609 판을 먼저 읽는다.** 구조까지 베끼고 수치만 바꾼다
