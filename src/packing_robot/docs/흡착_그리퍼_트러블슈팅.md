> ⚠ 구 저장소(`cobot3_ws`)에서 옮겨온 기록이다. **좌표·치수는 옛 셀 기준**이고
> Palletris 에서는 다르다 (`../README.md` 맨 위 대조표).

> SurfaceGripper 삽질 기록. **B3 를 시작하기 전에 읽을 것** — 여기 적힌 함정 하나에 반나절씩 갔다.

# 문제 ① 팔이 링잉해서 박스를 쳐서 날린다

> **[GIF 3 — `로봇 팔 움직임 속도 조정.gif`]**
> 팔이 목표 자세로 훅 움직이면서 진동하고, 박스가 밀려 기울어진다.

## 현상

팔을 목표 자세로 보내면 도착할 때 **진동(ringing)** 이 남고, 그 흔들림이
박스를 쳐서 날려버렸다. 흡착 위치를 아무리 정밀하게 맞춰도 소용이 없었다.

## 원인 — 네 가지가 겹쳐 있었다

### 1) 드라이브 타깃을 스텝 입력으로 줬다

GIF 에 보이는 코드가 그것이다:

```python
Q = {1:0.0, 2:-37.0, 3:-102.0, 4:0.0, 5:-41.02, 6:42.4}
for i, d in Q.items():
    stage.GetPrimAtPath("/World/h2017_isaac_sim/joints/joint_%d" % i) \
         .GetAttribute("drive:angular:physics:targetPosition").Set(d)
```

목표값을 **한 번에** 써넣으면 드라이브가 최대 토크로 팔을 잡아채고, 도착하면서 오버슈트한다.

### 2) 드라이브가 부족감쇠였다

`damping = stiffness / 2500` 로 되어 있었다. 임계감쇠는 이렇게 계산한다:

```
d_crit = 2 * sqrt(k_deg * I / 57.2958)      # USD 각드라이브는 도(degree) 단위
```

### 3) 물리 타임스텝이 60 Hz 였다

`physicsScene` 의 `physxScene:timeStepsPerSecond = 60`. 지터가 남는다.

### 4) `joint_2` 토크가 부족했다

상류 URDF 의 `effort = 372 N·m` 인데, 자세별 중력 토크를 계산해보니 **679.6 N·m** 가 필요했다.
드라이브가 못 버티고 처지면서 흔들렸다.

### 5) Play 순간의 lurch

`state:angular:physics:position` 이 authored 되어 있지 않으면, Play 하는 순간
zero pose 에서 드라이브 타깃까지 팔이 확 움직인다.

## 해결

| 항목 | 조치 |
|---|---|
| 이동 | 드라이브 타깃을 **선형 보간** (240~300 스텝). 교육자료 방식(`TCP_SPEED 0.004 m/step`)과 동일 |
| 감쇠 | 임계감쇠 근처로 재계산 → damping `[31, 80, 44, 1.8, 0.65, 0.05]` |
| 강성 | stiffness `[533, 1665, 1750, 70, 26, 2]` |
| 타임스텝 | `timeStepsPerSecond` 60 → **240** |
| 토크 | URDF `joint_2` effort `372` → **1000**, 씬의 `maxForce` 도 함께 |
| 초기 자세 | 저장 시 `drive:targetPosition == state:position` 을 맞춰서 Play 해도 안 튀게 |

## 결과

최종 `PICK` 하강 중 박스 좌표 변화 **0.0 mm** — `(-0.9893, 0.0097, 0.7923)` 그대로.
팔이 박스를 스치지 않는다.

# 문제 ② 흡착력 상한 16 kgf 를 물리로 못 건다

사양서 §4-4 의 "흡착력 16 kgf 가 병목" 을 시뮬레이션에서 재현하려 했다.
**두 갈래로 시도했고 둘 다 실패했다.** 실패 기록으로 남긴다.

## 시도 A — `coaxialForceLimit` / `shearForceLimit`

> **[GIF 4 — `흡착 그리퍼 적정수치 찾음.gif`]**
> 16 kg 이 잘 붙어 있다. **잘 된 것처럼 보이지만 아니다.**

### 잘 되는 것처럼 보였던 이유

`coaxialForceLimit` 을 **0.008 까지 낮춰도** 16 kg 이 그대로 붙어 있었다.
"흡착력이 충분하다" 가 아니라 **그 값에 힘이 도달하지 않고 있었다.**

원인은 `limit:transZ` 하드 리미트였다. 이 리미트가 하중을 대신 받아버려서
`coaxialForceLimit` 은 아무 힘도 보지 못한다. 즉 **측정 자체가 성립하지 않는 상태**였다.

### 리미트를 풀었더니 다른 것이 병목이었다

`limit:transZ:high` 를 0.10 으로 키우고 강성을 올려서 COAX 에 힘이 가게 만들었더니,
이번엔 **`shearForceLimit = 5.0` 이 진짜 병목**이었다.

당시 자세가 연직에서 **3.39°** 기울어 있었고, 16 kg(156.96 N)의 전단 성분은

```
156.96 N x sin(3.39 deg) = 9.28 N   >  shearForceLimit 5.0 N
```

축력이 아니라 **기울기 때문에** 떨어지고 있었던 것이다.
`tools/fk.py` 로 연직도 **0.025°** 인 자세를 찾아 쓰니 전단 성분이 **0.068 N** 로 떨어졌다.

### 그래도 못 쓴다

기울기를 잡은 뒤에도 `coaxialForceLimit = 1000000` 에서 떨어지는 경우가 나왔다.
**단위가 불투명하고 재현성이 없다.** 참고로 NVIDIA 예제는 **0.2 kg** 박스를 `0.005` 로 잡는다 —
뉴턴이 아니다.

## 시도 B — 수동 `FixedJoint` + `physics:breakForce`

> **[GIF 2 — `흡착 그리퍼 치수 찾는중 시행착오.gif`]**
> 콘솔이 에러로 도배되고 박스가 사라진다.

SurfaceGripper 를 우회해서, 패드에서 `raycast_closest` 로 대상을 찾아
`UsdPhysics.FixedJoint` 를 직접 만들고 `breakForce = 156.96 N`(= 16 kg × 9.81)을 걸어봤다.

### 에러 1 — `found a joint with disjointed body transforms`

```
[Warning] [omni.physx.plugin] PhysicsUSD: CreateJoint - found a joint with
disjointed body transforms, the simulation will most likely snap objects
together: /World/gripper/suction
```

조인트 양쪽 프레임이 같은 월드 포즈를 가리키지 않는다는 뜻이다. 원인:

```python
Mb = xc.GetLocalToWorldTransform(stage.GetPrimAtPath(tgt))   # scale 이 섞인 행렬
qr = (Mb * M6.GetInverse()).ExtractRotationQuat()            # -> 잘못된 회전
```

`test_box` 에 `scale = (0.34, 0.25, 0.2)` 가 걸려 있어서, 스케일이 섞인 행렬에서
회전을 뽑으면 틀어진다. 그 상태로 조인트를 만들면 PhysX 가 두 프레임을 억지로 맞추며
**스냅**이 발생하고, 유한한 `breakForce` 는 그 전이응답에 즉시 끊긴다.

**고친 방법** — 두 행렬 모두 스케일을 제거하고 나서 뽑는다.

```python
Mb = xc.GetLocalToWorldTransform(stage.GetPrimAtPath(tgt)).RemoveScaleShear()
M6 = xc.GetLocalToWorldTransform(stage.GetPrimAtPath(LINK6)).RemoveScaleShear()
```

> **여기서 이미 스케일이 범인이라는 신호가 나왔다.** 다만 이때는 "내 코드의 버그" 로만 보고
> 넘어갔다. SurfaceGripper 내부에도 같은 문제가 있으리라고는 생각하지 못했다. — 문제 ③ 으로 이어진다.

### 에러 2 — `RuntimeError: Accessed invalid null prim`

조인트가 붙어 있는 상태에서 `/World/test_box` 를 `RemovePrim` 했다가 씬이 폭발했다.
"실행하면 테스트박스가 사라진다" 는 증상이 이것이다.

**규칙: 붙어 있는 물체의 프림을 지우지 말 것.** 먼저 `open_gripper` 로 떼고
물리 스텝을 한 번 보낸 뒤에 지운다.

### 그래도 못 쓴다

`RemoveScaleShear()` 로 스냅을 없앤 뒤에도 `breakForce` 는 쓸 수 없었다.
**런타임에 조인트 프림을 만들거나 수정할 때마다 재파싱 전이응답이 걸려서**,
하중과 무관하게 그 순간 끊어진다.

| `breakForce` | 5 kg | 16 kg | 25 kg |
|---|---|---|---|
| `inf` | 유지 | 유지 | 유지 |
| 유한값 | 즉시 끊김 | 즉시 끊김 | 즉시 끊김 |

무게에 대한 단조성이 전혀 없다. 힘 상한을 모델링할 수 없다는 뜻이다.

## 결론 — 컨트롤러에서 규제한다

씬에서는 `coaxialForceLimit` / `shearForceLimit` 을 **`1e6`(사실상 무제한)** 으로 두고,
`physics:breakForce` 는 **`inf`** 로 둔다. 흡착력 상한은 **제어 코드에서** 지킨다.

```python
# rmpflow/h2017_palletizing_controller.py
SUCTION_LIMIT_KG    = 16.0   # Ø50 x 4패드 실용 흡착력 (안전계수 3 포함)
BOX_MASS_LIMIT_KG   = 10.0   # 골판지 상판 강성 — 10 < 16 이라 이쪽이 먼저 걸린다
ASSUMED_BOX_MASS_KG =  9.0   # 지시에 mass_kg 이 없을 때. 사양서 최대 박스(5호)

def payload_reason(mass_kg):
    """집으면 안 되는 이유. 집어도 되면 None."""
    if mass_kg > SUCTION_LIMIT_KG:  return "흡착력 상한 초과 — 붙여도 유지되지 않는다"
    if mass_kg > BOX_MASS_LIMIT_KG: return "운용 상한 초과 — 상판이 뜯어진다"
    return None
```

`start()` 에서 검사해 초과하면 **팔을 한 스텝도 움직이지 않고** `Phase.REJECTED` 로 거절한다.
집었다가 떨어뜨리면 박스가 깨지고 쌓아 둔 적재물까지 무너뜨리기 때문에, 시도 자체를 막는 게 맞다.

**16 kgf 에 안전계수 3 이 이미 들어 있다** (사양서 §4-4 는 진공 −60 kPa · 안전계수 3 ·
골판지 통기성을 반영한 값이라고 명시한다). 그래서 동적 여유율을 또 곱하지 않았다 — 이중 계상이다.
흡착 패드가 받는 하중은 박스뿐이므로 그리퍼 자중 2 kg 도 더하지 않는다.

> ⚠ **남은 구멍.** 업무분배안 §5 에서 동결한 배치 지시에는 **중량 필드가 없다.**
> 관제탑(C)이 `mass_kg` 을 실어 주기 전까지는 가정치 9 kg 으로 돌기 때문에
> 사양서 범위(3/5/9 kg) 박스는 전부 통과 —— **규제가 사실상 무효**다.

검사: `tools/test_palletizing.py` 5번 (3/5/9 kg 완주 · 12/25 kg 거절 시 팔 0 스텝 · 흡착 0회).

# 문제 ③ 박스가 42 mm 떨어진 채 붙는다

> **[GIF 1 — `흡착 그리퍼 에러2.gif`]**
> 박스가 패드에 닿지 않은 채 떨어져서 매달려 올라간다. 로그 끝줄은 `RESULT: NOT HELD`.

## 현상

흡착을 걸면 박스가 그리퍼 패드에 **닿지 않고 약 42 mm 떨어진 채로** 붙었다.
잡히기는 잡히는데 공중에 붕 뜬 상태라, 붙은 건지 아닌지 눈으로 구분이 안 됐다.

디지털 트윈으로서는 치명적이다. 팔이 박스에 닿지도 않았는데 박스가 날아와 붙는 것처럼 보인다.

## 원인이 아니었던 것들

간극이니까 "흡착 거리" 문제라고 생각하고 아래를 전부 돌려봤다. **전부 헛짚었다.**

| 파라미터 | 시도한 범위 | 결과 |
|---|---|---|
| `isaac:maxGripDistance` | 0.05 → 0.02 → 0.01 | 간극 그대로 |
| `isaac:clearanceOffset` | 0.045 → 0.008 → **0.0** | 간극 그대로 |
| `limit:transZ:high` | 0.10 → 0.005 | 간극 그대로 |
| `drive:transZ` 강성 | 2000 → 20000 | 간극 그대로 |

특히 `clearanceOffset` 은 저장된 씬에 `0.045` 가 들어 있어서 "이게 범인이다" 싶었는데,
**0 으로 놔도 똑같이 튀었다.** 이 값은 사람이 넣은 게 아니라 그리퍼가 잡을 때 스스로
측정해서 USD 에 되써 넣은 값이었다.

**"팔이 멀리서 잡아서" 도 아니었다.** 팔을 박스 윗면 **0.3 mm** 까지 내려보냈는데도
똑같이 42.8 mm 튀어올랐다. 접근 거리와 무관한 고정 오프셋이다.

## 진짜 원인 — 대상 프림에 걸린 `xformOp:scale`

`test_box` 를 `UsdGeom.Cube`(`size = 1.0`)에 `scale = (0.34, 0.25, 0.2)` 를 곱해서
340×250×200 mm 로 만들어 놓은 것이 원인이었다.

**SurfaceGripper 의 런타임 구속 앵커 계산이 프림 스케일을 처리하지 못한다.**
문제 ② 시도 B 에서 내 수동 조인트가 겪었던 것과 **정확히 같은 종류의 버그**다.

### 단일 변수 실험

높이 방향 기하(반높이 0.1 m, 윗면 월드 z)를 **완전히 동일하게** 두고 `scale` 만 제거했다.

| `test_box` | 흡착 시 튀는 양 |
|---|---|
| `Cube size=1.0`, `scale=(0.34, 0.25, 0.2)` | **+42.8 mm** |
| `Cube size=0.2`, `scale=(1, 1, 1)` | **−0.0 mm** |

바꾼 것은 `scale` 하나뿐이다. 원인은 치수가 아니라 **스케일 그 자체**다.

### 왜 USD 를 아무리 뒤져도 안 보였나

**SurfaceGripper 는 USD 의 attachment point 조인트를 건드리지 않는다.**
박스를 잡고 있는 상태에서 패드 프림을 덤프해보면:

```
pad_0..3   body0     = /World/gripper
           body1     = /World/h2017_isaac_sim/link_6   <- 잡은 뒤에도 여전히 팔 링크
           localPos1 = (±0.08, ±0.055, 0.15)           <- 그대로
           limit:transZ = [0, 0.005]
```

`body1` 이 박스로 바뀌지 않는다. 실제 구속은 PhysX 내부에서 **따로** 만들어지고,
USD 패드는 "여기에 흡착판이 있다" 는 **명세**일 뿐이다.

그래서 `limit:transZ = [0, 0.005]` 가 **44 mm 나 위반되고도 아무 저항이 없다.**
그 조인트는 박스를 잡고 있는 조인트가 아니기 때문이다.
→ USD 쪽 리미트·드라이브를 아무리 조여도 간극이 안 줄어들었던 이유.

## 해결

### 1) 대상 프림에서 스케일 제거

직육면체가 필요하므로 `UsdGeom.Cube`(한 변만 지정 가능) 대신
**점을 직접 박은 `UsdGeom.Mesh`** 로 만들었다.

```python
HX, HY, HZ = 0.17, 0.125, 0.10          # 340 x 250 x 200 mm
m = UsdGeom.Mesh.Define(stage, "/World/test_box")
pts = [(-HX,-HY,-HZ), (HX,-HY,-HZ), (HX,HY,-HZ), (-HX,HY,-HZ),
       (-HX,-HY, HZ), (HX,-HY, HZ), (HX,HY, HZ), (-HX,HY, HZ)]
m.CreatePointsAttr([Gf.Vec3f(*p) for p in pts])
m.CreateFaceVertexCountsAttr([4] * 6)
m.CreateFaceVertexIndicesAttr([0,3,2,1, 4,5,6,7, 0,1,5,4,
                               1,2,6,5, 2,3,7,6, 3,0,4,7])
m.AddScaleOp().Set(Gf.Vec3f(1, 1, 1))   # 반드시 (1,1,1)

UsdPhysics.MeshCollisionAPI.Apply(m.GetPrim()).CreateApproximationAttr("convexHull")
```

### 2) 팔이 실제로 박스까지 내려가게 함

`maxGripDistance` 를 0.05 → **0.02** 로 조여서 **닿아야만 잡히게** 하고,
`HOME → ABOVE → PICK` 3 단계로 내려보냈다.

# 재발 방지 체크리스트

- [ ] **흡착 대상 프림에 `xformOp:scale` 이 걸려 있지 않은가?** ← 제일 먼저 볼 것
- [ ] 치수는 지오메트리에 직접 굽는다 (직육면체는 `Mesh`, `Cube`+scale 금지)
- [ ] 조인트 프레임을 계산할 때 `RemoveScaleShear()` 를 먼저 부른다
- [ ] 흡착이 이상하면 파라미터를 돌리기 전에 대상 프림의 scale 부터 확인
- [ ] 흡착 자세는 연직 오차 1° 이내 (전단 성분이 축력보다 먼저 병목이 된다)
- [ ] 이동은 드라이브 타깃 선형 보간 (스텝 입력 금지)
- [ ] 저장 전에 `drive:targetPosition == state:position` 확인
- [ ] 힘 상한은 물리가 아니라 컨트롤러에서 건다

# 부록 — 함께 겪은 함정

- **`isaac:retryInterval` 은 "재시도 간격" 이 아니다.** 닫으려고 시도하는 **총 시간(초)** 이다.
  `0` 이면 즉시 포기해서 영영 `Open` 에 머문다. → `10.0`
- **`mount` 고정 조인트는 아티큘레이션에서 빼면 안 된다** (`excludeFromArticulation = False`).
  빼면 그리퍼가 팔을 55 mm 뒤처져 따라가서 흡착이 성립하지 않는다.
  반대로 **패드 D6 조인트는 반드시 빼야** 한다 (`True`). 헷갈리는 부분이다.
- **그리퍼 몸통을 `link_6` 하위에 둘 수 없다.** PhysX 는 강체 중첩을 허용하지 않아서
  Add > Physics 메뉴에 Rigid Body 항목이 아예 안 뜬다. 아티큘레이션 밖에 두고 `mount` 로 매단다.
- **Play 중에 저장하지 말 것.** 그 순간의 런타임 상태가 초기 상태로 저장돼서
  프레임 0 에서 구속 위반으로 씬이 터진다.
- **`asyncio.ensure_future()` 의 반환값을 전역에 붙들 것.** 참조를 안 잡으면 태스크가
  GC 돼서 **에러 한 줄 없이** 중간에 사라진다. 코루틴 내부 예외도 조용히 삼켜지므로
  `try/except + traceback.print_exc()` 필수.
- **Script Editor 콘솔은 ASCII 만 출력한다.** `print()` 에 한글 넣으면 `???` 만 나온다.
  (GIF 로그의 `?? mass=5.0`, `suction ??? ??` 가 그것이다.)
- **Property 패널의 `Status` 는 갱신되지 않는다.** `get_gripper_status()` 로 확인할 것.
- **`close_gripper` 직후 같은 줄에서 상태를 읽으면 항상 `Closing`** 이다. 물리 스텝이
  한 번도 안 지났기 때문.
